Module 3 · Lesson 3.4

The ops debugger's toolkit: grep, sed, awk, jq, find & xargs

Lesson 3.3 gave you the plumbing — streams as the data type, pipes and redirection as the wiring, exit codes as control flow. This lesson gives you the power tools that live in the middle of the pipe: the six programs an operator reaches for a hundred times a day. grep selects lines, sed edits them, awk does columns and arithmetic, jq handles structured JSON, and find + xargs walk the filesystem and act on what they find. None of them is new syntax to memorise for its own sake — each is a stream filter that snaps into exactly the pipelines you already know how to build. Learn the shape of each, and the 3 a.m. question "which URL is throwing the most 500s, and what's the p95 latency on it?" becomes one line you can write, not one you google.

~75 min read Prerequisites: Lessons 3.1, 3.2, 3.3 Conceptual · hands-on throughout Module 3 · Milestone 3
Learning objectives

By the end of this lesson you will be able to:

  1. Place each tool on a single map — selection (grep, find), transformation (sed), computation over columns (awk), structured data (jq), and the stream→arguments adapter (xargs) — and pick the right one on sight.
  2. Read and write regular expressions — the shared pattern language under grep, sed and awk — including anchors, character classes, quantifiers and groups, and know when you need extended regex (-E).
  3. Use grep fluently: -i -v -c -n -o -r -E -F -w -A/-B/-C, and know why grep -F exists.
  4. Use sed for the 90% case — s/old/new/g, addressed edits, -n …p, deletion — and understand the danger of sed -i.
  5. Use awk as what it is — a tiny language of pattern { action } rules over auto-split fields ($1…$NF), with BEGIN/END, variables and associative arrays for grouping and summing.
  6. Use jq to query JSON by structure instead of guessing at whitespace — field access, [], select(), pipes and -r — and explain why JSON logs need it and not awk.
  7. Use find to name files by predicate (name, type, age, size) and find … -exec / xargs -0 -P to act on them safely, including the -print0/-0 null-separator discipline.
  8. Compose all six into real DevBoard incident-triage one-liners, and know the honest boundary where you should stop and write Python instead.
Where this sits on the map

Lesson 3.3 handed you the connectors: |, >, &&, globbing, quoting. This lesson fills the boxes those connectors join. Everything here is a stream filter — it reads stdin, writes stdout, sets an exit code — so it plugs into the exact model you already hold. Downstream, this toolkit is the beating heart of Lesson 3.6 (reading journalctl output), every log-triage step in Module 12 (Observability), the RUN lines that massage config in a Dockerfile (Module 7), and the shell steps of a GitHub Actions job that parse test output and fail the build (Module 9). Fluency in these six commands is the single highest-leverage manual skill in operating a Linux server — the difference between finding the answer in ten seconds and not finding it at all.

1 · Problem Statement

It is a Tuesday afternoon and DevBoard's error rate just spiked. You SSH into the production VPS (as your unprivileged user, per Lesson 3.2) and you have exactly what Lesson 3.3 gave you: a prompt, pipes, and the raw materials of the machine. But now the questions are sharper than "count the 500s," and the data comes in two different shapes — Nginx's access log is whitespace-separated text, and the Express app's log is one JSON object per line: 

# /var/log/nginx/access.log  — one request per line, space-separated
203.0.113.7 - - [17/Aug/2026:14:03:11 +0000] "GET /api/boards/42 HTTP/1.1" 500 812 "-" "axios/1.6" 0.184
198.51.100.9 - - [17/Aug/2026:14:03:11 +0000] "POST /api/login HTTP/1.1" 200 44 "-" "Mozilla/5.0" 0.031

# /var/log/devboard/app.log  — one JSON object per line ("JSON Lines")
{"ts":"2026-08-17T14:03:11Z","level":"error","route":"/api/boards/42","status":500,"ms":184,"msg":"pg: deadlock detected"}
{"ts":"2026-08-17T14:03:11Z","level":"info","route":"/api/login","status":200,"ms":31}

The questions in your head are precise, and each one defeats a plain grep | sort | uniq:

  • "Which route is throwing the most 500s right now, and what's its p95 latency — not from the count, but computed from the ms field?"
  • "The app log is JSON. I need every error-level line whose route starts with /api/boards — but grep 500 would also match a latency of 500 ms or a byte count of 500. I must match a field, not a substring."
  • "A config value changed across 30 files under /etc/devboard. I need to rewrite db.pool=10 to db.pool=20 in every one — as a repeatable, scriptable edit, not by opening each in an editor."
  • "Some upload job left thousands of stale temp files older than 7 days under /srv. I need to find exactly those — by age and size — and delete them, safely, even though some have spaces in their names."
  • "For each client IP, how many requests, and what fraction errored? That's grouping and arithmetic, not just counting identical lines."

Look at the shape of each. They are no longer "filter and count identical lines" — the job sort | uniq -c does. They are match by pattern, match a specific field, rewrite text, compute over columns, query a structure, and select files by properties and act on them. The pipe from Lesson 3.3 is still the wiring — but the boxes in the middle have to be smarter than sort and wc.

The core problem

Operating a server means constantly interrogating and reshaping unstructured or semi-structured text — logs, config, process lists, filesystem trees — with questions that are more than "how many?": match by pattern, edit in place, split into fields and do arithmetic, drill into nested JSON, and select files by their properties then act on each. The generic tools of Lesson 3.3 (sort, uniq, wc, cut) can't express these. We need a small set of specialised stream filters, each a master of one of these jobs, all sharing the same stdin→stdout interface so they compose in the same pipes. That set — grep, sed, awk, jq, find, xargs — is the ops debugger's toolkit.

The promise of this lesson: by the end, a line like awk '$9==500{c[$7]++} END{for(u in c) print c[u], u}' access.log | sort -rn | head reads to you as plainly as an English sentence — "for every request whose status field is 500, tally it by URL, then print the tallies, ranked" — and you can compose the JSON equivalent with jq without pausing.

2 · Historical Context

These tools were not designed together in a weekend. They accreted over a decade at Bell Labs, each solving the frustration the previous one left behind — which is exactly why they form such a clean progression from "match lines" to "a real programming language for text."

1968–1969 · Thompson, regular expressions, and the QED editor

Ken Thompson took Stephen Kleene's mathematical notion of a regular expression — a compact algebra for describing sets of strings — and built it into the qed and ed editors as a way to search text. This is the ancestor of everything in this lesson: the pattern language that grep, sed and awk all speak was born here.

1973 · grep is extracted from the editor

The story is famous. A colleague asked Thompson to find lines matching a pattern across a set of files. Rather than do it by hand in ed, Thompson took ed's command g/re/p — globally search for a regular expression and print — and made it a standalone program overnight. The name is literally that editor command. grep embodies the Unix philosophy perfectly: one tool, one job (select lines by pattern), composes with everything.

1973–1974 · sed — the editor as a filter

Lee McMahon wrote sed (the stream editor). The insight: the same search-and-replace commands you run interactively in ed could be applied non-interactively, line by line, to a stream flowing through a pipe. It made editing a composable pipeline stage — you could transform text on its way from one program to another without ever opening a file.

1977 · awk — a language for fields

Alfred Aho, Peter Weinberger and Brian Kernighan built awk (their initials) because sed's line-at-a-time substitution couldn't easily do the thing everyone actually wanted with tabular data: split each line into fields, refer to them by number, and do arithmetic and grouping. awk is a genuine programming language — variables, arithmetic, associative arrays, control flow — wrapped in a "for each line, run these rules" loop. It is the bridge between "text tools" and "real programs."

1987 · Perl absorbs them — and the pendulum swings back

Larry Wall built Perl explicitly to unify grep, sed, awk and shell into one language for bigger text-processing jobs. Perl (and later Python) is where you graduate when a pipeline outgrows one line — a boundary we treat honestly in §10. But for interactive, one-line questions, the small specialised tools stayed faster to reach for, which is why they're still what you type at 3 a.m.

2012 · jq — the awk of the JSON era

The web changed the shape of data. Logs, APIs and cloud tooling now emit JSON, which is nested and quoted — and therefore hostile to whitespace-splitting tools like awk. Stephen Dolan wrote jq to be for JSON what awk is for columns: a small, composable filter language that understands the structure, so you query by field path instead of praying that a value never contains a space. It completes the toolkit for the world DevBoard actually lives in.

find (1974, part of the original Unix utilities) and xargs (added early to bridge "a list of filenames on stdin" back into "arguments to a command") round out the set — they extend the same filter model from streams of text to the filesystem tree.

The through-line

One idea — regular expressions — seeds a family of tools, each adding one capability the last one lacked: grep selects lines by pattern; sed edits them; awk adds fields, arithmetic and memory; jq re-does awk's job for structured data; find + xargs stretch the model over the filesystem. Fifty years on, every one is still installed on every server and container you will ever touch.

3 · The Previous Solution (in detail)

Before these tools were reflexes, how did people answer §1's questions? Two default strategies, both of which still trap engineers who haven't internalised the toolkit.

3.1 Open the file in an editor and eyeball / hand-edit it

The GUI-brain instinct: open the log in an editor, use its find box, scroll, and manually change lines. Fine for a 200-line file you look at once. But DevBoard's access log is 400 MB, the config change spans 30 files, and "eyeball it" is neither repeatable nor automatable — you cannot paste an eyeball into a deploy script or a CI step. It also does not compute: no editor tells you the p95 latency per route.

3.2 Reach only for the generic Lesson-3.3 tools

The half-fluent instinct: force every question through grep | sort | uniq -c and cut. This works for "count identical lines," but it buckles the moment you need to match a field rather than a substring, or do arithmetic, or touch JSON: 

# You want "requests whose STATUS is 500". You reach for grep:
grep " 500 " access.log        # ⚠️ also matches a 500-BYTE response, or 500 ms latency,
                                #    or an IP like 10.0.0.500 — grep sees a substring, not a field.

# You want the URL column. cut splits on a SINGLE char, but the log is space-separated
# with QUOTED fields that themselves contain spaces:
cut -d' ' -f7 access.log       # ⚠️ "GET /api/boards/42 HTTP/1.1" is ONE logical field but
                                #    THREE space-separated tokens — cut miscounts every column after it.

# You want the average latency. sort/uniq/wc cannot add numbers at all. Dead end.

# The app log is JSON. grep for a value works by luck until a message contains that text:
grep '"status":500' app.log    # brittle: breaks on a space after the colon, key order, nesting…

The assumptions these approaches bake in:

Text is a flat blob of characters, not records with fields
Substring matching (plain grep) and single-char splitting (cut) treat a line as undifferentiated bytes. They have no concept of "the 7th field, correctly handling quoted spaces."
You can only count, never compute
sort | uniq -c tallies identical lines. It cannot average, sum, take a max, or compute a percentile — because it has no variables and no arithmetic.
Structure is something you match through, not into
Treating JSON as text means matching brittle substrings of its serialisation, instead of asking for a value by its path in the structure. It works until the day it silently doesn't.
Editing is a manual, interactive act
Changing text means a human in an editor — so it can't be scripted, reviewed in a diff, or run across 30 files identically.

Each of these works for the smallest version of the problem, which is exactly why they're seductive. The next section is where they hit their wall — and every wall points at the specific tool that removes it.

4 · Why It Failed (as an operating model)

"Failed" is scoped, as always: an editor and grep|sort|uniq are the right tools for the jobs they fit. They fail as a general way to interrogate a running system, because production questions routinely need field-awareness, arithmetic, structure and scale — and each of those is a hard wall for the naive approach.

4.1 Substring matching gives false positives and false negatives

Matching " 500 " to find HTTP 500s is a coin flip: it also matches a 500-byte body, a 500 ms timing, or the number 500 anywhere on the line — and it misses a 500 that happens to sit at the start or end of the line where your spaces don't line up. When the answer drives an incident response, "roughly matches" is a bug. You need to match a column with a value, which is awk's home turf: $9 == 500.

4.2 The generic tools cannot do arithmetic or keep state

"Average latency per route," "p95," "error rate per IP" — every one requires summing, dividing, or remembering values across lines. sort, uniq and cut have no variables and no math; the wall is absolute. This is the exact gap awk's associative arrays and arithmetic were invented to fill.

4.3 JSON breaks whitespace tools by design

JSON is nested and its string values can contain spaces, commas, colons and even escaped braces. Any tool that splits on a delimiter (cut, awk's default) will eventually cut through the middle of a value and hand you garbage — not always, but unpredictably, which is worse. A log message "msg":"error: 500 rows, done" destroys a grep '"status":500' heuristic. Structured data demands a structure-aware tool: jq.

4.4 Manual editing doesn't scale or reproduce

Changing one value in 30 files by hand is slow, error-prone, and — fatally — not reproducible. You can't code-review an editor session, can't re-run it on the staging box, can't put it in a deploy script. Repeatable text transformation is precisely what sed (for streams) and find … -exec sed -i (for many files) provide.

4.5 "Act on every matching file" outgrows the glob

A glob (*.log) matches filenames in one directory by name. It cannot say "every file under this whole tree, older than 7 days, larger than 100 MB, whatever it's named." And once you've selected thousands of files, passing them all to one command can overflow the command line's length limit. Selecting by predicate across a tree is find; safely turning that list into command arguments is xargs.

The pattern behind all five failures

Every wall is the same shape: the generic tools see undifferentiated text, but the questions are about structure, computation, and scale. The fix is not a bigger generic tool — it's a small set of specialists, each fluent in one missing dimension (patterns, editing, fields+math, JSON structure, filesystem predicates), all wearing the same stdin→stdout interface so they drop into the pipelines you already build. Meet the specialists.

5 · The New Solution

The solution is a toolkit of composable stream filters, organised by the kind of job each does. The single most useful thing you can carry out of this lesson is the map: given a question, which tool is its natural home. Vocabulary first, then the map.

5.1 The core vocabulary

Regular expression (regex)
A compact pattern language for describing sets of strings — "a digit," "three letters then a dot," "starts with /api." It is the shared engine under grep, sed and awk; learn it once and it pays off in all three (and in your editor, and in most languages).
grep — the selector
Reads lines, prints the ones that match a regex (or, with -v, the ones that don't). Pure filter: it never changes a line, only decides whether it passes. "Which lines are about X?"
sed — the stream editor
Reads lines and transforms them — most often substitution (s/old/new/) — then prints the result. "Rewrite every line like this." Editing as a pipeline stage.
awk — the field processor
Splits each line into fields ($1, $2, … $NF), and runs your pattern { action } rules against each. It has variables, arithmetic and associative arrays, so it can group, sum, average and rank. "For each record, compute something across its columns."
jq — the JSON processor
awk for structured data. Parses JSON and lets you select and transform by path (.route, .[], select(.status==500)). Understands nesting and quoting, so it never mis-splits a value.
find — the filesystem selector
grep for the directory tree: walks a whole subtree and prints the paths matching predicates — name, type, age (-mtime), size (-size), depth. Optionally acts on each with -exec.
xargs — the stream→arguments adapter
Reads items on stdin and turns them into command-line arguments for a program you name. The bridge from "a pipeline that produces a list of things" to "a command that takes them as arguments," batching to respect the argv length limit and parallelising with -P.
The one map to hold onto

Ask what kind of job it is. Select lines by pattern → grep. Edit/rewrite text → sed. Split into columns and do math or grouping → awk. The data is JSON → jq. Select files by their properties across a tree → find. Turn a produced list back into a command's arguments → xargs. Every pipeline in this lesson is these six specialists snapped into the pipe from Lesson 3.3.

5.2 The shape of the solution

Return to §1's hardest question — the noisiest 500 route and its p95 latency — and watch the toolkit dissolve it. First, from the space-separated Nginx log with awk (fields, comparison, grouping, arithmetic), then from the JSON app log with jq (same question, structured source): 

# TEXT log → awk matches the STATUS FIELD ($9), tallies by ROUTE field, ranks:
awk '$9==500 {count[$7]++} END {for (r in count) print count[r], r}' access.log \
  | sort -rn | head -3
#      └ match field, not substring ┘└ group+count in an array ┘└ print┘   └ rank ┘

# JSON log → jq queries by STRUCTURE, no whitespace guessing:
jq -r 'select(.status==500) | .route' app.log | sort | uniq -c | sort -rn | head -3
#         └ pick error records ┘ └ pull the route ┘ └───── group, count, rank ─────┘

Now the rest of §1, one tool each. Rewrite a config value across 30 files? find /etc/devboard -name '*.conf' -exec sed -i 's/db.pool=10/db.pool=20/' {} + — find selects the files, sed does the repeatable edit. Match only error-level lines on a /api/boards route in JSON? jq 'select(.level=="error" and (.route | startswith("/api/boards")))' app.log — a structural predicate, no false positives. Delete stale temp files safely, even with spaces in names? find /srv -name '*.tmp' -mtime +7 -print0 | xargs -0 rm — predicate selection, null-safe hand-off. Error rate per IP? One awk program with two arrays. One toolkit, every question in §1 answered — and none of them needed a program written.

6 · Internal Mechanics

Now each tool in the depth you need to use it, not just recognise it. We take them in an order that builds: (6.1) regular expressions, the shared language; (6.2) grep; (6.3) sed; (6.4) awk, the centrepiece; (6.5) jq; (6.6) find; (6.7) xargs and the null-separator discipline; (6.8) assembling all six into DevBoard triage.

6.1 Regular expressions — the language under grep, sed and awk

A regex is a pattern that matches a set of strings. Three tools in this lesson speak it, so learning it once triples your return. The core alphabet:

PatternMatchesExample
.any single charactera.c → abc, a5c
*zero or more of the preceding itemab*c → ac, abc, abbc
^ … $start / end of the line (anchors)^GET matches lines beginning with GET
[abc] / [0-9]one character from a set / range[45][0-9][0-9] → a 4xx or 5xx code
[^abc]one character not in the set[^ ] → any non-space char
\escape — treat a metacharacter literally\. → a literal dot; 3\.14
+ ? {n,m} EREone-or-more / zero-or-one / n-to-m repeats[0-9]+ → one or more digits
(…) | EREgrouping / alternation ("or")(GET|POST) → either word

The one wrinkle that confuses everyone: there are two dialects. Basic regex (BRE) is the default in grep and sed, and it makes you backslash-escape +, ?, (, | and { to get their special meaning (\+, \(…\)). Extended regex (ERE) — turned on with grep -E / sed -E, and the default in awk — lets you write those plainly. Life is easier in ERE; reach for -E and stop escaping.

Regex * is not glob *

A trap for the newly-fluent. In a glob (Lesson 3.3), * means "any run of characters." In a regex, * means "zero or more of the thing before it" — so the regex that means "anything" is .* (any char, repeated). grep abc* looks for ab followed by zero-or-more cs, not "abc followed by anything." Same symbol, different language. Keep the two straight and a whole class of "why didn't that match?" vanishes.

6.2 grep — select lines by pattern

grep PATTERN [file…] prints every line that matches. It is a pure filter — it never alters a line — and it sets a useful exit code: 0 if it matched anything, 1 if not (§6.5 of Lesson 3.3), which is why grep -q is the idiom for "does this appear?" in scripts. The flags you'll use daily:

FlagEffectWhen
-icase-insensitivegrep -i error catches Error, ERROR
-vinvert — print non-matching linesstrip out noise: grep -v healthcheck
-cprint a count, not the lines"how many matches?" in one step
-nprefix each match with its line numberjumping to it in an editor after
-oprint only the matched part, one per lineextract just the thing (feed to sort/uniq)
-r / -Rrecurse through a directory treegrep -rn TODO src/
-Eextended regex (no escaping + ? ( ) |)any non-trivial pattern
-Ffixed string — no regex at allsearching for literal ., [, an IP
-wmatch whole words onlygrep -w id skips uuid, width
-A/-B/-C NN lines after/before/contextsee the stack trace around an error

Two flags earn special mention. grep -F (fixed strings) exists because your search term often contains regex metacharacters: to find the literal IP 10.0.0.1, plain grep 10.0.0.1 treats each . as "any char" and over-matches; grep -F 10.0.0.1 searches for the exact text and is also faster. And grep -o turns grep into a mini-extractor — grep -oE '[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+' access.log | sort | uniq -c pulls every IP out of a line, ready to count. 

grep -i "deadlock" app.log                 # case-insensitive search
grep -c "level\":\"error" app.log          # how many error lines? (count only)
grep -rn "TODO" src/                        # every TODO under src/, with file:line
grep -A3 "Traceback" app.log               # the error line + 3 lines of trace after it
grep -vE "healthcheck|favicon" access.log  # drop the boring noise before you look
A note on ripgrep (rg)

On your laptop you'll often meet rg — a modern, much faster grep that respects .gitignore and defaults to recursive, ERE search. It's wonderful and worth installing. But it is not guaranteed to exist on a bare production server or inside a minimal container, whereas grep always is. Learn grep as the portable baseline; enjoy rg where you have it.

6.3 sed — edit a stream, line by line

sed reads each line, applies your editing commands, and prints the result. Ninety percent of real usage is one command — substitute: 

sed 's/old/new/'      # replace the FIRST "old" on each line with "new"
sed 's/old/new/g'     # GLOBAL: replace EVERY "old" on each line (the flag you usually want)
sed 's/old/new/gi'    # global + case-insensitive
sed -E 's/[0-9]+/N/g' # ERE: replace every run of digits with N  (redact numbers)

The structure is s/PATTERN/REPLACEMENT/FLAGS. The / is just a delimiter — if your pattern contains slashes (like a path), change the delimiter to avoid a thicket of escapes: sed 's#/old/path#/new/path#' reads far better than sed 's/\/old\/path/\/new\/path/'. In the replacement, & means "the whole matched text," and \1, \2 refer to captured groups — so you can reshape, not just replace: 

# Wrap every matched IP in brackets ( & = the match )
sed -E 's/[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+/[&]/'

# Swap "user=alice id=42" → "42:alice" using capture groups \1 \2
sed -E 's/user=([a-z]+) id=([0-9]+)/\2:\1/'

sed can also address which lines a command applies to — by line number, by range, or by regex — and can delete or print selectively. With -n (suppress the default "print every line") plus the p command, sed becomes a line-slicer: 

sed -n '10,20p' file       # print ONLY lines 10–20 (like a targeted head/tail)
sed '/^#/d' config.conf     # DELETE every comment line (starts with #)
sed '/DEBUG/d' app.log      # drop every line containing DEBUG
sed -n '/START/,/END/p' f   # print the block between a START line and an END line
The -i footgun: editing files in place

By default sed writes to stdout and touches nothing. sed -i edits the file itself — powerful and dangerous. Never run sed -i blind. Run it without -i first and eyeball the output; a wrong regex can silently mangle a production config. When you do commit, keep a backup: GNU sed's sed -i.bak 's/…/…/' file writes the edited file and saves the original as file.bak. (Caveat: macOS/BSD sed -i requires an explicit suffix argument — sed -i '' … for no backup — a classic portability trap between your Mac and the Linux server.)

6.4 awk — the field processor (the centrepiece)

awk is the tool that turns "text on a screen" into "data you can compute over," and it repays real study. Its entire model is one loop you don't write: for every input line (a record), split it into fields, then run each of your pattern { action } rules against it.

Record & fields
Each line is a record. awk auto-splits it on whitespace into fields $1, $2, … . $0 is the whole line; $NF is the last field (NF = "number of fields"); NR is the current record number (line count so far).
pattern { action }
The core structure. For each line, if the pattern is true, run the action. Omit the pattern → run on every line. Omit the action → default is print $0. So awk '/error/' behaves like grep, and awk '{print $7}' prints the 7th field of every line.
BEGIN { } … END { }
Special patterns: the BEGIN block runs once before any input (set things up, print a header), and END runs once after all input (print totals). The END block is where summaries live.
Variables & associative arrays
awk has real variables and arithmetic, and — crucially — associative arrays indexed by strings: count["/api/login"]++. This is how you group and tally, the thing uniq -c can only do for pre-sorted identical lines.
FS / OFS
The input and output field separators. Default is whitespace; set -F, for CSV or -F: for /etc/passwd. OFS is what print a, b puts between fields.

Watch the model climb from "grep clone" to "computes a percentile" in five steps:

# 1. pattern only → acts like grep
awk '/error/' app.log

# 2. action only → print a field (space-split); $9 is the status in our access.log
awk '{print $9}' access.log

# 3. pattern + action → match a FIELD (no false positives), print the URL
awk '$9==500 {print $7}' access.log

# 4. associative array → GROUP and COUNT 500s per URL (no sort needed to group!)
awk '$9==500 {count[$7]++} END {for (u in count) print count[u], u}' access.log | sort -rn

# 5. arithmetic + END → average latency (last field $NF) per route
awk '{sum[$7]+=$NF; n[$7]++} END {for (r in sum) printf "%.1f ms  %s\n", sum[r]/n[r], r}' access.log \
  | sort -rn | head

Step 4 is the payoff moment. uniq -c can only count lines that are already identical and adjacent (hence the mandatory sort before it in Lesson 3.3). awk's array counts by an arbitrary key you choose — the URL field — with no pre-sorting, and in one pass over the data. And because it has arithmetic, step 5 does something sort|uniq physically cannot: compute an average. A short but complete "error rate per IP" program shows the two-array idiom that answers §1's last question: 

awk '{
        total[$1]++                 # count all requests per client IP ($1)
        if ($9 >= 500) err[$1]++    # count the erroring ones
     }
     END {
        for (ip in total)
           printf "%-15s %4d reqs  %5.1f%% errors\n",
                  ip, total[ip], 100*err[ip]/total[ip]
     }' access.log | sort -k2 -rn | head
The mental model

Picture awk as a tiny spreadsheet engine that reads one row at a time. Each line is a row; $1…$NF are its columns; your { } blocks are formulas that run per row; arrays are named cells that accumulate across rows; and the END block is the summary row at the bottom. Everything else — if, loops, printf — is there to make those formulas expressive. If a question is "per something, compute a number," it's an awk question.

6.5 jq — awk for JSON

The instant your data is JSON — DevBoard's app logs, docker inspect, a kubectl -o json, any REST API — the whitespace tools become a liability and jq becomes the answer. jq parses the JSON into a real structure and runs a small filter language over it. A filter is an expression that takes one JSON value in and emits zero or more JSON values out — and, exactly like the shell, filters compose with |.

FilterDoesExample on our app.log line
.the whole value (identity) — pretty-prints itjq . app.log
.fieldaccess an object field.route → "/api/boards/42"
.a.bdrill into nested fields.req.headers.host
.[]iterate array elements (one output each).items[]
select(cond)keep the value only if cond is trueselect(.status==500)
a | bpipe: feed a's output into bselect(.status==500) | .route
-rraw output: strings without JSON quotesso the result pipes cleanly into sort/uniq
-ccompact: one JSON value per linere-emit JSON Lines for the next stage

The -r (raw) flag is the one beginners forget and then get puzzled by: without it, jq prints strings with their JSON quotes ("/api/login"), which then pollutes a downstream sort | uniq -c. With -r you get bare /api/login, ready to compose. Watch the §1 question answered structurally, then some staples: 

# The §1 question, on JSON: routes of 500-status records, ranked
jq -r 'select(.status==500) | .route' app.log | sort | uniq -c | sort -rn | head

# Structural predicate — error level AND route under /api/boards (no false positives)
jq 'select(.level=="error" and (.route | startswith("/api/boards")))' app.log

# Reshape into a compact "route status ms" line for awk to average
jq -r '[.route, .status, .ms] | @tsv' app.log | awk '{sum[$1]+=$3; n[$1]++} END{for(r in sum) print sum[r]/n[r], r}'

# Count log lines by level  (group-by, jq-native)
jq -r '.level' app.log | sort | uniq -c | sort -rn

Notice the last-but-one line: jq and awk are partners, not rivals. Use jq to safely extract fields out of the structure into flat columns (here with @tsv), then hand those columns to awk for arithmetic. Structure-aware extraction up front, column math after — a pattern you'll use constantly.

6.6 find — select files by predicate across a tree

find is grep for the filesystem. find START_DIR [predicates] [action] walks the entire subtree under START_DIR and, for each entry, tests your predicates; the survivors are printed (or acted on). The everyday predicates:

PredicateSelects entries…
-name '*.log'whose name matches a glob (quote it so the shell doesn't expand it first!)
-iname '*.LOG'same, case-insensitive
-type f / -type dthat are regular files / directories
-mtime +7 / -mtime -1modified more than 7 days ago / less than 1 day ago
-size +100Mlarger than 100 MB
-maxdepth 2don't descend deeper than 2 levels
-path '*/node_modules/*' -pruneskip an entire subtree (e.g. don't recurse into node_modules)

Predicates are ANDed together by default; combine and act: 

find /srv -type f -name '*.tmp' -mtime +7          # stale temp files, tree-wide, by name+age
find /var/log -type f -size +100M                  # the disk hogs under /var/log
find . -type d -name node_modules -prune -o -type f -name '*.js' -print  # all .js, skipping deps

# ACT on each match. Two forms of -exec:
find /srv -name '*.tmp' -mtime +7 -exec rm {} \;   # runs rm ONCE PER FILE ({} = the path)
find /srv -name '*.tmp' -mtime +7 -exec rm {} +    # batches MANY files into ONE rm (faster)

In -exec, {} is replaced by the matched path. The terminator matters: \; runs the command once per file; + packs as many paths as fit into one invocation (far fewer processes, much faster on thousands of files). find's -exec … + is often all you need — but the moment you want to pipe the file list into a chain (grep it, count it, parallelise it), you hand off to xargs.

6.7 xargs — turn a stream of items into a command's arguments

Some programs read stdin (grep, wc); many don't — rm, cp, mv, kill, docker rm take their targets as arguments, not on stdin. xargs is the adapter: it reads items from stdin and appends them as arguments to a command you name. echo file1 file2 | xargs rm runs rm file1 file2. Beyond convenience, xargs solves a real problem — the kernel caps how long a single command line can be, so rm $(find …) with 100,000 matches fails with "Argument list too long"; xargs automatically batches the items into as many rm calls as needed.

The null-separator discipline (this one bites everyone)

By default xargs splits its input on whitespace — so a filename containing a space (my report.log) is torn into two arguments, and you delete the wrong things. The fix is a pact between the producer and consumer: have find separate paths with a NUL byte (the one character that can't appear in a filename) using -print0, and tell xargs to split on NUL with -0. Make find … -print0 | xargs -0 … your automatic habit whenever filenames are involved. (Similarly, grep -rlZ pairs with xargs -0.) 

find /srv -name '*.tmp' -mtime +7 -print0 | xargs -0 rm        # ✅ null-safe deletion
find . -name '*.js' -print0 | xargs -0 grep -l "TODO"          # which JS files mention TODO
docker ps -aq | xargs -r docker rm                             # -r: do nothing if input is EMPTY
find . -name '*.png' -print0 | xargs -0 -P4 -n1 optipng        # -P4: run 4 in PARALLEL, -n1: one file each
find . -name '*.log' -print0 | xargs -0 -I{} mv {} {}.archived # -I{}: put the arg in a SPECIFIC spot

Four flags carry most of the value: -0 (null-separated, always with find -print0), -r / --no-run-if-empty (don't run the command at all if stdin was empty — avoids docker rm with no args erroring), -P N (run N invocations in parallel — a free speedup on multi-core boxes), and -I{} (place the argument at a chosen position rather than only at the end, needed for mv-style commands). Between find -exec … + and xargs you can act on any set of files you can describe.

6.8 Putting it together: the toolkit as DevBoard triage

Everything composes back into the pipe from Lesson 3.3. Read each as a sentence:

# Top 5 routes by 500-count, from the text access log (awk matches the status FIELD)
awk '$9==500 {c[$7]++} END{for(u in c) print c[u], u}' access.log | sort -rn | head -5

# Same answer from the JSON app log (jq queries by structure)
jq -r 'select(.status==500) | .route' app.log | sort | uniq -c | sort -rn | head -5

# Average latency per route (jq extracts safely → awk does the math)
jq -r '[.route,.ms] | @tsv' app.log | awk '{s[$1]+=$2; n[$1]++} END{for(r in s) printf "%.0fms  %s\n", s[r]/n[r], r}' | sort -rn

# Bump a config value in every .conf under /etc/devboard, keeping backups
find /etc/devboard -name '*.conf' -exec sed -i.bak 's/db.pool=10/db.pool=20/' {} +

# Reclaim disk: delete *.tmp older than 7 days under /srv, safely (spaces in names OK)
find /srv -type f -name '*.tmp' -mtime +7 -print0 | xargs -0 -r rm -v

# Live tail, keep only real errors, extract the route, count as they stream by
tail -f app.log | jq -rc 'select(.level=="error") | .route' | awk '{c[$0]++; print c[$0], $0}'

This is the lesson's payoff: you didn't memorise six commands, you learned a division of labour. Selection, transformation, computation, structure, filesystem, adaptation — a slot for every question, all snapping into the same pipe. Everything downstream in this course (journald in 3.6, the log stack in Module 12, the shell steps of CI in Module 9) is this toolkit, applied.

7 · Real Industry Example

This is not beginner scaffolding that professionals outgrow — it is the day-to-day instrumentation of running systems, from a solo VPS to a hyperscaler. Four concrete places you'll meet it:

Incident response is grep + awk + jq

Long before the dashboard loads (Module 12), the on-call engineer who can type jq -r 'select(.status>=500)|.route' app.log | sort | uniq -c | sort -rn has the culprit route in ten seconds. In postmortems across the industry, "grepped the logs and found…" is the single most common first step. Fluency here is measurably faster mean-time-to-recovery.

CI pipelines parse output with these tools

A GitHub Actions step (Module 9) that must fail the build when coverage drops runs the test output through grep/awk to extract the number and compare it — then relies on the exit code (Lesson 3.3) to gate the merge. jq parses the JSON that gh, aws and kubectl emit, feeding decisions in the pipeline.

Cloud & container CLIs speak JSON → jq

aws … --output json, docker inspect, kubectl get -o json, gh api — the entire modern cloud toolchain emits JSON, and jq is the universal glue for extracting one field, filtering a list, or reshaping it for the next command. It is arguably the most-installed non-standard binary on professional servers for exactly this reason.

Bulk operations run on find + xargs

"Rotate every log older than 30 days," "re-encode 40,000 images," "remove all stopped containers" — fleet-scale maintenance is find … -print0 | xargs -0 -P in a cron job. The -P parallelism turns an overnight job into a ten-minute one, and the null-separator discipline is what keeps it from deleting the wrong file at 2 a.m.

The Aho–Weinberger–Kernighan book and the original Bell Labs memos are still cited because the model never needed replacing: professional operations at Google, Netflix, and every serious shop bottom out in these filters somewhere, precisely because "match, extract, compute, decide" is what interrogating a running system is.

9 · Advantages

  • The right specialist for each dimension. Pattern, edit, compute, structure, filesystem, adapt — each tool is a master of one, so questions map cleanly onto tools instead of being forced through one blunt instrument.
  • One shared interface, infinite composition. Every tool reads stdin and writes stdout, so they combine with each other and with the Lesson 3.3 tools in any order. jq→awk, find→xargs→grep — the pipe is the integration.
  • Regex learned once pays off three times. The same pattern language drives grep, sed and awk (and your editor, and most languages). It's the highest-leverage sub-skill in the set.
  • Interactive and automatable are the same artifact. The one-liner that found the answer at 3 a.m. pastes verbatim into a cron job, a deploy script, or a CI step — exploration and automation share one syntax.
  • Constant memory over unbounded data. Because they stream (Lesson 3.3), a 400 MB log or an endless tail -f flows through awk/jq in tiny chunks — you compute over data far larger than RAM.
  • Universal and stable. grep, sed, awk, find, xargs are on every Linux box and nearly every container; jq is a one-line install. Learn them once, use them on every machine for the rest of your career.

10 · Limitations

  • Regex is powerful and treacherous. The two dialects (BRE vs ERE), greedy matching, and escaping rules make patterns easy to get subtly wrong. A regex that works on your sample can over- or under-match on real data — always test against real lines.
  • Field-splitting is fragile for anything but simple columns. awk's whitespace split mishandles quoted fields with embedded spaces (the Nginx request field, real CSV with quoted commas). For true CSV use a CSV-aware tool (csvkit, or a small script); for JSON use jq, never awk.
  • sed -i and xargs rm are genuinely dangerous. An in-place edit with a bad regex, or a whitespace-split filename, can corrupt config or delete the wrong files irreversibly. The safety habits (dry-run first, -print0/-0, keep backups) are not optional.
  • Portability gaps between GNU and BSD. Your Mac (BSD tools) and the Linux server (GNU tools) differ on sed -i, find options, and grep -P. A one-liner that works locally can fail on the server. When in doubt, test on the target.
  • They don't scale to programming-in-the-large. Past roughly a screenful — multiple data sources, real error handling, tests, reuse — a pile of piped one-liners becomes unmaintainable. That's the signal to rewrite in Python (with its json, re, csv modules). Shell tools are scalpels, not load-bearing beams.
  • Read-optimised, not audit-trailed. These tools give you an answer, not a durable record. For questions you'll ask repeatedly, or need alerting on, the answer is a real observability stack (Module 12) — the toolkit is the first responder, not the monitoring system.

11 · Common Misconceptions

"grep 500 finds the HTTP 500 errors."

It finds lines that contain the substring "500" anywhere — a 500-byte response, a 500 ms latency, an IP ending in 500, the number in a message. To match the actual status you must match the field: awk '$9==500' (or jq 'select(.status==500)' for JSON). Substring ≠ field; conflating them produces both false positives and false negatives, and it always seems to work on your small test file.

"Regex * means 'anything', like a glob."

In a regex, * means "zero or more of the preceding item," so "anything" is .*. grep ab* matches a followed by zero-or-more bs — not "ab then anything." Globs (filenames) and regexes (text patterns) are different languages that unluckily share the character; keeping them straight removes a huge class of "why didn't it match?" confusion.

"awk and jq are two ways to do the same thing; pick one."

They serve different data shapes and are best combined. awk is for whitespace/columnar text and can do arithmetic; jq is for nested, quoted JSON and never mis-splits a value. The idiomatic pipeline uses jq to extract fields safely out of the structure into flat columns, then awk to do math on them. Using awk on raw JSON, or jq on flat text, is the wrong tool for the shape.

"sed edits the file."

By default sed reads a file (or stdin) and writes the transformed result to stdout, changing nothing on disk — that's what makes it a pipeline stage. Only sed -i edits the file in place, and it's irreversible without a backup. Always run the substitution without -i first to preview, then add -i.bak to keep the original.

"find's -exec is basically the same as piping to xargs."

They overlap but differ. -exec … + is self-contained and needs no separator trickery, but it can't pipe the list through a chain or parallelise. xargs can filter, count, and run -P in parallel — but you must pair it with find -print0 and xargs -0 to survive spaces in filenames. Use -exec + for a simple act-on-each; use find -print0 | xargs -0 when you need the pipeline's flexibility or parallelism.

"xargs just saves typing; the defaults are fine."

Default xargs splits on whitespace, so a filename with a space becomes two arguments and you act on the wrong things — a real cause of data loss. Make find … -print0 | xargs -0 automatic. Also add -r so an empty input doesn't run the command with no arguments (e.g. a docker rm that then errors). The defaults are a footgun, not a convenience.

13 · Summary

  • The toolkit is a division of labour: grep selects lines by pattern, sed edits text, awk computes over fields, jq queries JSON, find selects files by predicate, and xargs turns a produced list into a command's arguments. Match the question to the job, and the tool is obvious.
  • Regular expressions are the shared language of grep/sed/awk — anchors (^ $), classes ([…]), quantifiers (* + ?), groups ((…) |) — with two dialects; reach for extended regex (-E) to stop escaping. Regex * ("zero or more of the previous") is not glob *.
  • grep is a pure selector with a useful exit code; master -i -v -c -o -r -E -F -w -A/-B/-C, and remember -F for literal strings and -o for extraction.
  • sed is s/old/new/g plus addressed edits and -n …p slicing; it writes to stdout by default — only sed -i touches the file, so preview first and keep a .bak.
  • awk is the centrepiece: a pattern { action } loop over auto-split fields ($1…$NF, NR, NF) with BEGIN/END, arithmetic, and associative arrays for grouping and summing — matching a field ($9==500) instead of a substring, and computing what sort|uniq never can.
  • jq is awk for JSON: query by path (.route, .[], select()), pipe filters with |, and use -r to emit raw strings for the next stage. Pair it with awk — jq extracts, awk computes.
  • find selects files across a tree by name/type/age/size and can act with -exec … {} +; xargs adapts a stream into arguments, batching past the argv limit and parallelising with -P. Always pair find -print0 with xargs -0 to survive spaces in filenames.
  • These are first responders, not a monitoring system: superb for interactive triage and scripting, but past a screenful — or for anything you'll ask repeatedly — graduate to Python (Limitations) or a real observability stack (Module 12).
The lesson in one line

Give each kind of question its specialist — grep to select, sed to edit, awk to compute over columns, jq for JSON, find+xargs for the filesystem — snap them into the pipe from Lesson 3.3, and any question you can phrase about a running system becomes one line you can write.

How to use this

Answer in your own words before revealing the model answer — two or three sentences each. You're ready for Lesson 3.5 (packages, repositories & the software supply chain) when you can answer Q1, Q3, Q5 and Q8 cold and have completed E1–E7 on a real machine.

Map each of the six tools to the kind of job it does.

grep — select lines by pattern. sed — edit/rewrite text. awk — split into fields and compute (arithmetic, grouping) over columns. jq — query and transform structured JSON by path. find — select files across a tree by predicate (name/type/age/size). xargs — turn a stream of items into a command's arguments. All share the stdin→stdout interface, so they snap into the same pipe.

Why is grep 500 access.log the wrong way to find HTTP 500 errors, and what's right?

grep 500 matches the substring "500" anywhere on the line — a 500-byte body, a 500 ms latency, an IP, a message — giving false positives (and it can miss 500s formatted differently). The status is a specific field, so match it as one: awk '$9==500' for the space-separated log, or jq 'select(.status==500)' for JSON. Substring ≠ field.

In a regex, what does * mean, and how is it different from a glob's *?

In a regex, * means "zero or more of the preceding item," so ab* is "a, then any number of b's" and "match anything" is .*. In a glob (filenames, Lesson 3.3), * means "any run of characters." Same symbol, two different languages; conflating them is a top source of "why didn't it match?" bugs.

What is the difference between BRE and ERE, and how do you get ERE in grep/sed?

Basic regex (BRE) is the default in grep/sed and requires backslash-escaping the special forms + ? ( ) { } | (e.g. \(…\), \+). Extended regex (ERE) lets you write those plainly and is the default in awk. Turn it on with grep -E / sed -E. Prefer ERE — it's far more readable and stops the escaping thicket.

Explain awk's execution model: records, fields, patterns/actions, BEGIN/END.

awk loops over input one line (a record) at a time, auto-splitting it into fields $1…$NF ($0 is the whole line). For each line it runs your pattern { action } rules: if the pattern is true, the action runs (default action is print $0; default pattern is "always"). BEGIN{} runs once before any input and END{} once after all of it — END is where you print totals accumulated in variables/arrays.

How does awk's count[$7]++ differ from sort | uniq -c, and why does it matter?

uniq -c counts only adjacent identical lines, so it needs a sort first and can only tally whole lines. awk's associative array count[$7]++ tallies by an arbitrary key you choose (here the URL field), in a single pass, with no pre-sorting — and because awk has arithmetic, it can also sum and average, which sort|uniq cannot do at all. That's the jump from "count identical lines" to "compute per-group statistics."

Why use jq instead of awk/grep on JSON logs, and what does -r do?

JSON is nested and its string values can contain spaces, commas and colons, so any whitespace/delimiter splitter (awk default, cut) will eventually cut through the middle of a value and return garbage. jq parses the structure and lets you address values by path (.status, select(.level=="error")), immune to spacing and key order. -r ("raw") prints strings without their JSON quotes, so results pipe cleanly into sort|uniq instead of arriving as "quoted" tokens.

What does sed do by default vs with -i, and what's the safe habit?

By default sed reads input and writes the transformed result to stdout, leaving files untouched — which is what makes it a pipeline stage. sed -i edits the file in place, irreversibly. The safe habit: run the substitution without -i first to preview the change, and when committing use -i.bak so the original is saved as file.bak. (Note the GNU vs BSD/macOS difference in how -i takes its suffix.)

When would you use find … -exec … {} + vs find … -print0 | xargs -0 …?

Use -exec … {} + for a simple "run this command on each match" — it's self-contained and needs no separator handling. Switch to find -print0 | xargs -0 when you need pipeline flexibility (filter/count the list first) or parallelism (xargs -P). The -print0/-0 pairing separates paths by the NUL byte so filenames containing spaces or newlines aren't split into multiple arguments.

Why is find … | xargs rm dangerous by default, and how do you make it safe?

xargs splits its input on whitespace by default, so a filename like my report.tmp becomes two arguments (my and report.tmp) and rm deletes the wrong things. Make it safe with the null-separator pact: find … -print0 | xargs -0 rm, which splits only on the NUL byte that can't occur in filenames. Add -r so an empty input doesn't run rm with no arguments, and preview with xargs -0 echo rm before committing.

Give the idiomatic way to combine jq and awk, and say why you'd split the work.

Use jq to safely pull fields out of the JSON structure into flat columns (e.g. jq -r '[.route,.ms] | @tsv'), then pipe those columns into awk to do the arithmetic (sum, average, per-group stats). You split the work because jq is the only one that parses JSON correctly, while awk is better at fast column math and associative-array grouping — structure-aware extraction first, computation second.
