Module 3 · Lesson 3.3

The shell as a programming model: streams, pipes, redirection, exit codes & globbing

You can now name any object on the machine as a path (3.1) and reason about who may touch it (3.2). This lesson gives you the third pillar of operating a server: the ability to make the machine do work. The shell is not a place you type commands — it is a small, strange, and remarkably powerful programming language whose data type is the stream of bytes, whose function composition operator is the pipe, and whose control flow runs on exit codes. Master its five core ideas — streams, redirection, pipes, exit codes and globbing — and you stop copying commands from the internet and start composing tools you've never seen into answers to questions nobody wrote a program for. This is the model behind every deploy script, every CI step, and every 3 a.m. debugging session for the rest of the course.

~70 min read Prerequisites: Lessons 3.1, 3.2 Conceptual · hands-on at the end Module 3 · Milestone 3
Learning objectives

By the end of this lesson you will be able to:

  1. Explain that the shell is an interpreter for a programming language — a read-eval-print loop that parses a line, expands it, and executes programs — not merely a command prompt.
  2. Name the three standard streams — stdin (fd 0), stdout (fd 1), stderr (fd 2) — and connect them to the file descriptors from Lesson 3.1's "everything is a file."
  3. Redirect any stream to or from a file with >, >>, <, 2>, 2>&1 and &>, and discard output to /dev/null.
  4. Explain a pipe as an in-kernel buffer joining one program's stdout to the next's stdin, and build multi-stage pipelines that answer real questions.
  5. Read and use exit codes ($?, 0=success), chain commands with && and ||, and understand why set -euo pipefail is the first line of every serious script.
  6. Predict exactly what globbing (*, ?, […]) and brace expansion ({a,b}) expand to — and why the shell, not the command, does the expanding.
  7. Quote correctly (single vs double vs none), so spaces, globs and variables behave — the single most common source of broken scripts.
  8. Read a real deploy/CI one-liner and narrate every symbol in it, then write your own DevBoard log-triage pipelines.
Where this sits on the map

Lesson 3.1 gave you the nouns (paths, files, file descriptors); Lesson 3.2 gave you the access rules (every command runs as your user, subject to the permission bits). This lesson gives you the verbs and the grammar — how to combine programs into new behaviour. It is the direct foundation of Lesson 3.4 (the ops debugger's toolkit: grep, sed, awk, jq, find, xargs — every one of which is a stream filter designed to live in a pipe), Lesson 3.6 (systemd units are commands with their streams wired to the journal and judged by their exit code), and every RUN line of a Dockerfile and every step of a GitHub Actions job in later modules — all of them shell. Get streams, pipes and exit codes into your hands now and the rest of DevOps reads like a language you already speak.

1 · Problem Statement

You are logged into DevBoard's server (as your own unprivileged user, per Lesson 3.2), and something is wrong. The API feels slow. You have no dashboard yet — that's Module 12 — so the only instruments you have are the raw materials of the machine: a log file that is now 400 MB, a directory of rotated logs, a list of running processes, and a prompt. The questions in your head are concrete and urgent, and none of them is answered by a single ready-made command:

  • "How many 500 errors did the API return in the last hour, and which three URLs caused the most of them?"
  • "Something is filling the disk. Which directories, ranked by size, and is it the logs or an upload gone wrong?"
  • "I need to restart the app only if the config file actually parses — never restart into a broken config. How do I make the second action depend on the first succeeding?"
  • "I want to back up all *.env files under /srv — there are dozens, in folders I'd have to type out by hand. Can I name them all at once?"
  • "My deploy script ran ten steps and 'finished,' but did step 6 actually work, or did it fail silently and the script barrelled on to production anyway?"

Notice the shape of every one of these. Each is a small program — take some data, filter it, transform it, count it, decide something, act on the result. But writing an actual program (a C or Python file) for each throwaway question is absurd: you'd spend more time on boilerplate than on the answer, and you'd need to write a new one every time the question changed slightly. What you need is a way to assemble a bespoke program in one line, out of tools that already exist, in the time it takes to think of the question — and to do it so routinely that composition becomes reflex.

The core problem

Operating a server is a relentless stream of one-off data-processing and decision tasks — filter these lines, count those, rank the results, and take an action only if the previous one succeeded — that no single pre-written command answers. Writing a standalone program for each is far too slow, and clicking through a GUI (even if one existed on a headless server) can neither be repeated exactly nor automated. We need a programming model in which tiny, single-purpose tools can be composed on the fly — their outputs fed into each other's inputs, their success or failure driving what happens next — fast enough to keep pace with the questions, and reproducible enough to paste into a deploy script tomorrow. That model is the Unix shell.

The promise of this lesson: by the end you will look at a line like grep ' 500 ' access.log | awk '{print $7}' | sort | uniq -c | sort -rn | head -3 and read it the way you read a sentence — not as an incantation, but as a data pipeline whose every stage you understand and could have written yourself.

2 · Historical Context

The shell's power is not an accident of syntax; it is the direct expression of a design philosophy that predates it. Each step below added one idea to the model you'll use today.

1964–1969 · Multics and the idea of a "shell"

The term shell — a program that wraps the kernel and lets a human drive it — comes from Multics, the ambitious time-sharing system that Unix's authors worked on and reacted against. Multics established that the command interpreter should be an ordinary, replaceable user program, not a privileged part of the OS. That single decision — the shell is just another process, with no special powers beyond your own (exactly the point of Lesson 3.2) — is why you can swap bash for zsh or fish without touching the kernel.

1971 · The Thompson shell — small, and a real program

Ken Thompson wrote the first Unix shell (sh). It was tiny, but it already carried the revolutionary ideas: a command was just a program to run, and its input and output could be redirected to files with < and >. Redirection existed before pipes — the shell could already treat a program's output as detachable from the terminal.

1973 · The pipe — the idea that changed everything

Doug McIlroy had been agitating for years for a way to connect programs "like a garden hose." In 1973 Ken Thompson added the pipe (|) to the shell and the kernel in a single evening. Overnight, the crucial move became possible: the output of one program could become the input of the next, with no temporary file and no coordination between the two programs. McIlroy's insistence crystallised into the Unix philosophy, which he later stated as: "Write programs that do one thing and do it well. Write programs to work together. Write programs to handle text streams, because that is a universal interface." The pipe is the mechanism that makes that philosophy pay off.

1977–1979 · The Bourne shell — a real programming language

Stephen Bourne (Bell Labs) rewrote the shell as sh — the Bourne shell — turning it from a command launcher into a genuine programming language: variables, control flow (if, for, while, case), functions, and the use of a command's exit status as a boolean for that control flow. The #!/bin/sh script was born. This is the direct ancestor of the syntax in every deploy script you'll ever write.

1978 · The C shell, and the fork in the road

Bill Joy at Berkeley wrote csh, adding interactive conveniences (command history, job control) with a C-like syntax. It seeded a lasting split between "good for scripting" (Bourne family) and "nice interactively" (C family) — a distinction that still bites people who write csh-isms into sh scripts.

1989 · Bash — "Bourne Again," and the modern default

Brian Fox wrote bash (the Bourne-Again SHell) for the GNU project: Bourne-compatible for scripting, but with the interactive niceties of csh and more. It became the default login shell of Linux and thus the lingua franca of servers, containers and CI systems. When this course says "the shell," it means a POSIX sh-compatible shell, with bash as the concrete default — the one inside your Ubuntu VPS and inside almost every Docker image.

The through-line

Every historical step added one piece of the same model: the shell is a replaceable user program (Multics) that runs other programs (Thompson), can redirect their streams (1971) and connect them with pipes (1973), treats their exit status as truth for control flow (Bourne), and is itself a full programming language (Bourne → bash). Streams, pipes, exit codes, composition — the four ideas were assembled fifty years ago and have never needed replacing.

3 · The Previous Solution (in detail)

What did people do before the compose-small-tools model, and what do engineers still default to when they haven't internalised it? Two patterns, both instructive because both feel reasonable.

3.1 The monolithic program with a hundred flags

The pre-Unix instinct — and the instinct of many modern tools — is: if a program needs to do more, add more options to it. Want your file-lister to also sort by size, filter by date, count matches, and email you the result? Add --sort, --filter, --count, --email flags. Each program grows into a self-contained universe that tries to anticipate every use. 

THE MONOLITH MODEL  ("one big program that does everything")

  supertool --input access.log --filter status=500 --since 1h \
            --group-by url --sort count --desc --top 3 --format table

  Every capability is a FLAG that the tool's author had to foresee,
  implement, document, and version. Want something they didn't foresee?
  You wait for a new release — or you're stuck.

3.2 Writing a bespoke program per task

The other pre-shell answer: for anything the standard tools couldn't do, write a small program in C (later Perl, Python). Correct, general — and far too slow for the throwaway questions of §1. A five-line C program to count status codes needs a source file, a compile step, and a name; multiply that by the fifty small questions you ask in a debugging session and you get nothing done.

The assumptions both patterns bake in:

Functionality lives inside tools, not between them
A new capability means changing a program's source or its flag set — never a new arrangement of existing programs.
Programs are endpoints, not building blocks
Each tool owns its input source and output destination (a file, the terminal, an email). Two tools have no standard way to hand data to each other.
Composition, if it happens, goes through temporary files
To feed tool A's output into tool B you run A into a temp file, then run B on it, then clean up — manual, error-prone, and impossible to do at conversational speed.
The set of possible questions is fixed at authoring time
You can only ask what some tool author already built a flag for. Novel questions require new code.

Both models work — plenty of excellent software is monolithic, and sometimes a real program is the right answer. Their appeal is real: a single tool is discoverable (one --help) and self-contained. But as a way to operate a machine, both share a fatal ceiling: the number of things you can do is bounded by what someone anticipated and shipped. The next section is where that ceiling hits.

4 · Why It Failed (as an operating model)

"Failed" is scoped precisely: monolithic tools and bespoke programs are not wrong — they are the right shape for a product. They fail as the model for operating a system, where the questions are infinite, unpredictable, and urgent. Each assumption becomes a concrete wall.

4.1 The combinatorial explosion of features

If capability must live inside tools, then the number of features a tool needs is the number of combinations of things users might want — which explodes. A file lister that also sorts, filters, counts, formats and mails is five features; wanting any pair of them combined in a new way needs a sixth flag its author didn't foresee. No author can foresee them all, so every monolith is permanently missing the exact combination you need right now.

4.2 Every tool re-implements the same plumbing

When each program owns its input and output, every program must re-implement reading files, writing files, parsing arguments, sorting, and paging — badly, differently, and incompatibly. Fifty tools contain fifty slightly different sort routines. The effort is duplicated everywhere and shared nowhere.

4.3 You cannot answer a question nobody anticipated

This is the real failure. "How many 500s per URL in the last hour, top three" is a perfectly ordinary operational question — and there is no supertool with exactly that flag, nor should there be. In a model where functionality lives inside tools, an unanticipated question is simply unanswerable without writing new software. On a server on fire, that is unacceptable.

4.4 Temp-file composition is too slow and too fragile to automate

Stitching tools together through temporary files — A > tmp1; B tmp1 > tmp2; C tmp2 — is slow to type, leaves litter, races with itself if two runs collide, and gives you no clean way to know whether stage B actually succeeded before stage C ran. It is composition in theory but not at the speed or reliability real operations demand.

The pattern behind all four failures

Every failure traces to one root cause: functionality was trapped inside programs instead of living in the connections between them. The fix is a single inversion — make the connection a first-class, universal thing. Give every program the same three connections (an input stream, an output stream, an error stream), make the output of one the input of the next a trivial one-character operation (the pipe), and expose each program's success or failure as a value the shell can branch on (the exit code). Then a new capability is no longer a new flag or a new program — it is a new arrangement, composed in one line. That inversion is §5.

5 · The New Solution

The solution is the shell's programming model: treat every program as a function whose type is "bytes in → bytes out," give them all a universal interface (three standard streams), make composition a single character (the pipe), and make control flow run on a program's exit code. Add globbing so the shell itself expands patterns into arguments, and you have a complete, tiny language for making the machine work. Vocabulary first.

5.1 The core vocabulary

Shell
An ordinary user program that reads a line you type, parses and expands it, launches the program(s) it names (with the streams wired up), waits, and shows you the result — then loops. A read-eval-print loop (REPL) whose "eval" is "run programs."
Stream
A one-directional flow of bytes. The shell's universal data type. A stream can come from the keyboard, a file, a pipe, or another program — the program reading it usually can't tell which, and doesn't care. (This is Lesson 3.1's "everything is a file" cashing out.)
Standard streams (stdin/stdout/stderr)
The three streams every process is born with: standard input (fd 0, where it reads), standard output (fd 1, where it writes results), and standard error (fd 2, where it writes diagnostics). Keeping errors on a separate stream from results is what makes pipes clean.
Redirection
Telling the shell to connect a stream to a file instead of the terminal: > (stdout to a file, overwrite), >> (append), < (a file into stdin), 2> (stderr to a file).
Pipe (|)
An in-kernel buffer that connects the stdout of the program on its left to the stdin of the program on its right, so they run concurrently and data flows between them with no temp file.
Exit code / status
The small integer (0–255) every program returns when it ends. 0 means success; any non-zero means some kind of failure. The shell stores the last one in $? and uses it as the boolean for &&, ||, if and while.
Glob / wildcard
A pattern (*, ?, […]) that the shell expands into a list of matching filenames before the command runs. The command never sees the * — it sees the filenames.
Expansion
The set of transformations the shell applies to your line before executing it — variable expansion ($VAR), command substitution ($(...)), brace expansion ({a,b}), globbing, and word splitting. Understanding expansion order is understanding the shell.
The one sentence to hold onto

The shell runs each program as a function over byte streams — stdin in, stdout/stderr out — lets you rewire those streams to files (redirection) or to each other (the pipe), branches on each program's exit code (0 = success), and expands globs and variables in your line before anything runs. Every deploy script, every Dockerfile RUN, every CI step and every debugging one-liner in this course is just that model applied.

5.2 The shape of the solution

Return to §1's hardest question — top three URLs causing 500 errors — and watch the model dissolve it. Each stage is a tiny tool doing one thing; the pipe is the composition; nobody had to anticipate this exact question: 

grep ' 500 ' access.log | awk '{print $7}' | sort | uniq -c | sort -rn | head -3
└──────┬──────┘ └──────┬───────┘ └─┬─┘ └──┬───┘ └───┬───┘ └──┬──┘
 keep only 500  print the 7th     sort  count    sort by    take
 lines          field (the URL)   them  identical count,     the
 (a filter)     (a transform)           adjacents descending top 3
                                        (=per-URL) (rank)

  DATA FLOWS LEFT → RIGHT through the pipes. No temp files. Each program
  reads stdin, writes stdout, and knows nothing about its neighbours.
  A NEW question = a NEW arrangement of the same parts.

Now re-answer the rest of §1 in one line of model each. Restart only if the config parses? nginx -t && systemctl reload nginx — the && runs the reload only if the test's exit code was 0. Back up every *.env under /srv? A glob names them all at once. Which directories are eating the disk? du -h --max-depth=1 /srv | sort -rh | head — measure, rank, top. Did deploy step 6 really succeed? Because every step returns an exit code and set -e halts the script the instant one is non-zero. One model, five answers, no new software written.

6 · Internal Mechanics

Now the machine in detail. We will (6.1) see the shell as an interpreter and trace what it does to one line; (6.2) pin down the three streams as file descriptors; (6.3) master redirection, including the tricky 2>&1; (6.4) open up the pipe as a real kernel object; (6.5) make exit codes and &&/||/set -e precise; (6.6) nail globbing and expansion order; (6.7) get quoting right once and for all; and (6.8) assemble it into DevBoard operations.

6.1 The shell is an interpreter: what one line actually triggers

When you press Enter, the shell does not hand your text to some command. It runs a small parse- and-expand pipeline of its own, then launches processes. Understanding this sequence is what separates "the command did something weird" from "I know exactly why." Roughly, for a simple command the shell:

  1. Splits the line into words on whitespace (this is why spaces matter so much).
  2. Applies expansions in a defined order (§6.6): brace {} → tilde ~ → variables $VAR and command substitution $(...) → word splitting → globbing *.
  3. Sets up redirections — opens any files named by >, <, etc., and points the right file descriptors at them.
  4. Finds the program — a shell builtin (like cd), or an executable found by searching each directory in $PATH.
  5. fork()s a child, wires up its streams, and exec()s the program; the shell wait()s and collects the child's exit code.

The crucial consequence: the command never sees your original text. By the time ls *.log runs, ls receives app.log web.log db.log — the shell already replaced the *.log. This one fact explains a huge fraction of "why did that happen?" surprises, and we'll lean on it repeatedly.

6.2 The three streams are just file descriptors

Lesson 3.1 taught that an open file is referred to by a small integer — a file descriptor — in a per-process table, and that "everything is a file." The three standard streams are simply the three descriptors every process is handed at birth:

StreamfdDefault targetPurpose
stdin — standard input0your keyboardwhere the program reads its input from
stdout — standard output1your terminalwhere the program writes its results — the data other tools want
stderr — standard error2your terminalwhere the program writes diagnostics: errors, warnings, progress

Why two output streams? Because results and complaints must be separable. When you run grep 500 *.log | wc -l, you want only the matching lines (stdout) to flow into wc; a message like "grep: web.log: Permission denied" is not data and must not pollute the count — so it goes to stderr, which is not piped, and lands on your terminal instead. Keeping fd 1 clean (data only) and fd 2 for humans is the discipline that makes pipes composable. A subtle corollary that trips people: on a terminal both look identical, so you can't tell which stream a line came from by looking — until you pipe or redirect and the error "escapes" the pipe.

The mental model

Picture every program as a box with one input pipe (fd 0) and two output pipes (fd 1 for data, fd 2 for complaints). By default all three are plugged into your terminal. Redirection and pipes are nothing more than unplugging one of these and plugging it into a file or into another box's input. The program is oblivious — it just reads fd 0 and writes fd 1/2, exactly as always. That obliviousness is the whole trick: it's what lets tools that know nothing about each other snap together.

6.3 Redirection: rewiring a stream to a file

Redirection connects a standard stream to a file instead of the terminal. The operators are few and worth memorising exactly, because a wrong one silently loses data. 

command >  file      # stdout → file, TRUNCATE (overwrite). The famous data-loser.
command >> file      # stdout → file, APPEND (add to the end)
command <  file      # file → stdin (feed the program from a file)
command 2> file      # stderr (fd 2) → file  — capture only the errors
command 2> /dev/null # discard errors entirely (/dev/null = the black hole, from 3.1)
command > out 2> err # results to out, errors to err — two separate files
command > file 2>&1  # stdout → file, THEN stderr → "wherever fd 1 now points" (=file)
command &> file      # bash shorthand for the line above: BOTH streams → file

The one that confuses everyone is 2>&1, and it rewards one careful reading. 2>&1 means "make fd 2 point at whatever fd 1 currently points at" — it copies the destination, not the stream. Order therefore matters: 

command > file 2>&1     # ✅ 1 is set to file FIRST, then 2 is aimed at the same file → both in file
command 2>&1 > file     # ⚠️ 2 is aimed at the TERMINAL (where 1 still points), THEN 1 moves to file
                        #    → errors go to the screen, results go to the file. Rarely what you meant.

Read redirections strictly left to right, each one acting on the file descriptors as they are at that moment. Two more constructs you'll meet constantly: the here-document feeds a literal block into stdin, and the here-string feeds a single string: 

cat <<'EOF' > /etc/devboard/notes.txt     # everything up to EOF becomes stdin for cat
This is a here-doc.
Handy for writing config files from a script.
EOF

grep devboard <<< "$SOME_VARIABLE"        # here-string: feed one string as stdin
The classic footgun

sort file > file destroys file. The shell sets up the redirection before sort runs, so > file truncates it to empty first, and then sort reads an empty file. Never redirect a command's output onto its own input file. Use a temp file, or a tool with an explicit in-place flag (sort -o file file, sed -i). This bug has eaten many people's data — including config files on production boxes.

6.4 The pipe: an in-kernel buffer between two live programs

A pipe is not a file and not a variable — it is a small buffer inside the kernel (classically 64 KB) with a read end and a write end. A | B tells the shell to: create a pipe, start both A and B at the same time, wire A's stdout (fd 1) to the pipe's write end, and wire B's stdin (fd 0) to the pipe's read end. A writes; B reads; the kernel moves the bytes. 

   producer                    kernel pipe buffer                 consumer
  ┌──────────┐   fd1  write ──▶ ┌───────────────────┐ ──▶ read  fd0 ┌──────────┐
  │  grep    │═════════════════▶│  ~64 KB of bytes  │═════════════▶│   wc     │
  └──────────┘                  └───────────────────┘              └──────────┘
      │                                                                  │
      └─ if the buffer FILLS, grep BLOCKS until wc reads (back-pressure) ┘
      └─ if wc reads faster than grep writes, wc BLOCKS waiting for data ─┘

Three consequences fall straight out of this being a bounded buffer between concurrent processes:

  • The stages run simultaneously, not one-then-the-next. grep and wc are both alive; data streams through. This is why tail -f app.log | grep ERROR shows new errors live — the pipeline never "finishes" the first stage before starting the second.
  • Memory stays tiny even for huge inputs. A 400 MB log piped through a chain never lives in RAM all at once; only ~64 KB is ever "in flight." You can process files far larger than memory.
  • Back-pressure is automatic. If a downstream stage is slow, the buffer fills and the kernel blocks the upstream writer until there's room. Nobody floods anybody; the fast producer politely waits.

Two important details. First, only stdout flows through the pipe — stderr does not, which is exactly why errors still reach your screen mid-pipeline (§6.2). To pipe errors too, merge them first: command 2>&1 | less. Second, a pipe connects adjacent stages only; there's no "skip a stage." Data is a relay, hand to hand.

6.5 Exit codes: the shell's booleans, and safe scripts

Every program, when it ends, returns an integer 0–255 to its parent. The convention is rigid and universal: 0 = success; any non-zero = a failure (and different non-zero values can distinguish kinds of failure — e.g. grep returns 1 for "no matches found," 2 for "real error"). The shell captures the most recent exit code in the special variable $? and — crucially — uses it as the truth value for all control flow. 

ls /etc/devboard ; echo $?      # run it, then print the exit code (0 if the dir exists)
grep -q ERROR app.log           # -q = quiet: no output, just an exit code (0 = found)
echo $?                          # 0 if "ERROR" was present, 1 if not

# && = "and then, only if the left SUCCEEDED (exit 0)"
# || = "or else, only if the left FAILED (non-zero)"
mkdir -p /srv/devboard/releases && cd /srv/devboard/releases   # cd only if mkdir worked
systemctl is-active --quiet devboard || systemctl start devboard  # start only if NOT running
nginx -t && systemctl reload nginx || echo "config broken, NOT reloaded"

Because if and while also test exit codes, control flow reads naturally: if grep -q ERROR app.log; then … means "if grep succeeded (found a match)." There is no separate boolean type — success is the boolean. This is the Bourne-shell insight from §2.

The three lines that make a script safe

By default a shell script ignores failures and marches on: if step 6 fails, step 7 runs anyway, and you deploy a half-built release. The fix is the first line of every serious script: set -euo pipefail.

set -e — exit the whole script the moment any command returns non-zero, so a failure stops the deploy instead of continuing past it. set -u — treat use of an unset variable as an error, so a typo'd $RELEAES_DIR can't silently expand to empty and rm -rf $EMPTY/ your disk. set -o pipefail — make a pipeline fail if any stage fails, not just the last one; without it, false | true "succeeds" because only true's exit code counts. Memorise this line; it is the difference between a deploy script that fails loudly and early and one that fails silently in production.

6.6 Globbing and expansion — and the order that governs everything

A glob is a filename pattern the shell expands into a list of matching paths before the command runs. The command never sees the pattern. The wildcards:

PatternMatchesExample → expands to
*any run of characters (incl. none), except a leading dot*.log → app.log web.log
?exactly one characterapp.? → app.c app.h
[…]one character from the set/rangelog[0-9] → log1 log8
[!…]one character not in the set[!.]* → files not starting with dot

Two facts about globbing catch nearly everyone. First: globbing is done by the shell, not the program. When you run rm *.log, the shell expands *.log to the actual filenames and hands those to rm; rm has no idea a glob was involved. That is why quoting a glob (rm "*.log") disables it — the shell leaves the literal string alone and rm looks for a file literally named *.log. Second: if a glob matches nothing, a POSIX shell passes the literal pattern through unchanged (bash default) — so ls *.tar in a directory with no tarballs runs ls '*.tar' and errors with "No such file." (This surprising default can be changed with bash's nullglob, but knowing the default explains the error.)

Distinct from globbing is brace expansion, which is pure text generation and does not look at the filesystem at all: 

echo file{1,2,3}.txt        → file1.txt file2.txt file3.txt   (whether or not they exist)
mkdir -p /srv/devboard/{releases,shared,current}   # make three dirs in one go
cp app.conf{,.bak}          → cp app.conf app.conf.bak   (a common "backup this file" idiom)
echo {1..5}                 → 1 2 3 4 5   (ranges)

And this is where expansion order earns its keep, because the shell applies these transformations in a fixed sequence, and the order explains otherwise baffling behaviour: 

EXPANSION ORDER (bash), left conceptually as a pipeline the shell runs on your line:

  1. Brace expansion        {a,b}       →  a b            (pure text, no filesystem)
  2. Tilde expansion        ~           →  /home/you
  3. Parameter/variable     $VAR ${VAR} →  its value
     & command substitution $(cmd) `cmd`→  the cmd's stdout
  4. Arithmetic             $((1+2))    →  3
  5. Word splitting         splits UNQUOTED results on whitespace (IFS)
  6. Pathname expansion     *  ?  [ ]   →  matching filenames (GLOBBING happens LAST)

  Key takeaways:
    • Globbing happens AFTER variable expansion → a glob stored in $VAR still expands.
    • Word splitting happens on UNQUOTED expansions → this is why "$var" needs quotes.
    • Brace expansion happens FIRST and never touches the disk → {a,b} always expands.

6.7 Quoting: the rule that ends half your bugs

Because the shell splits on whitespace and expands globs and variables (§6.6), quoting is how you control what stays literal. There are exactly three modes, and knowing them cold prevents an enormous class of failures:

FormWord splitting?$VAR expands?Globs expand?Use it for
no quotes — $xyesyesyeswhen you want a glob or splitting to happen
double — "$x"noyesnothe default you should reach for: value in, spaces safe
single — '$x'nononoa totally literal string (e.g. an awk program)
 
file="my report.txt"
rm  $file      # ⚠️ becomes: rm my report.txt  → tries to delete TWO files, "my" and "report.txt"
rm "$file"     # ✅ becomes: rm "my report.txt" → deletes the ONE file you meant

echo '$HOME costs $5'   # single quotes: literal  → $HOME costs $5
echo "$HOME costs \$5"  # double quotes: expands   → /home/you costs $5
The habit to build

Quote every variable expansion in double quotes by default — "$var", "$(cmd)", "${arr[@]}" — and only drop the quotes when you specifically want word-splitting or globbing. Almost every "it worked until a filename had a space / until the variable was empty" bug is a missing pair of double quotes. This one habit will save you more grief than any other single thing in this lesson.

6.8 Putting it together: the model as DevBoard operations

Everything above composes into the real work of operating DevBoard. A few representative one-liners, each annotated — read them as sentences now: 

# Top 3 URLs returning 500, last hour's log (the §1 question, solved)
grep ' 500 ' access.log | awk '{print $7}' | sort | uniq -c | sort -rn | head -3

# What's eating the disk under /srv, biggest first
du -h --max-depth=1 /srv 2>/dev/null | sort -rh | head

# Reload nginx ONLY if its config parses; report clearly either way
nginx -t && systemctl reload nginx && echo "reloaded" || echo "BAD CONFIG — left running"

# Follow the live log, keep only errors, and save a copy while watching
tail -f app.log | grep --line-buffered ERROR | tee errors.log

# Count how many times each log level appears right now
awk '{print $3}' app.log | sort | uniq -c | sort -rn

# Back up every .env under /srv (glob names them; brace makes the .bak suffix)
for f in /srv/**/*.env; do cp "$f" "$f.bak"; done   # (bash globstar) — quote $f for spaces!

This is the payoff of the whole lesson: you did not learn six commands, you learned a model in which those commands — and hundreds you haven't met — snap together. Lesson 3.4 hands you sharper filters for the middle of these pipes (grep, sed, awk, jq); they slot into exactly the model you now hold.

7 · Real Industry Example

This model is not a beginner's toy that "real" systems outgrow — it is the substrate that professional infrastructure is built on. Three concrete places you'll see it:

CI/CD pipelines are shell

Every step in a GitHub Actions job (Module 9) is a run: block executed by bash. The job succeeds or fails on the exit code of each step — this is §6.5 exactly. A test command that exits non-zero fails the build and blocks the merge. Your entire "is this change safe?" gate is exit codes and pipes.

Dockerfiles are shell

Every RUN apt-get update && apt-get install -y … in a Dockerfile (Module 7) is this model. The && chaining is deliberate: if update fails, the install must not run against a stale index. Image builds live or die by exit-code chaining you now understand.

systemd runs commands & reads exit codes

A systemd service (Lesson 3.6) is fundamentally a command whose stdout/stderr are wired to the journal and whose exit code decides restart policy. "Restart the app if it crashes" is systemd watching for a non-zero exit — the same integer $? gives you.

The one-liner that saves the outage

When something breaks at 3 a.m. and there's no dashboard for this question, the engineer who can compose journalctl -u devboard --since '10 min ago' | grep -i timeout | wc -l in ten seconds finds the answer while everyone else is googling. Fluency here is measurably faster incident response.

Google's, Netflix's and every serious shop's deploy tooling bottoms out in shell somewhere, precisely because the compose-small-tools model is the fastest way to express "do this, check it worked, then do the next thing" — which is what deployment is.

9 · Advantages

  • Infinite composability from a finite toolset. A few dozen small tools plus the pipe yield billions of pipelines. You answer questions no tool author anticipated, by arrangement rather than new code.
  • A universal interface. Because every tool speaks the same "text stream in/out," any tool composes with any other. There is no per-pair integration work — the pipe is the integration.
  • Constant memory over unbounded data. Streaming through pipes means a 400 MB log — or an infinite tail -f — flows through in ~64 KB chunks. You process data far larger than RAM without thinking about it.
  • Reproducible and automatable. A pipeline that answered a question interactively is the same text you paste into a deploy script or CI step. Exploration and automation are one artifact — unlike clicking a GUI, which vanishes.
  • Fail-fast control flow for free. Exit codes plus &&/set -e give you "do this only if that worked" as a one-character operator — the exact primitive safe deployment needs.
  • Ubiquitous and stable. The same model works on your laptop, the VPS, inside every container, and in every CI runner — and has been stable for decades. Learning it once pays off everywhere in this course and after it.

10 · Limitations

  • The syntax is genuinely treacherous. Word splitting, glob surprises, and quoting rules mean a script that works on your files breaks on a filename with a space or a newline. The model is elegant; the surface is full of sharp edges (which is why §6.7 and set -euo pipefail matter so much).
  • Text streams are a lossy interface for structured data. Parsing columns with awk '{print $7}' is fragile: change the log format and every pipeline breaks. Truly structured data (JSON) needs structure-aware tools (jq, Lesson 3.4) rather than whitespace splitting.
  • Poor for real programming-in-the-large. Beyond ~50 lines, shell's lack of real data structures, error handling, and testing makes it a bad choice. When a script grows arms and legs, rewrite it in Python. Shell is glue, not girders.
  • Portability gaps. bash-isms ([[ ]], arrays, &>) don't work in the leaner sh/dash that many containers ship as /bin/sh. A script with #!/bin/sh that uses bash features fails mysteriously.
  • Silent failure is the default. Without set -e/pipefail, errors are ignored and scripts continue — arguably the language's worst default, and a real cause of bad deploys. You must opt into safety.
  • Security footguns. Unquoted expansions and naive use of eval or command substitution on untrusted input are classic injection vectors. The same flexibility that composes tools can compose an attacker's input into a command.

11 · Common Misconceptions

"The program interprets the * — I'm passing a wildcard to ls."

The shell expands * into the list of matching filenames before ls ever runs; ls receives ordinary filenames and never sees the *. Proof: ls "*.log" (quoted) disables the glob, and ls then complains it can't find a file literally named *.log. Globbing is a shell service, uniform across every command — which is why it works identically with rm, cp, and tools that have never heard of wildcards.

"A pipe runs the first command fully, saves the output, then runs the second."

Both commands run concurrently, with a small kernel buffer between them; data streams through as it's produced. That's why tail -f log | grep ERROR shows matches live forever and why huge inputs use tiny memory. There is no intermediate file and no "finish then start."

"> and | do basically the same thing."

> sends a stream to a file (redirection); | sends stdout to another program's stdin (a pipe). grep 500 log > out writes a file; grep 500 log | wc feeds a program. You can't | file.txt and you (usually) don't want > anotherprogram.

"Exit code 1 means the number one / an error count."

The exit code is a status, not a quantity. 0 = success; any non-zero = a category of failure (e.g. grep uses 1 for "no match," 2 for "actual error"). It never means "one error occurred." And higher isn't "worse" — the numbers are labels, not a severity scale.

"Piping to less or grep also filters the error messages."

Only stdout flows through a pipe; stderr bypasses it and hits your terminal directly. That's by design — errors are not data. To include them, merge first: command 2>&1 | less. Forgetting this is why "why is this error still on my screen when I piped everything to a file?" is such a common question.

"Quotes are optional style — $var and "$var" are the same."

They differ whenever the value contains spaces, globs, or is empty. Unquoted $var is word-split and glob-expanded after substitution; "$var" is inserted as a single literal word. rm $file where file="a b" deletes two files; rm "$file" deletes one. Quote by default.

13 · Summary

  • The shell is a programming language and interpreter, not a command prompt: it parses your line, expands it, wires up streams, runs programs, and branches on their exit codes.
  • Every process has three standard streams — stdin (fd 0), stdout (fd 1, data), stderr (fd 2, diagnostics) — the file descriptors from Lesson 3.1. Keeping data and errors on separate streams is what makes pipes clean.
  • Redirection (>, >>, <, 2>, 2>&1, &>) rewires a stream to a file; > truncates, >> appends, and 2>&1 copies fd 1's current destination — so order matters.
  • A pipe is an in-kernel buffer joining one program's stdout to the next's stdin; the stages run concurrently, memory stays tiny, and back-pressure is automatic. Only stdout flows through — stderr escapes to the terminal.
  • Exit codes (0=success, non-zero=failure, in $?) are the shell's booleans: && runs the next command only on success, || only on failure. set -euo pipefail turns silent failure into fail-fast — the first line of every serious script.
  • Globbing (*, ?, […]) is done by the shell, before the command runs and last in the expansion order; brace expansion ({a,b}) is pure text done first and never touches the disk.
  • Quote every variable in double quotes by default ("$var") — this single habit prevents the largest class of shell bugs (spaces, empty values, accidental globbing).
  • This model is the substrate of CI steps, Dockerfile RUN lines, and systemd services — learning it now is learning the grammar of the rest of the course.
The lesson in one line

Compose small single-purpose programs by wiring their byte streams together with pipes and redirection, branch on their exit codes, and let the shell expand your globs and variables — and you can make the machine do anything, one line at a time.

E4Exit codes and safe chaining

E5Globbing, brace expansion, and quoting — prove who does the work

16 · Quiz

How to use this

Answer in your own words before revealing the model answer. Two or three sentences each. You're ready for Lesson 3.4 (the grep/sed/awk/jq toolkit) when you can answer Q1, Q3, Q5 and Q7 cold and have completed E1–E6 on a real machine.

Name the three standard streams, their file descriptor numbers, and why stdout and stderr are kept separate.

stdin (fd 0, input), stdout (fd 1, results/data), stderr (fd 2, diagnostics/errors). They're separate so that a program's results can flow cleanly through a pipe to the next tool while its error messages go to the human on the terminal instead of polluting the data. If both shared one stream, an error like "Permission denied" would be counted as a data line by the next stage.

What is the difference between command > file and command | other?

> is redirection: it connects the command's stdout to a file (overwriting it). | is a pipe: it connects the command's stdout to another program's stdin, and the two run concurrently with an in-kernel buffer between them. One writes to storage; the other feeds a live program. You redirect to save/persist; you pipe to keep processing.

Explain 2>&1, and why cmd > f 2>&1 and cmd 2>&1 > f differ.

2>&1 means "point fd 2 (stderr) at whatever fd 1 currently points at." Redirections are applied left to right. In cmd > f 2>&1, fd 1 is aimed at f first, then fd 2 is aimed at the same place → both land in f. In cmd 2>&1 > f, fd 2 is aimed at the terminal (where fd 1 still points) first, then fd 1 moves to f → errors go to the screen, results to the file.

Why does tail -f app.log | grep ERROR keep printing new errors forever, and use very little memory?

Because a pipe runs both programs concurrently with a small (~64 KB) kernel buffer between them, streaming data as it's produced rather than "finish tail, then run grep." tail -f never exits — it emits each new line as the file grows — and grep filters each line as it arrives. Only a tiny buffer's worth of data is ever in memory, so it works on unbounded/huge inputs without loading them.

What does an exit code of 0 mean vs non-zero, and how do && and || use it?

0 = success; any non-zero = a category of failure (stored in $?). A && B runs B only if A exited 0 ("and then, if it worked"); A || B runs B only if A exited non-zero ("or else, as a fallback"). This is how the shell does control flow — success itself is the boolean, so nginx -t && systemctl reload nginx reloads only when the config test passes.

What does set -euo pipefail do, and why is it the first line of a deploy script?

-e aborts the script on the first command that fails (non-zero), so a broken step stops the deploy instead of continuing. -u makes referencing an unset variable an error, catching typos before they expand to empty (which prevents disasters like rm -rf $TYPO/). -o pipefail makes a pipeline fail if any stage fails, not just the last. Together they convert the shell's dangerous default — ignore errors and keep going — into fail-fast behaviour, so problems surface loudly and early rather than silently in production.

When you run rm *.log, who expands the *.log, and what does rm actually receive?

The shell expands *.log into the list of matching filenames before rm runs; rm receives ordinary filenames (e.g. app.log web.log) and never sees the *. Globbing is a uniform shell service, which is why it works identically with every command and why quoting (rm "*.log") disables it — the shell then passes the literal string and rm looks for a file actually named *.log.

Distinguish globbing from brace expansion. Which one touches the filesystem?

Globbing (*, ?, […]) matches existing filenames — it reads the filesystem, happens last in expansion order, and yields nothing new if no file matches (in bash's default it passes the literal pattern through). Brace expansion ({a,b}, {1..5}) is pure text generation — it happens first, ignores the filesystem entirely, and always expands (e.g. mkdir {a,b,c} makes three dirs regardless of what exists).

Why can rm $file and rm "$file" behave differently, and which should you default to?

After the shell substitutes the variable, an unquoted $file is subject to word splitting and globbing: if file="my notes.txt", rm $file becomes rm my notes.txt — two arguments, wrong files. "$file" inserts the value as a single literal word, so rm "$file" deletes the one intended file. Default to double-quoting every expansion ("$var", "$(cmd)"); it prevents the biggest class of shell bugs (spaces, empties, accidental globs).

You pipe a command's output to less but an error message still flashes on your screen. Why, and how do you capture it too?

A pipe only carries stdout (fd 1); stderr (fd 2) is not connected to the pipe and goes straight to the terminal — by design, since errors aren't data. To route errors into the pipe as well, merge them into stdout first: command 2>&1 | less. (Or to discard them: command 2>/dev/null | less.)
