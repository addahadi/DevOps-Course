Module 3 · Lesson 3.5

Packages, repositories & trust: apt, signing keys & the software supply chain

Every tool you learned in Lessons 3.3 and 3.4 — grep, jq, awk — arrived on your server as software someone else built, somewhere else, and shipped to you. This lesson opens that box. A package is software bundled with the metadata that says what it is, what it needs, and where its files go. A repository is a trusted catalog of packages. apt is the program that reads that catalog, solves the puzzle of dependencies, and installs the result. And a signing key is the cryptographic proof that the bytes you're about to run as root really came from who they claim to — because installing a package means running someone else's code with full privileges, and the entire question of the software supply chain is: how do you know you can trust it?

~70 min read Prerequisites: Lessons 3.1, 3.2, 3.4 Conceptual · hands-on throughout Module 3 · Milestone 3
Learning objectives

By the end of this lesson you will be able to:

  1. Define a package as software plus metadata (dependencies, version, file list, maintainer scripts), and explain why bundling that metadata is what makes automated installation possible.
  2. Explain what a repository is, how apt knows about one (/etc/apt/sources.list.d/), and the difference between apt update (refresh the catalog) and apt upgrade (install newer versions).
  3. Trace what actually happens on apt install nginx — index read, dependency resolution, download, signature verification, unpack, configure — and name which step each command performs.
  4. Explain dependency resolution and why "just download the .deb and run it" (dependency hell) is the problem package managers were invented to kill.
  5. Describe the trust chain: a repository ships a signed Release file whose hashes vouch for the package index, which in turn vouches for every .deb — and how a signing key anchors the whole chain.
  6. Add a third-party repository safely in the modern way (a keyring file + a signed-by= source), and explain why the old apt-key add pattern is deprecated and dangerous.
  7. Explain the software supply chain as a real attack surface — typosquats, compromised upstreams, malicious post-install scripts, the curl | sudo bash anti-pattern — and state the defensive habits that address each.
  8. Connect all of this to DevBoard: pin the exact package versions your server and your Docker images install, so a build is reproducible and a supply-chain change can't slip in unnoticed.
Where this sits on the map

Lesson 3.2 taught you that installing software needs sudo — root privilege — because it writes to system directories and runs scripts as root. This lesson is the direct sequel: it asks what you're granting that privilege to, and how you know it's safe. Everything downstream depends on it. Every Dockerfile in Module 7 begins with an apt-get install or apk add line — the same model in a container. Every CI job in Module 9 installs its toolchain from a package repository. And the whole of Module 11 (Production Reality: secrets, backups, security) rests on the idea introduced here — that trust is a chain you can inspect, not a feeling. Get packages and signing keys into your hands now, and "supply-chain security," the phrase you'll hear at every turn in real DevOps, stops being jargon and becomes something you can actually reason about.

1 · Problem Statement

You have a fresh Ubuntu server (per Lesson 3.2, logged in as your own unprivileged user) and DevBoard needs a web server in front of it. So you need nginx. That one small, ordinary need — "get me this program" — hides a startling amount of difficulty the moment you try to satisfy it honestly:

  • Where do the bytes come from? There is no nginx on the machine. You need to fetch it — from somewhere on the internet. Which somewhere, and why should you believe it?
  • What else does it need? nginx doesn't stand alone: it links against libraries (libssl, libpcre, zlib…). Those need their dependencies. Install the wrong versions and it won't start — or worse, it starts and something else breaks.
  • Where do its files go? The binary belongs in /usr/sbin, its config in /etc/nginx, its service unit in /lib/systemd, its docs in /usr/share. Who decides that, and how is it undone cleanly when you remove it?
  • How do you update it next month when a security fix lands — without hunting the whole internet again?
  • And the sharpest one: installing it means running its installer as root. That installer can do anything. How do you know the bytes you downloaded are the real nginx and not an impostor that someone swapped in on the wire or on a hacked mirror?
The core problem

Getting software onto a server is not "download a file." It is: find the right software, and everything it depends on, at compatible versions; place dozens of files in exactly the right system locations; make the whole thing updatable and removable later; and — because installation runs code as root — do all of it with a way to prove the bytes are authentic and untampered. Doing this by hand, per program, is slow, error-prone, and fundamentally insecure. We need a system that automates the finding, the dependency-solving, and the placement — and bakes cryptographic trust into every step. That system is the package manager plus its signed repositories.

The promise of this lesson: by the end, sudo apt install nginx will stop being a magic spell and become a sequence you can narrate — catalog lookup, dependency solve, authenticated download, verified unpack — where you know what each step does, what could go wrong, and how the signature at the center of it protects you.

2 · Historical Context

Package management wasn't designed in one stroke; it accreted, each step answering a specific pain the previous one left behind. The trust machinery came last and most painfully — which is exactly why supply-chain security is still where real incidents happen today.

Early 1990s · "just untar it into place"

The first way to ship software for Linux was a .tar.gz archive: a compressed bundle of files you unpacked into your filesystem. Simple, and it worked — until you needed to remove the software (which files were even part of it?), or update it (overwrite blindly and hope), or find out that it silently needed a library you didn't have. The archive carried the files but none of the knowledge about the files. That missing knowledge is the whole story of what came next.

1993–1995 · the birth of the package: .deb and .rpm

Debian introduced the .deb and Red Hat the .rpm: an archive of files plus a metadata record — the package's name, version, the list of every file it installs, the other packages it depends on, and small maintainer scripts to run before and after installation. Now the system could answer "what does this install?", "what does it need?", and "remove it cleanly." The dpkg tool managed a local database of everything installed. This was the leap from "a pile of files" to "a package."

1998–1999 · apt and the repository — solving dependency hell

dpkg could install one .deb, but if that .deb needed three others, you got an error and had to go find them — and their dependencies — by hand. This misery had a name: dependency hell. Debian's apt (Advanced Package Tool, 1998) killed it by adding two ideas: a repository (a whole catalog of packages on a server, with an index listing every package and its dependencies) and a solver that could read that index, compute the complete set of packages needed, and download and install them all in the right order. "Install nginx" became one command instead of an afternoon.

2005 onward · adding trust: signed repositories

Early apt downloaded packages over plain HTTP with no way to verify them — a hostile mirror or a man-in-the-middle could serve you a poisoned package and you'd install it as root, none the wiser. The fix was Secure APT: the repository publishes a Release file listing the cryptographic hashes of its indexes, and signs that file with a private key. Your machine holds the matching public key and verifies the signature before trusting anything. This is the trust chain at the heart of this lesson — and it was bolted on after the fact, which is why so much of the ecosystem's security folklore is about not undoing it.

The through-line

Each era added one missing piece to the same idea: ship the files (tar) → ship the knowledge about the files (the package) → ship a catalog that resolves dependencies (the repository + apt) → ship proof the catalog is authentic (signing keys). Files, metadata, resolution, trust. Miss any one and you're back in an earlier, more painful decade — and skipping the last one is exactly how supply-chain attacks succeed.

3 · The Previous Solution (in detail)

To feel why the package/repository model is shaped the way it is, look closely at what people did before it — and what many still default to when a package isn't handy. Two patterns, both reasonable on the surface, both with a fatal ceiling.

3.1 Download-and-run (the tarball or the raw installer)

You find the software's website, download an archive or an installer script, and run it. It puts files wherever its author decided. This is discoverable (you went to the source) and direct (no system in the way). It is also the model behind the modern curl <url> | sudo bash one-liner you'll see on countless "quick install" pages — which is the very same thing wearing a convenient costume. 

# the pattern, in three equivalent disguises:
tar xzf sometool-2.3.tar.gz -C /usr/local        # unpack files into place, by hand
sudo ./install.sh                                # run the author's installer as root
curl -fsSL https://example.com/get | sudo bash   # download code and run it as root, unseen

3.2 The bespoke, hand-tracked install

The disciplined version of 3.1: you install by hand and keep your own notes — which files you placed, which libraries you first had to install, what to delete later. Correct in principle, and exactly how the very first system administrators worked. But it means you are the dependency solver, you are the file database, and you are the audit log — a full-time job that scales to roughly one server and zero teammates.

The assumptions baked in

  • Software knows how to install itself — each author invents their own placement and update logic.
  • Dependencies are the human's problem to discover and satisfy.
  • Trust is implicit: "I went to the official site, so it's fine."
  • Removal and audit are done from memory or private notes.

Why it feels fine at first

  • One program on one machine: genuinely quick.
  • No system to learn — just a download and a command.
  • Works identically on any distro (no package format needed).
  • The failure modes are invisible until you scale, update, or get attacked.

4 · Why It Failed (as an operating model)

As with the shell in 3.3, "failed" is scoped: downloading and running software is not wrong — it's the right shape for trying one thing once. It fails as the model for operating a server, where you install dozens of interlocking programs, keep them patched for years, and must be able to trust every byte you run as root. Each assumption becomes a concrete wall.

4.1 Dependency hell

If dependencies are the human's job, then installing one program can require hunting down five libraries, each needing others, some conflicting on version — program A wants libfoo 1.2, program B demands libfoo 2.0, and satisfying one breaks the other. Multiply across a real server's worth of software and the graph of requirements is far too large and too interlocked for a person to solve by hand. This is the wall that defines the whole field.

4.2 No clean update or removal

When software installs itself with no shared record of which files it owns, updating means overwriting blind and removing means guessing. Orphaned files accumulate; a half-removed program leaves landmines; two programs that both dropped a file into /usr/local/bin silently clobber each other. The system's actual state becomes unknowable.

4.3 No reproducibility

"Set up another server exactly like this one" is unanswerable when the install history lives in a human's memory. You cannot reliably recreate a machine, which means you cannot test safely, scale horizontally, or recover from disaster — all things Modules 8–11 will demand.

4.4 The trust wall — the sharpest failure

This is the one that still bites in the news. curl | sudo bash runs code you never read, as root, fetched over a connection you didn't verify, from a server that might be compromised or impersonated. There is no signature, no check, no record. If the download is tampered with — on the wire, on a hacked mirror, or by a typosquatted domain one letter off — you hand a stranger root on your machine and never know. Individual downloads have no chain of trust, and at server scale that is not a risk you can carry.

The pattern behind all four failures

Every failure traces to one root cause: the knowledge lived in people and websites, not in the system. The fix is a single inversion — move the knowledge into the machine. Bundle each program with metadata the system can read (its files, its dependencies): the package. Publish those packages in a catalog the system can query and solve against: the repository. And sign that catalog so the system can verify what it downloads: the signing key. Then installing is a solved, repeatable, authenticated transaction — not a hopeful download. That inversion is §5.

5 · The New Solution

The solution is the package manager over signed repositories. Bundle every program with machine-readable metadata (the package). Collect packages into a catalog with an index of names, versions and dependencies (the repository). Give the system a solver that reads the index and computes the full, correct install set (apt). And sign the catalog so the system can prove authenticity before running anything as root (the signing key). Vocabulary first.

5.1 The core vocabulary

Package (.deb)
A single file bundling a program's files plus metadata: its name, version, the exact list of files it installs and where, the packages it depends on, and optional maintainer scripts that run (as root) before/after install. The unit of installable software.
dpkg
The low-level tool that installs/removes a single .deb and maintains the local database of what's installed (/var/lib/dpkg). It does not fetch dependencies — it's the bricklayer, not the architect.
Repository
A server hosting a collection of packages plus index files that list every package, its version, and its dependencies — and a signed Release file vouching for those indexes. A trusted catalog.
apt
The high-level tool: it reads repository indexes, resolves dependencies (solves the graph), downloads the needed packages, verifies their signatures, and drives dpkg to install them in order. The architect that directs the bricklayer.
Sources list
The files in /etc/apt/sources.list.d/ (and legacy /etc/apt/sources.list) that tell apt which repositories to trust and where they live.
Signing key
A public/private key pair. The repository owner signs its Release file with the private key; your machine holds the public key (in a keyring file) and verifies the signature. Possession of the public key is what lets you trust a repository.
Release file & index
The Release file lists cryptographic hashes of the package index; the index lists hashes of every .deb. Signature on Release → trust the index → trust each package. One signature secures the whole tree.
Software supply chain
The full path software travels from an author's source code to running on your machine — build servers, maintainers, mirrors, keys. An attack surface: compromise any link and you compromise the software, without ever touching the target directly.
The one sentence to hold onto

apt reads a signed catalog of packages (software + metadata), solves the dependency graph into a complete install set, verifies every download against a signature anchored by a public key you hold, and hands the verified packages to dpkg to place their files and run their scripts — turning "get me this software" from a hopeful download into an authenticated, repeatable, reversible transaction.

5.2 The shape of the solution

Return to §1's need — "get me nginx" — and watch the model dissolve every sub-problem at once. One command triggers finding, solving, verifying, placing: 

sudo apt update          # refresh the local copy of the catalog (indexes), verifying its signature
sudo apt install nginx   # solve nginx's full dependency set, download + verify each, unpack, configure

"Where do the bytes come from?" — the repository named in your sources list. "What else does it need?" — the solver reads the index and pulls every dependency. "Where do the files go?" — the package's metadata says exactly, and dpkg records it for clean removal. "How do I update?" — apt upgrade next month. "How do I know it's real?" — the signature on the Release file, checked against your held public key, before a single byte is trusted. One model, every sub-problem answered.

6 · Internal Mechanics

Now the machine in detail. We'll (6.1) open a .deb and see the metadata; (6.2) trace exactly what apt install does, step by step; (6.3) make dependency resolution concrete; (6.4) walk the full trust chain from your held key down to a single .deb; (6.5) add a third-party repository the safe modern way and see why the old way was dangerous; and (6.6) tie it to reproducible DevBoard installs.

6.1 What's actually inside a package

A .deb is just an ar archive of three parts. You can look, and looking demystifies the whole thing: 

apt download nginx          # fetch the .deb into the current dir without installing it
ar t nginx_*.deb            # list the archive's members:
#   debian-binary            → format version (a "2.0\n")
#   control.tar.*            → the METADATA: dependency list, maintainer scripts, file manifest
#   data.tar.*              → the actual FILES, laid out as they'll sit on disk (./usr/sbin/nginx …)

dpkg-deb --info  nginx_*.deb   # human-readable metadata: Depends:, Version:, Maintainer: …
dpkg-deb --contents nginx_*.deb # every file it will install, and where

The Depends: line in that metadata is the entire reason a solver exists. The data.tar is why installation is just "unpack into /." And the maintainer scripts inside control.tar are why installation runs code as root — the exact fact that makes trust non-negotiable.

Read this twice

A package can contain preinst/postinst scripts that run as root during installation. That is by design — it's how a package creates a user, or reloads systemd. It's also precisely why a malicious or tampered package is catastrophic, and why the signature check in §6.4 exists. Installing is not copying files; it is executing the maintainer's code with full privilege.

6.2 What apt install nginx actually does

Press Enter and a precise sequence runs. Knowing it is the difference between "it installed" and "I know exactly what just touched my system":

  1. Read local indexes. apt consults the catalog copies fetched by the last apt update (cached under /var/lib/apt/lists/). It does not hit the network to re-list here — that's why a stale update gives you yesterday's versions.
  2. Resolve dependencies. It reads nginx's Depends:, then their Depends:, building the complete set, choosing versions that satisfy every constraint, and flagging conflicts. This is the solver — §6.3.
  3. Plan & confirm. It prints exactly what will be installed/upgraded/removed and the download size, and waits for your y. Read this list. An unexpected removal here is your early warning.
  4. Download. It fetches each needed .deb from the repository into /var/cache/apt/archives/.
  5. Verify. Each download is checked against the hash in the (signature-verified) index. A mismatch aborts the install. This is the trust chain paying off — §6.4.
  6. Unpack & configure. apt hands each verified .deb to dpkg, which unpacks data.tar into /, runs the maintainer scripts (as root), and records every file in its database so removal is exact.
update vs upgrade — the eternal confusion

apt update refreshes your local copy of the catalog (which packages/versions exist) — it installs nothing. apt upgrade installs newer versions of already-installed packages, using whatever the last update learned. The idiom sudo apt update && sudo apt upgrade (the && is Lesson 3.3's "only if the first succeeded") means "learn what's new, then apply it." Running upgrade without a fresh update just re-applies yesterday's knowledge.

6.3 Dependency resolution, made concrete

A dependency graph is a set of "needs" arrows. The solver's job is to pick one coherent version of every node so all arrows are satisfied — the thing that was unbearable by hand: 

       nginx
        ├── needs libssl3      (≥ 3.0)
        ├── needs libpcre2-8   (≥ 10.x)
        └── needs zlib1g
                    └── (already installed at a compatible version → reused, not re-fetched)

apt-cache depends nginx     # show nginx's direct dependencies
apt-cache rdepends libssl3  # reverse: what would break if you removed libssl3
apt list --installed        # the full solved state of your machine, as dpkg records it

When two requirements can't both be met (a version conflict), the solver says so instead of silently breaking things — the exact failure mode §4.1 described, now surfaced as a clear error you can act on rather than a mystery you discover at 3 a.m.

6.4 The trust chain: from your key down to one .deb

This is the security heart of the lesson. The chain has four links, and each vouches for the next:

LinkWhat it isVouched for by
Public key (in your keyring)The repository owner's public key, stored locally in /etc/apt/keyrings/ or /usr/share/keyrings/You — the root of trust. You chose to install it.
Release fileLists the cryptographic hashes of the package indexes, and is signed with the owner's private keyIts signature, verified by the public key above
Package indexLists every package and the hash of each .debIts hash appears in the (now-trusted) Release file
The .debThe actual software you installIts hash appears in the (now-trusted) index

Read it top-down: you trust the public key → the key proves the Release signature is authentic → the Release hashes prove the index is untampered → the index hashes prove each .deb is exactly what the repository published. One signature, verified once, secures an entire repository of thousands of packages. Break the chain at the top — install a malicious key — and every link below it lies to you convincingly. That is why which keys you install is a security decision, not a formality.

6.5 Adding a third-party repository — the safe way

You'll routinely need software newer than the base distro ships — a recent Docker, Node, or Postgres. That means adding a third-party repository and its key. There is a right way and a dangerous deprecated way, and the difference is exactly the trust chain above.

The modern, safe pattern

Fetch the key into a dedicated keyring file, then tell one source to trust only that key via signed-by=:

# 1) put the vendor's public key in its own keyring (not the global trust store)
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://example.com/vendor.gpg \
  | sudo gpg --dearmor -o /etc/apt/keyrings/vendor.gpg

# 2) add a source that is scoped to trust ONLY that key
echo "deb [signed-by=/etc/apt/keyrings/vendor.gpg] https://example.com/apt stable main" \
  | sudo tee /etc/apt/sources.list.d/vendor.list

sudo apt update      # now apt verifies this repo against that one key, and nothing else
The deprecated, dangerous pattern — don't

The old advice was curl … | sudo apt-key add -. This dumped the key into a global trust store, meaning that one vendor's key could then vouch for any repository on your system — a single compromised third party could authenticate malicious packages system-wide. apt-key is deprecated for exactly this reason. The signed-by= pattern scopes each key to its own repository, so trust stays compartmentalised. If a "quick install" guide tells you to apt-key add, treat it as out of date.

6.6 Reproducible installs: pinning versions

"Install nginx" gives you whatever version is newest today — fine for a laptop, a liability for a server you need to rebuild identically. Pin the exact version, and your install becomes reproducible and immune to a surprise change slipping in: 

apt list -a nginx                 # see every available version
sudo apt install nginx=1.24.0-1   # install one EXACT version, not "latest"

# in a Dockerfile (Module 7 preview) — pin so every rebuild is identical:
#   RUN apt-get update \
#    && apt-get install -y --no-install-recommends nginx=1.24.0-1 \
#    && rm -rf /var/lib/apt/lists/*

This is the bridge from "packages" to the reproducibility Modules 8–11 demand: a build you can't reproduce byte-for-byte is a build you can't fully trust, and a version you didn't pin is a version an attacker (or an accident) can change under you.

7 · Real Industry Examples

7.1 A base Docker image is nothing but this model

Open almost any Dockerfile (Module 7) and the first real line is apt-get update && apt-get install -y …. A container image is built by running package installs against signed repositories — the exact mechanics of this lesson, executed at build time instead of on a live server. When people say "containers made deployment reproducible," a large part of what they mean is "we pinned our package versions and installed from trusted repositories in a scripted, repeatable way."

7.2 The event-stream incident (2018)

A popular JavaScript package was handed off to a new "maintainer" who quietly added a dependency that stole cryptocurrency wallets — downloaded millions of times before discovery. Different ecosystem (npm, not apt), identical lesson: the attacker never touched a single victim's machine directly. They compromised one link in the supply chain and let the normal, trusted install process do the rest. This is why "who is allowed to publish, and how is it verified" is a security question, not a bureaucratic one.

7.3 Distro security teams and the CVE feed

When a vulnerability (a CVE) is found in, say, OpenSSL, distribution security teams build a fixed package and push it to the repository, signed. Every server running unattended-upgrades or a nightly apt update && apt upgrade pulls the verified fix automatically. The signed-repository model is what makes "patch the entire fleet overnight, safely" possible — the same machinery you're learning by hand here, running at planetary scale.

7.4 The xz backdoor (2024)

A multi-year social-engineering effort planted a hidden backdoor into the xz compression library — a dependency of countless systems — by patiently becoming a trusted maintainer. It was caught almost by accident. The takeaway that matters for you: trust chains protect the transport, not the intent of the source. A signature proves the bytes came from the maintainer unchanged; it cannot prove the maintainer is honest. Supply-chain security is defense in depth, and pinning + review + minimal dependencies are all part of it.

8 · Diagrams

9 · Advantages

  • Dependency hell, solved. One command computes and installs the complete, compatible set — the field's founding problem, gone.
  • Clean, exact removal & update. The system records every file it placed, so removal and upgrade are precise, not guesswork.
  • Authenticated by default. Signed repositories mean you verify, cryptographically, that what you run as root is what the maintainer published — before it runs.
  • Reproducibility. Pinned versions + scripted installs make "another identical server / image" a solved problem, the foundation of everything in Modules 7–11.
  • Fleet-wide patching. A signed security update propagates to every machine safely and automatically — the model that keeps the internet patched.
  • Auditability. dpkg's database and apt's logs (/var/log/apt/) give you a real record of what's installed and when it changed.

10 · Limitations

  • Signatures prove transport, not intent. A verified package is unchanged since the maintainer built it — it does not prove the maintainer is trustworthy (see xz, §7.4).
  • Distro packages lag. Stability means older versions; needing the newest software pushes you to third-party repos, which widens your trust surface (each new key is a new risk).
  • Post-install scripts run as root. The convenience that lets a package configure itself is also the mechanism a malicious package abuses. Trust is unavoidable, not optional.
  • Key management is a real, ongoing job. Keys expire, rotate, and get compromised; a mismanaged keyring silently breaks updates or, worse, weakens trust.
  • "It verified" ≠ "it's safe to run." Verification is necessary, not sufficient. Minimal dependencies, review, and pinning are the rest of the defense.

11 · Common Misconceptions

apt update upgrades my software.

It refreshes the catalog — the list of what's available — and installs nothing. apt upgrade is what installs newer versions. The pair update && upgrade means "learn what's new, then apply it."

Installing a package just copies files onto my disk.

It also runs maintainer scripts as root. That's how packages create users, enable services, or migrate config — and exactly why a malicious package is so dangerous and why the signature check exists.

curl <url> | sudo bash is fine if it's the official site.

It runs unread code as root over a connection with no signature check, from a server that could be compromised or impersonated. "Official site" is a feeling, not a verification. Prefer a signed repository; if you must run a script, download it, read it, then run it.

A signed package is a safe package.

A signature proves the bytes are unchanged since the maintainer built them — not that the maintainer is honest or the code is bug-free. The xz backdoor was, in effect, "properly signed." Verification protects the pipe, not the water.

Adding a third-party key with apt-key add is the normal way.

It's deprecated and dangerous: it makes that key able to vouch for any repo on the system. The modern way puts the key in its own keyring file and scopes it with signed-by= so trust stays compartmentalised.

Pinning versions is pedantic; "latest" is always better.

"Latest" means "whatever changed upstream since yesterday, unreviewed." For a server or an image you must rebuild identically — or defend against a supply-chain surprise — a pinned version is what makes the build reproducible and the change visible.

12 · Practical Use Cases

Standing up DevBoard's server

Install nginx, the Postgres client, and your runtime from signed repos; pin the versions; record them so the box is reproducible. This is Milestone 3's "operate and harden" made concrete.

Building a Docker image

The apt-get install lines in your Dockerfile (Module 7) are this lesson, pinned for reproducibility and cleaned up (rm -rf /var/lib/apt/lists/*) to keep the image small.

Nightly security patching

unattended-upgrades pulls signed security fixes automatically — the fleet-patching model, running on your one server.

Adding a newer runtime safely

Need a Node/Postgres/Docker newer than the distro ships? Add the vendor repo with a scoped signed-by= keyring — new software, trust kept compartmentalised.

13 · Summary

  • A package is software plus metadata — its files, its dependencies, and scripts that run as root — which is what makes automated, reversible installation possible.
  • A repository is a signed catalog of packages; apt reads its index, resolves the dependency graph, and installs the complete set. dpkg places one package; apt directs the whole job.
  • apt update refreshes the catalog; apt upgrade installs newer versions. They are different jobs.
  • The trust chain runs from a public key you chose to hold → the signed Release file → the index → each .deb. One verified signature secures a whole repository; a bad key at the top poisons everything below.
  • Add third-party repos the safe way: a dedicated keyring + signed-by=. The old apt-key add is deprecated because it makes one key trust the whole system.
  • Installing runs code as root, so trust is unavoidable — and the software supply chain (typosquats, compromised maintainers, malicious scripts, curl | sudo bash) is a real attack surface. Verification protects the transport, not the intent; pin versions, minimise dependencies, and read before you run.

16 · Quiz

How to use this

Answer in your own words before revealing the model answer — two or three sentences each. You're ready for Lesson 3.6 (services that survive reboots: systemd & journald) when you can answer Q1, Q4, Q6 and Q8 cold and have completed E1–E5 on a real machine.

What is the difference between a package and a plain .tar.gz of files?

A package bundles the files plus metadata the system can read: its version, the exact list of files it installs, the other packages it depends on, and maintainer scripts. That metadata is what lets the system resolve dependencies, place files correctly, and remove or update the software cleanly — none of which a bare tarball supports, because it carries the files but no knowledge about them.

What's the difference between dpkg and apt?

dpkg installs or removes a single .deb and maintains the local database of what's installed — but it does not fetch dependencies. apt is the high-level tool that reads repository indexes, resolves the whole dependency graph, downloads and verifies the packages, and then drives dpkg to install them in order. dpkg is the bricklayer; apt is the architect.

Explain apt update vs apt upgrade, and why the order in update && upgrade matters.

apt update refreshes the local copy of the catalog (which packages and versions exist) and installs nothing. apt upgrade installs newer versions of already-installed packages, using whatever the last update learned. Running upgrade without a fresh update just re-applies stale knowledge and can miss a just-released fix — so update && upgrade ("learn what's new, then apply it") is the safe idiom.

What problem does dependency resolution solve, and what was the world like without it?

Software rarely stands alone; it needs libraries, which need their libraries, sometimes at conflicting versions. The solver reads the dependency metadata and computes one coherent set of packages that satisfies every requirement, installing them in the right order. Without it you had dependency hell — hunting each dependency by hand, discovering conflicts only when something broke — which is the misery apt was invented to end.

Walk the trust chain from a signing key down to a single .deb.

You choose to hold a repository's public key. That key verifies the signature on the repo's Release file. The Release file contains the hashes of the package index, so a valid signature means the index is authentic. The index contains the hash of every .deb, so a matching hash means the package is exactly what the repository published. One verified signature, anchored by the key you hold, secures the entire repository top to bottom.

Why is installing a package a bigger deal than copying files, security-wise?

Because a package can contain maintainer scripts (preinst/postinst) that run as root during installation — by design, so it can create users or enable services. That means installing a malicious or tampered package hands an attacker root-level code execution. It's the exact reason the signature check exists and why which repositories and keys you trust is a real security decision.

Why is curl <url> | sudo bash risky even from an "official" site?

It downloads code and runs it as root unread, with no signature verification, from a server that could be compromised or a domain that could be a typosquat — and if the transfer is tampered with, you never know. "Official site" is trust by feeling, not by proof. A signed repository verifies authenticity cryptographically; if you must run a script, download it, read it, then run it.

What's wrong with apt-key add, and what replaced it?

apt-key add puts a key into the global trust store, so that one vendor's key can then vouch for any repository on the system — a single compromised third party could authenticate malicious packages everywhere. It's deprecated for that reason. The modern replacement stores each key in its own keyring file and scopes it to one repository with signed-by= in the source line, keeping trust compartmentalised.

Does a valid signature mean a package is safe? Explain.

No. A signature proves the bytes are unchanged since the maintainer built them — it protects the transport. It cannot prove the maintainer is honest or the code is free of backdoors; the xz attack was, in effect, "properly signed" malicious code from a trusted maintainer. Verification is necessary but not sufficient; minimal dependencies, review, and pinning are the rest of supply-chain defense.

Why pin an exact package version (nginx=1.24.0-1) instead of installing "latest"?

"Latest" resolves to whatever changed upstream since yesterday, so two installs a week apart can differ — and an unwanted or malicious change can slip in unnoticed. Pinning makes the install reproducible (the same server or Docker image every rebuild) and makes any version change an explicit, reviewable edit rather than a silent surprise. It's the bridge from "packages" to the reproducibility Modules 7–11 require.
