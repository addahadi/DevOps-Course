Module 3 · Lesson 3.1

The filesystem hierarchy and "everything is a file" (including your socket)

Module 2 explained the machine — CPU, RAM, storage — from the hardware up. Module 3 turns that understanding into the ability to operate a Linux server, and it begins where every Linux interaction begins: the single tree of paths that starts at /. In Lesson 2.5 you learned that a file is really an inode over some blocks. This lesson is the astonishing decision Unix made on top of that: to present almost everything — your disks, your terminal, your running processes, your kernel's tuning knobs, even a live network socket — as entries in that one filesystem tree, readable and writable with the same handful of operations. Understand this and the entire Linux system stops being a pile of unrelated commands and becomes one navigable, inspectable object you can explore with cd, ls and cat.

~70 min read Prerequisites: Module 2 (esp. 2.2, 2.5) Conceptual · hands-on at the end Module 3 · Milestone 3
Learning objectives

By the end of this lesson you will be able to:

  1. Explain the single-rooted directory tree, how mounting grafts separate filesystems into it, and why Linux has no drive letters.
  2. Navigate the Filesystem Hierarchy Standard (FHS) — know what actually lives in /etc, /var, /usr, /home, /tmp, /bin and friends, and why DevBoard's config, logs and data land where they do.
  3. State precisely what "everything is a file" means and does not mean, and name the file types (regular, directory, symlink, device, socket, pipe, and the /proc pseudo-files).
  4. Explain the file descriptor abstraction — why stdin/stdout/stderr, an open file, a socket and a pipe all look identical to a program.
  5. Read /dev, /proc and /sys as live windows into devices, processes and kernel state — connecting them back to Module 2's memory, CPU and storage.
  6. Distinguish hard from symbolic links, and reason about absolute vs relative paths, ., .. and the current working directory.
Where this sits on the map

This is the doorway to Module 3. It builds directly on Lesson 2.5's inode (a filename is a label on an inode) and Lesson 2.2's kernel/user-space split (the tree is the interface the kernel offers user space). Everything after it in this module is an application of the ideas here: Lesson 3.2 (users & permissions) attaches ownership bits to these files; 3.3 (the shell) pipes data between the file descriptors defined here; 3.6 (systemd) reads unit files from /etc and writes logs to /var; 3.8 (diagnosing a sick box) is almost entirely the art of reading /proc and /sys. Master the tree now and the rest of Linux is exploration, not memorisation.

1 · Problem Statement

You now own a live Linux server (Milestone 2). SSH into it and you are dropped at a prompt with a single starting point — / — and nothing else obvious. On this one machine there are many genuinely different kinds of things you will need to reach: the actual bytes of your configuration files; two or three separate storage devices (the root disk, maybe a data volume from Lesson 2.5, a swap partition); the keyboard and screen of your terminal; dozens of running processes; the network card; the kernel's own internal counters and tuning knobs; and later, DevBoard's Unix socket. Historically, each of these came with its own bespoke way to name it and its own special commands to inspect it. The problem this lesson solves is the one that makes a machine operable at all:

  • "There are many devices, filesystems, processes and kernel structures on this box, each a different kind of thing. Do I need a different naming scheme and a different tool for every one — or can they share a single addressing system I can learn once?"
  • "I have three separate storage devices. On the systems I grew up with they'd be C:, D:, E:. Where are they here, and why does /, /home and /data all look like one seamless tree with no drive letters?"
  • "A program reads from the keyboard, writes to the screen, reads a file, and talks over the network. Must it use four completely different APIs, or can it treat all four the same way?"
  • "When I need to know how much memory a process is using, or what the CPU is doing, or what's tuning the kernel — is there a place I can just look, with cat, instead of a magic tool per question?"
  • "Someone tells me DevBoard's config goes in /etc, its logs in /var/log, its binary in /usr/bin. Is that arbitrary folklore, or is there a predictable map I can rely on across every Linux machine I'll ever touch?"
The core problem

A running Unix machine is a zoo of fundamentally different resources — storage devices, partitions, terminals, processes, network endpoints, kernel data structures — and a human operator (and every program) needs to name, find, inspect and manipulate all of them. The naïve approach gives each resource its own namespace, its own access API and its own specialised tools, so operating the machine means learning dozens of unrelated systems. What we want instead is one uniform namespace — a single tree of paths — and one small set of operations (open, read, write, close) that work on nearly everything in it, plus a predictable convention for where each kind of thing lives, so that knowledge of one Linux box transfers to every other. That unification is the whole of this lesson.

The promise: by the end, a Linux system will look like a single explorable object. "Where does that live?" will have a principled answer (the FHS), "what is this thing?" will be one of a short list of file types, and "how do I look at it?" will almost always be "it's a path — cat it, ls it, or open it," whether the thing is a text file, a hard disk, a process, or a socket.

2 · Historical Context

The single tree and "everything is a file" were not obvious; they were a deliberate, radical simplification made at Bell Labs, and much of their staying power comes from how ruthlessly they were applied. Each step in the history pushed one more kind of thing into the file abstraction.

Before Unix · A namespace per resource

Earlier operating systems typically addressed different resources in different ways: files by one scheme, devices by special control calls, each subsystem with its own vocabulary. Reaching a tape drive, a disk and a printer meant three unrelated mechanisms. There was no unifying idea that these might all be the same shape to a program.

1969–1971 · Unix: one tree, and files as byte streams

Ken Thompson and Dennis Ritchie's Unix made two decisions that define this lesson. First, a single hierarchical directory tree rooted at /, into which all storage was grafted — no per-device namespaces. Second, and more radical, the file was redefined as a featureless stream of bytes with a tiny interface — open, read, write, close — and then devices were made to wear that same interface. A program writing to a disk file and a program writing to a terminal used identical calls. This is the birth of "everything is a file."

1970s · Device files and the uniform interface deepen

Special files under /dev let programs treat hardware as files: /dev/tty for the terminal, disk devices for raw storage, and the famous pseudo-devices /dev/null (a sink that discards everything) and later /dev/zero and /dev/random. The insight compounded: if a device looks like a file, every existing file tool — redirection, piping, cp, cat — suddenly works on hardware too, for free.

Late 1970s–1980s · Pipes and sockets — same interface, new plumbing

The pipe (1973) let the output of one program become the input of another as an anonymous in-kernel file. Then Berkeley Unix added sockets (1983) for networking. Sockets are the one famous place the abstraction bends — they need extra calls to establish a connection — but once connected they are read and written as file descriptors like everything else. Your DevBoard process talking to PostgreSQL over a Unix socket is using this lineage.

1990s · /proc and /sys — the kernel as files

Linux pushed the idea to its logical end with pseudo-filesystems. /proc exposes every process and much of the kernel's state as files you can cat (/proc/meminfo, /proc/<pid>/status — the very files you used in Lesson 2.4). /sys exposes devices and kernel tunables the same way. Nothing under these is on a disk; reading the "file" runs kernel code that produces the answer on the spot. The machine's own internals became browsable with ls and cat.

1994 onward · The FHS standardises the map

As Unix fragmented into many variants and Linux distributions multiplied, where things lived threatened to diverge. The Filesystem Hierarchy Standard (from the earlier FSSTND, first released 1994) codified the meaning of /etc, /var, /usr, /bin and the rest, so that skills and scripts transfer across distributions. That standard is the map §6.2 teaches, and it is why DevBoard's files have predictable homes on any Linux server you will ever rent.

3 · The Previous Solution (in detail)

To feel what the single tree buys you, look at the model many engineers already carry from other systems: multiple named volumes as separate roots (drive letters), plus special-purpose APIs for non-file resources. This is not a strawman — it is a coherent, widely-used design, and seeing its specific frictions is the fastest way to appreciate Unix's choice.

The model, stated plainly:

MULTI-ROOT + PER-RESOURCE-API MODEL  (e.g. drive letters)

  Storage: each device is its own root namespace
     C:\Windows\...        (system disk)
     D:\data\...           (second disk)
     E:\backup\...         (a USB stick)
  A path must FIRST name a volume, THEN a location within it.

  Non-file resources: each has its own dedicated interface
     devices   → special device-control calls / a Device Manager
     processes → a process API / Task Manager
     network   → a sockets API (separate from files)
     settings  → a registry / config database (its own tree, its own tools)

  To inspect the system you learn a DIFFERENT tool per resource type.

The assumptions this model bakes in:

Storage is many roots, not one
There is no single top; a path is meaningless until you say which volume it is on. Add or remove a device and the set of top-level roots changes.
Non-file resources are not files
Devices, processes, the network and system settings each live behind their own API and their own inspection tools. The uniform "open/read/write" of files does not extend to them.
Tools are resource-specific
Because each resource has its own interface, general text tools (search, redirect, pipe) can't be reused across resource types. You need a bespoke utility per question.
Location is convention-light
Without a strong cross-system standard for where things belong, each application chooses its own home for config, logs and data, and that placement varies between machines.

And this model genuinely works — hundreds of millions of people use it daily, and separating volumes by letter is arguably more immediately intuitive for a newcomer ("the USB stick is E:"). Its virtues are real: explicit volume names make "which disk is this on?" instantly visible, and purpose-built tools can be tuned to their resource. It becomes friction the moment you want to automate, script and compose operations across many resource types on a headless server — exactly the job of a DevOps engineer. The next section is those frictions.

4 · Why It Failed (for servers)

"Failed" here is scoped: the multi-root, per-resource model is fine for a desktop, but for a programmable, remotely-operated server it fights you at every turn. Each assumption becomes a concrete cost.

4.1 Fragmented namespaces resist composition

When storage lives under many roots and every other resource has its own namespace, there is no single way to refer to "a thing on this machine." A script that must touch a config, a device and a log has to speak three dialects. Automation — the heart of DevOps — thrives on uniform addressing, and fragmentation denies it.

4.2 A different tool per resource multiplies what you must learn and build

If inspecting memory needs one tool, processes another, devices a third, and network a fourth, then both humans and programs must master a sprawling, unrelated toolset — and every new resource type adds yet another. The general, powerful text tools (search, filter, transform, redirect) can't be pointed at resources that aren't files, so their power is stranded.

4.3 Non-file resources can't be piped, redirected or scripted uniformly

The single most productive pattern in Unix — take the output of X, feed it to Y — only works if X and Y both speak the file interface. When a device or a process or a kernel counter is not a file, you cannot cat it, cannot redirect it, cannot pipe it into grep. The composition that makes a server operable from a keyboard evaporates.

4.4 Weak location conventions make systems unpredictable

Without a strong, shared standard for where config, logs, binaries and data belong, every machine is a little different, and every application hides its files somewhere new. Operating a fleet becomes an exercise in remembering exceptions, and a script that works on one box breaks on the next.

The pattern behind all four frictions

Every friction traces to one root cause: resources are addressed and accessed in many incompatible ways. The fix is a double unification — put everything into one namespace (a single directory tree, so there is exactly one way to name any resource) and give almost everything the same tiny interface (open/read/write/close, so one set of tools operates on all of it) — and then standardise where things live (the FHS, so knowledge transfers). That is precisely the design of §5: one tree, "everything is a file," and a predictable map.

5 · The New Solution

The solution is three ideas that reinforce each other: one single-rooted tree for all naming, "everything is a file" for all access, and the FHS for all placement. Definitions first — the vocabulary for the rest of the module.

5.1 The core vocabulary

Root (/) & the single tree
There is exactly one top of the filesystem, written /. Every path in the system descends from it. There are no drive letters; all storage is grafted into this one tree.
Path (absolute vs relative)
A location in the tree. An absolute path starts at the root (/etc/nginx/nginx.conf); a relative path starts at your current working directory (logs/app.log), and uses . (here) and .. (parent).
Mount & mount point
The act of grafting a separate filesystem (a partition, a disk, a network share, a pseudo-filesystem) onto a directory in the tree, called its mount point. After mounting a data disk at /data, paths under /data transparently live on that disk. This is how many devices become one seamless tree.
"Everything is a file"
The design principle that most system resources — regular files, directories, devices, pipes, sockets, and kernel state — are represented as entries in the filesystem and accessed through the same small interface (open/read/write/close). "File" here means "something you can address by a path and operate on uniformly," not "bytes on a disk."
File descriptor (fd)
A small integer the kernel gives a process when it opens something; the process then reads/writes using that integer, regardless of what it refers to. Every process starts with three: 0=stdin, 1=stdout, 2=stderr. An open file, a socket and a pipe are all just file descriptors to the program.
File type
What an entry actually is, shown by the first character of ls -l: - regular file, d directory, l symlink, c/b character/block device, s socket, p named pipe.
Pseudo-filesystem (/proc, /sys)
A filesystem whose "files" are not stored on any disk; reading one runs kernel code that generates the answer live. /proc exposes processes and kernel info; /sys exposes devices and tunables.
FHS (Filesystem Hierarchy Standard)
The convention defining the purpose of each top-level directory (/etc, /var, /usr, /home, …), so that files have predictable homes across Linux systems.
The one sentence to hold onto

Linux presents the entire machine as a single directory tree rooted at /, into which all storage is mounted, in which almost every resource — files, devices, processes, kernel state, even sockets — appears as a path you can open and read/write through the same tiny interface (the file descriptor), organised by the predictable FHS map. Nearly every Linux operation in this course — piping, redirection, reading /proc, editing /etc, mounting a data volume — is a consequence of that one design.

5.2 The shape of the solution

Picture the machine as one tree. Different subtrees are backed by different things — a partition, a pseudo-filesystem, a device node — but to you they are all just directories and files under /: 

THE SINGLE TREE  ("one namespace, many backends, mounted together")

  /                         ← the one root (on the root partition)
  ├── etc/                  system configuration        (text files)
  ├── home/deploy/          your user's files
  ├── var/log/              logs that grow over time
  ├── usr/bin/              installed programs
  ├── tmp/                  scratch, cleared on reboot
  ├── data/         ◀── a SEPARATE disk mounted here (Lesson 2.5 volume)
  ├── dev/          ◀── device files: sda, null, tty   (the hardware, as files)
  ├── proc/         ◀── pseudo-fs: one dir per process + kernel info (live)
  └── sys/          ◀── pseudo-fs: devices & kernel tunables (live)

  Same tools everywhere:
     cat /etc/hostname          # a config file
     cat /proc/meminfo          # LIVE kernel memory stats (not on any disk)
     cat /sys/class/net/eth0/address   # the NIC's MAC address
     cp file /dev/null          # discard, using the ordinary copy tool

Now re-answer §1's questions, one line each. One scheme for many kinds of thing? Yes — a path, for all of them. Where are the three disks? Mounted into the one tree at /, /data, and (swap aside) wherever you graft them — no drive letters. Four APIs for keyboard/screen/file/network? No — all four are file descriptors, read and written identically. A place to just look at memory/CPU/kernel? Yes — /proc and /sys, with cat. Arbitrary folklore for config/logs/binaries? No — the FHS, the same on every box. One tree, one interface, one map.

6 · Internal Mechanics

Now the machine in detail. We will (6.1) build the single tree via mounting; (6.2) walk the FHS map; (6.3) enumerate the file types; (6.4) explain the file descriptor and the three standard streams; (6.5) read /dev as hardware-as-files; (6.6) read /proc and /sys as the live kernel; (6.7) pin down where sockets and pipes fit the abstraction; and (6.8) separate hard links from symlinks.

6.1 One tree from many filesystems: mounting

At boot, the kernel mounts one filesystem as the root (/). Every other filesystem — a second data disk, a swap-free partition, a USB stick, a network share, or a pseudo-filesystem like /proc — is mounted onto a directory within that tree, its mount point. Once mounted, the boundary is invisible in normal use: cd /data simply enters whatever filesystem is mounted there, on whatever device. This is why Linux needs no drive letters — the tree absorbs devices instead of listing them as separate roots. You saw the block devices behind this in Lesson 2.5's lsblk; mount (or findmnt) shows which device is grafted where and with which filesystem type. The elegance: a program reading /data/uploads/x.png neither knows nor cares that /data is a different physical disk than /.

6.2 The FHS: a place for everything

The top-level directories are not arbitrary. Learn this map once and you can find anything on any Linux box, and you will know exactly where DevBoard's pieces belong:

PathHoldsDevBoard relevance
/etcSystem-wide configuration, as editable text files. No binaries.Nginx config, systemd unit files, SSH config live here (Lessons 3.6–3.7).
/varVariable data that grows/changes at runtime: logs, spools, caches, databases./var/log for logs; a container/DB's data may live under /var/lib.
/usrInstalled read-only program files: most binaries (/usr/bin), libraries (/usr/lib), docs.Where installed tools (node, nginx, docker) actually live.
/homeOrdinary users' home directories (/home/deploy).Your deploy user's files, SSH keys, project checkout (Lesson 3.2).
/rootThe root user's home (note: not /).Avoid working here; use a normal user (least privilege, Lesson 3.2).
/tmpTemporary scratch, world-writable, often cleared on reboot.Safe scratch space; never store anything you need to keep.
/bin, /sbinEssential commands (and system/admin commands in sbin). On modern distros these symlink into /usr.ls, cp, ss, mount.
/optSelf-contained third-party software installed outside the package manager.Occasionally where a vendor blob lands.

The organising logic is worth internalising: the FHS separates files along two axes — static (programs in /usr, config in /etc) vs variable (runtime data in /var), and shareable vs host-specific. That is why "config is text in /etc, logs are in /var/log, the program is in /usr/bin" is a rule, not a coincidence — and why a well-behaved package puts its pieces exactly there.

6.3 The file types: what an entry actually is

"Everything is a file" does not mean everything is the same — it means everything wears the file interface. The first character of an ls -l line tells you which of a short list of types you're looking at: 

$ ls -l
-rw-r--r--  1 deploy deploy  1240 app.log        # -  regular file (ordinary bytes)
drwxr-xr-x  2 deploy deploy  4096 uploads/       # d  directory (a name→inode table)
lrwxrwxrwx  1 root   root      11 latest -> app.log   # l  symbolic link
crw-rw-rw-  1 root   root  1,   3 /dev/null       # c  character device (byte-stream hw)
brw-rw----  1 root   disk  8,   0 /dev/sda        # b  block device (block storage, L2.5)
srw-rw-rw-  1 postgres postgres 0 /var/run/postgresql/.s.PGSQL.5432   # s  socket
prw-r--r--  1 deploy deploy    0 mypipe           # p  named pipe (FIFO)
    │
    └─ first character = the file TYPE
Regular file (-)
Ordinary bytes on a filesystem — the inode-over-blocks of Lesson 2.5. Text, binaries, images.
Directory (d)
A file whose contents map names to inode numbers (Lesson 2.5). "Folders" are just this.
Symbolic link (l)
A tiny file whose contents are a path to another location — a pointer by name (§6.8).
Character & block devices (c, b)
Files under /dev standing in for hardware: character devices deliver a byte stream (terminals, /dev/null), block devices deliver fixed-size blocks (disks). The two numbers (major, minor) identify the driver and the specific device.
Socket (s) & named pipe (p)
Inter-process communication endpoints that appear as paths (§6.7) — a Unix-domain socket like PostgreSQL's, or a FIFO for streaming one program's output into another.

6.4 The file descriptor: why everything reads the same

The mechanism that makes "everything is a file" real for programs is the file descriptor. When a process opens anything — a file, a device, a socket, a pipe — the kernel returns a small integer. From then on the process calls read(fd, …) and write(fd, …) with that integer, and the kernel routes the operation to the right subsystem behind the scenes. The program does not branch on "is this a disk or a network card"; it just reads and writes an fd. Three descriptors are opened for every process automatically: 

  fd 0  stdin    ← where the program READS input   (keyboard by default)
  fd 1  stdout   → where it WRITES normal output    (screen by default)
  fd 2  stderr   → where it WRITES error output      (screen by default)

  Because these are just fds pointing at "some file," the shell can REPOINT them:
     myapp  > out.log        # fd 1 now points at a file, not the screen
     myapp 2> err.log        # fd 2 (errors) to a separate file
     myapp < input.txt       # fd 0 reads from a file, not the keyboard
     producer | consumer     # fd 1 of producer wired to fd 0 of consumer (a pipe)

This is the quiet engine of the entire Unix command line, and it is why Lesson 3.3 (the shell) is so powerful: redirection and pipes are nothing more than the shell swapping what fds 0/1/2 point at before launching your program. The program is written once, against "read fd 0, write fd 1," and works whether its input is a keyboard, a file, or another program's output. That uniformity is "everything is a file," paying off.

6.5 /dev: the hardware, as files

/dev is where devices wear the file interface. Some entries are real hardware (/dev/sda, /dev/nvme0n1 — the block devices of Lesson 2.5; /dev/tty — your terminal), and some are useful fictions the kernel provides:

/dev/null
A bottomless sink: anything written to it is discarded, reading it returns end-of-file. The universal "throw this away" — you already used > /dev/null in Lesson 2.5's exercises.
/dev/zero
An infinite source of zero bytes — used to create or wipe files (Lesson 2.5's dd if=/dev/zero).
/dev/random, /dev/urandom
Sources of cryptographic-quality random bytes from the kernel — where key generation and tokens draw entropy (you'll meet this in Module 4's cryptography).

Because these are files, ordinary tools operate on hardware and pseudo-devices for free: cat /dev/urandom | head -c 16 pulls 16 random bytes; cp bigfile /dev/null is a read-speed test; writing an image to /dev/sdb with dd flashes a disk. No special API — just the file interface, pointed at hardware.

6.6 /proc and /sys: the live kernel as files

This is where the abstraction becomes genuinely magical. Nothing under /proc or /sys is stored on a disk. When you cat /proc/meminfo, the kernel generates the answer at that instant. It is a window, not a document. The layout: 

  /proc/meminfo             # live memory stats (Lesson 2.4's MemAvailable etc.)
  /proc/cpuinfo             # the CPUs (Lesson 2.1)
  /proc/loadavg             # system load
  /proc/mounts              # what's mounted where (the §6.1 tree)
  /proc//              # ONE directory per running process:
  /proc//status        #   its state, RSS/VSZ (Lesson 2.4)
  /proc//fd/           #   every file descriptor it has OPEN (§6.4!) — as symlinks
  /proc//cmdline       #   the command that started it
  /sys/class/net/eth0/address   # the NIC's MAC (Module 4)
  /sys/block/sda/queue/rotational  # 1=spinning disk, 0=SSD (Lesson 2.5!)

Read /proc/<pid>/fd/ and the whole lesson closes on itself: it lists, as symlinks, exactly the file descriptors from §6.4 — you can literally see that "everything is a file" is true for a running process, because its open socket, its log file and its stdin all appear there as fds. Much of Lesson 3.8's debugging, and tools like ps, top and lsof, are just friendly readers of /proc. And /sys is often writable: echoing a value into a /sys or /proc/sys file retunes the kernel live — which is exactly how you dropped the page cache in Lesson 2.5 (echo 3 > /proc/sys/vm/drop_caches).

6.7 Where sockets and pipes fit — the honest caveat

Sockets are the celebrated exception that proves the rule. A Unix-domain socket (like PostgreSQL's /var/run/postgresql/.s.PGSQL.5432) appears in the tree as a path with type s — you can see it, permission it, and DevBoard connects to it by that path. But you cannot simply cat a socket the way you can a regular file: establishing a connection needs extra system calls (socket, bind, connect, accept) that plain files don't. Network sockets (TCP/IP, Module 4) aren't even in the tree at all. The reconciling truth: once a socket is connected, it is a file descriptor read and written exactly like a file — so "everything is a file" holds for the data phase even where it bends for the setup phase. Named pipes (p) are the tidier case: a FIFO is a real path you can redirect into and out of like a file, letting two unrelated programs stream through the filesystem.

6.8 Hard links vs symbolic links

Lesson 2.5 introduced the hard link (a second directory entry pointing at the same inode). It is worth placing it beside the symbolic link, because they are constantly confused and behave very differently:

Hard linkSymbolic (soft) link
Points atthe same inode (the actual file)a path (a name), which it dereferences
If original name deleteddata survives — link count > 0link dangles (points at nothing)
Across filesystemsimpossible (inodes are per-filesystem)fine — it's just a path string
To a directorygenerally not allowedallowed and common
Made withln target nameln -s target name

Symlinks are everywhere in a real system — /usr/bin/python pointing at python3.11, a "current release" symlink swapped atomically during a deploy (a trick you'll use in Module 10's zero-downtime deploys). Knowing that a symlink stores a path while a hard link shares an inode explains why a symlink can dangle and cross disks while a hard link can't.

7 · Real Industry Examples

Redirecting a noisy program's output — because streams are files

A cron job or a service floods the terminal, and you want its normal output in one file and its errors in another. Because stdout and stderr are just fds 1 and 2 (§6.4), you write myjob > out.log 2> err.log, or discard chatter with 2> /dev/null. No feature of myjob made this possible — the file-descriptor abstraction did. This is the daily bread of operating services and the foundation of Lesson 3.3.

Diagnosing "what is this process actually doing" via /proc

A process is stuck or leaking. You cat /proc/<pid>/status for its memory (Lesson 2.4's RSS/VSZ), ls -l /proc/<pid>/fd to see every file, socket and pipe it has open (§6.4/6.6), and cat /proc/<pid>/cmdline for exactly how it was launched. Tools like lsof and ps are just prettier front-ends to these files. The machine's internals are browsable because the kernel exposed them as files.

Mounting DevBoard's data volume into the tree

In Lesson 2.5 you attached a block device for data. Here it becomes real: you create a filesystem on it, then mount it at /data (and add it to /etc/fstab so it remounts on boot). From that moment, /data/postgres transparently lives on the separate disk while the rest of DevBoard lives on the root disk — one tree, two devices, invisible seam (§6.1). This is the standard way to keep a database's storage separable from the OS.

The PostgreSQL Unix socket your app connects to

DevBoard's Express API connects to PostgreSQL. On the same host it typically uses the Unix-domain socket at /var/run/postgresql/.s.PGSQL.5432 — a path in the tree with type s (§6.7). You can ls -l it, see its permissions, and understand that "connect to the database" is, at bottom, "open this socket file and read/write the connection as a file descriptor." When Module 8 containerises the stack, this same socket-vs-TCP choice returns.

9 · Advantages

10 · Limitations

The abstraction is powerful but not total, and its edges matter.

"Everything is a file" is aspirational, not literal
Sockets need setup calls beyond open/read/write; network sockets aren't in the tree at all; some modern interfaces (certain ioctl-heavy devices, some kernel APIs) don't fit the byte-stream shape cleanly. The slogan is a strong tendency, not an invariant.
Text-stream everything can be lossy
Because the interface is "a stream of bytes," structure is often flattened to text that must be re-parsed downstream (the reason tools like awk/jq exist, Lesson 3.4). Newer approaches (structured logging, object APIs) push back on pure text.
The FHS is a convention, not enforcement
Nothing stops software from ignoring it; some vendor packages dump everything in /opt or a home directory. The map is reliable for well-behaved software, not guaranteed.
Pseudo-files can mislead the unwary
A /proc "file" has size 0 and changes every read; naïvely treating it like a static document (copying, diffing) produces nonsense. You must know it's a live window.
Mount complexity is real
Bind mounts, overlay filesystems (the basis of Docker images, Module 7), namespaces per container, network mounts that hang — the single-tree simplicity hides genuine complexity you'll meet later.

11 · Common Misconceptions

"'Everything is a file' means every resource is literally bytes stored on a disk."

No. "File" here means "addressable by a path and operated on through the open/read/write interface." Many "files" store nothing on disk: /proc and /sys are generated live by the kernel, /dev/null is a discard sink, a socket is a connection endpoint. It's a uniform interface, not a claim about storage.

"Linux needs drive letters like C: and D: for multiple disks."

It has none. Every filesystem is mounted onto a directory in the one tree rooted at / (§6.1). A second disk appears at, say, /data; entering it is just cd /data. Devices are absorbed into the namespace, not listed as separate roots.

"/root is the root of the filesystem."

The root of the tree is /. /root is merely the home directory of the root user, one ordinary directory under /. Easy to conflate, occasionally costly.

"A symbolic link and a hard link are basically the same."

They differ fundamentally (§6.8). A hard link is another name for the same inode (shares the data, same filesystem only, survives deletion of the other name). A symlink stores a path it dereferences (can dangle, can cross filesystems, can point to directories). One shares the file; the other points at a name.

"Configuration and logs could be anywhere; you just have to know each app."

For well-behaved software the FHS makes it predictable: editable config is text under /etc, growing runtime data and logs under /var (/var/log), installed binaries under /usr/bin (§6.2). That's a standard, not per-app folklore — which is exactly why skills transfer between Linux machines.

"You can cat a socket to read the database's traffic."

No — a Unix socket appears as a path but needs connection-setup syscalls (connect/accept); plain cat won't speak the protocol (§6.7). Once a program has connected, though, it reads and writes the socket as a file descriptor exactly like a file — the abstraction holds for the data phase, not the setup phase.

12 · Practical Use Cases

Finding where a service keeps its config, data and logs

Faced with an unfamiliar service on DevBoard's server, the FHS tells you where to look before you read a single doc: config in /etc/<service>, runtime data in /var/lib/<service>, logs in /var/log (or journalctl, Lesson 3.6). This map turns "I don't know this software" into "I know where its parts live."

Wiring programs together on the command line

Because stdout/stderr/stdin are files (§6.4), you compose: send a program's output to a file, split errors out, feed one command into another with a pipe, discard noise into /dev/null. Every non-trivial operational task — filtering logs, transforming data, chaining tools — is built on this, and it only works because these streams are files.

Inspecting the running system without special tools

Need the machine's memory, CPU, mounts, a process's open files, or whether a disk is an SSD? It's a cat away in /proc or /sys (§6.6) — and the same files power ps, top, free and lsof. When those tools aren't installed on a minimal container, you can still read the raw files directly.

Adding and organising DevBoard's storage

Mounting (§6.1) lets you keep the database's data on a dedicated volume mounted at /data, separate from the OS disk, so you can resize, snapshot or move it independently — and a symlink for the "current release" directory (§6.8) is the atomic-swap trick behind zero-downtime deploys in Module 10. The tree is not just for reading; it's how you lay out a system.

13 · Summary

  • A Linux machine is a zoo of different resources — storage, devices, terminals, processes, kernel state, sockets — and it is made operable by presenting almost all of them through one namespace and one interface.
  • There is a single tree rooted at /; every filesystem — real disks and pseudo-filesystems alike — is mounted onto a directory in it. No drive letters; a second disk just appears at a path like /data.
  • "Everything is a file" means most resources are addressable by a path and operated on through open/read/write/close — it's a uniform interface, not a claim that everything is bytes on a disk.
  • The file descriptor is the mechanism: a program reads/writes small integers, and the kernel routes each to a disk, device, socket, pipe or pseudo-file. stdin/stdout/stderr (fds 0/1/2) being files is why shell redirection and pipes work.
  • File types (from ls -l's first char) are a short list: regular -, directory d, symlink l, char/block device c/b, socket s, pipe p.
  • /dev exposes hardware as files (plus fictions like /dev/null, /dev/zero); ordinary tools therefore operate on devices for free.
  • /proc and /sys are pseudo-filesystems: their "files" are generated live by the kernel, exposing process and kernel state (the RSS/VSZ, meminfo, drop_caches you used in Module 2) as readable — and often writable — paths.
  • Sockets are the honest caveat: they appear in the tree and are read/written as fds once connected, but need extra setup calls; network sockets aren't in the tree at all.
  • Hard vs symbolic links: a hard link is another name for one inode (shares data, same FS, survives deletion); a symlink stores a path (can dangle, crosses filesystems, points to directories).
  • The FHS makes placement predictable: config as text in /etc, variable data and logs in /var, installed programs in /usr, homes in /home — the map DevBoard's files and the rest of Module 3 rely on.

15 · Exercise

Module 3's project increment is to harden and operate your Linux server. This first lesson's job is to make the machine legible: you will tour the tree, prove "everything is a file" with your own eyes, and read the live kernel. All commands are safe and read-only unless noted; do them on the real VPS, in a scratch directory (~/fs-lab) where you create files.

E1Tour the tree and confirm the single-root, mounted model

SSH into your VPS and survey the top level and the mounts:

ls -l /                  # the top-level FHS directories
tree -L 1 / 2>/dev/null || ls /   # one-level overview (tree if installed)
findmnt || mount         # which device/filesystem is mounted where (§6.1)
df -h                    # cross-check: filesystems and their mount points (L2.5)

Identify: the device mounted at /, at least one pseudo-filesystem (e.g. proc on /proc), and — if you attached a data volume in Lesson 2.5 — where it is mounted. Explain, using §6.1, why there are no drive letters.

Deliverable: the device mounted at /, one pseudo-filesystem you found, and one sentence on how mounting produces a single seamless tree. Adds to your Milestone 3 inventory.
E2Read the file types straight off ls -l

Look at directories rich in different types and decode the first character (§6.3):

ls -l /dev | head        # devices: c (char) and b (block) — find null and sda/vda
ls -l /dev/null /dev/zero
ls -ld /etc /tmp         # directories (d)
ls -l /usr/bin/python* 2>/dev/null   # often a symlink (l) → a versioned binary

For four entries, name the type from the first character and what it is. Find /dev/null (character device) and confirm a symlink somewhere with ls -l showing ->.

Deliverable: four ls -l lines annotated with their type (-/d/l/c/b) and what each is.
E3Prove file descriptors and redirection (streams are files)

Show that stdout, stderr and stdin are just repointable files (§6.4):

mkdir -p ~/fs-lab && cd ~/fs-lab
ls /etc /nope 1> out.log 2> err.log   # split normal output and errors into files
cat out.log ; echo '---' ; cat err.log
echo "hi" > /dev/null                  # discard via the null device
ls -l /proc/self/fd                    # THIS shell's open fds (0,1,2 + more) as symlinks

Explain why the successful listing landed in out.log and the error in err.log, and what /proc/self/fd is showing you (its link back to §6.4/6.6).

Deliverable: the split out.log/err.log result and one sentence identifying fds 1 and 2 as the reason redirection works.
E4Read the live kernel through /proc and /sys

Confirm that these "files" are live windows, not disk files (§6.6):

cat /proc/uptime         # seconds up — run it twice, the number changes
head -3 /proc/meminfo    # the MemAvailable etc. from Lesson 2.4
cat /proc/self/status | grep -E 'Vm(RSS|Size)'   # this shell's memory
cat /sys/block/*/queue/rotational 2>/dev/null    # 1=HDD, 0=SSD (Lesson 2.5)
ls -la /proc/meminfo     # note the size shows 0 — it isn't stored anywhere

Run cat /proc/uptime twice and note it changed. Explain, using §6.6, why a /proc file has size 0 yet returns data, and connect rotational back to Lesson 2.5's SSD-vs-HDD physics.

Deliverable: two different /proc/uptime readings, your machine's rotational value (SSD or HDD), and one sentence on why /proc files are generated live.
E5Hard link vs symlink, hands-on

Build both kinds of link and watch them behave differently (§6.8):

cd ~/fs-lab
echo "v1" > app.log
ln    app.log hardlink.log     # hard link: same inode
ln -s app.log symlink.log      # symlink: stores the path "app.log"
ls -li app.log hardlink.log symlink.log   # compare inode numbers & link counts
rm app.log                     # delete the ORIGINAL name
cat hardlink.log               # still works (data survives via hard link)
cat symlink.log                # dangles: "No such file or directory"

Explain, using §6.8, why hardlink.log still reads after deleting app.log while symlink.log breaks — and what the inode numbers and link counts told you.

Deliverable: the ls -li output (same inode for the hard link, different for the symlink) and one sentence contrasting "another name for the inode" with "a stored path."

16 · Quiz

How to use this

Answer in your own words before revealing the model answer. Two or three sentences each. You're ready for Lesson 3.2 (users & permissions) when you can answer Q1, Q3, Q5 and Q7 cold and have completed E1–E5 on a real machine.

Linux has three disks but no C:/D:/E:. How are they all reachable, and where?

Through mounting into a single tree rooted at /. One filesystem is mounted as the root; every other device — a data disk, a USB stick, even pseudo-filesystems — is grafted onto a directory (its mount point), e.g. a data disk at /data. After that, cd /data transparently enters that disk. There are no drive letters because the tree absorbs devices into one namespace rather than listing them as separate roots.

State precisely what "everything is a file" means — and one thing it does not mean.

It means most system resources — regular files, directories, devices, pipes, sockets, and kernel/process state — are addressable by a path and operated on through the same small interface (open/read/write/close). It is a claim about a uniform interface. It does not mean everything is bytes stored on a disk: /proc and /sys are generated live by the kernel, /dev/null discards data, and a socket is a connection endpoint — none are disk files, yet all wear the file interface.

Why does myprog > out.log 2> err.log work? What makes it possible?

Because stdout and stderr are just file descriptors 1 and 2 (§6.4) — handles that point at "some file," the screen by default. The shell repoints them before launching the program: fd 1 to out.log, fd 2 to err.log. The program does nothing special; it just writes fds 1 and 2 as always. This uniform file-descriptor abstraction is exactly what makes redirection and pipes possible across all programs.

Where would you expect a well-behaved service's config, logs and binary to live, and why is that predictable?

Editable config as text under /etc; growing runtime data and logs under /var (e.g. /var/log); the installed binary under /usr/bin. It's predictable because the Filesystem Hierarchy Standard (FHS) defines each directory's purpose along axes like static-vs-variable and shareable-vs-host-specific, so the same map holds across Linux systems and skills/scripts transfer between machines.

You run cat /proc/meminfo and ls -l shows its size as 0. Explain.

/proc is a pseudo-filesystem: its entries aren't stored on any disk. When you read /proc/meminfo, the kernel generates the answer at that instant from its live internal state, so the "file" has no on-disk size (reported as 0) yet returns current data — and returns different data next time. It's a live window into the kernel, not a static document, which is why tools like free and ps are really just readers of /proc.

Contrast a hard link and a symbolic link. What happens to each if the original name is deleted?

A hard link is another directory entry pointing at the same inode; it shares the actual data, works only within one filesystem, and if the original name is deleted the data survives (the inode's link count is still > 0). A symlink is a small file storing a path it dereferences; it can cross filesystems and point to directories, but if the original name is deleted the link dangles (points at nothing). One shares the file; the other points at a name and can break.

Sockets are cited both as an example of "everything is a file" and as its exception. Reconcile that.

A Unix-domain socket appears in the tree as a path (type s) you can list and permission, and once connected it is read and written as a file descriptor exactly like a file — so the abstraction holds for the data phase. But establishing the connection needs extra syscalls (socket/bind/connect/accept) that plain files don't, so you can't just cat it, and network (TCP/IP) sockets aren't in the tree at all. It bends for setup, holds for data.

How would you list every file, socket and pipe a running process currently has open, using only the filesystem?

Read /proc/<pid>/fd/ (or /proc/self/fd for your own shell). It contains one symlink per open file descriptor, each pointing at what that fd refers to — a regular file, a device, a socket, a pipe, etc. This is the filesystem making §6.4 visible: "everything is a file" is literally true for a process's open handles, and it's exactly what lsof reads under the hood.

What is the difference between / and /root?

/ is the root of the entire filesystem tree — the single top from which every path descends. /root is just the home directory of the root (superuser) account, one ordinary directory located under /. They're easy to conflate but completely different: one is the top of everything, the other is one user's home.

Give two concrete ways the file abstraction lets ordinary tools operate on things that aren't ordinary files.

Examples (any two): cp bigfile /dev/null uses the normal copy tool to measure read speed by discarding into a device; cat /proc/cpuinfo reads live kernel data with a text tool; echo 3 > /proc/sys/vm/drop_caches retunes the kernel by "writing a file" (Lesson 2.5); dd if=/dev/zero of=file fills a file from a pseudo-device; redirecting a program's stderr into grep filters errors. All work because devices, kernel state and streams present the same open/read/write interface as files.
