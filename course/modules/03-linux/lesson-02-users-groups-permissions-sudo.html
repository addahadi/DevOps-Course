Module 3 · Lesson 3.2

Users, groups, permission bits, ownership, sudo and least privilege

In Lesson 3.1 you learned to name and read anything on the machine as a path in one tree. But every ls -l line carried three things we deliberately ignored: an owner, a group, and a cluster of permission bits. Those fields are the entire access-control system of a Unix machine — the answer to "who is allowed to read, change or run each file," and therefore the answer to "what can an attacker who breaks into my web app actually touch." This lesson takes the tree you can now navigate and adds the security layer that decides who may open each node in it. It is the difference between a machine you can read and a machine you can safely expose to the public internet — and it is the foundation of the single most important operational habit in this course: least privilege.

~70 min read Prerequisites: Module 2, Lesson 3.1 Conceptual · hands-on at the end Module 3 · Milestone 3
Learning objectives

By the end of this lesson you will be able to:

  1. Explain that every process runs as a user (a UID) in one or more groups (GIDs), and read a process's and a file's identity from the system.
  2. Decode and set the owner / group / other × read / write / execute permission model — both the rwx symbolic form and the octal form (644, 755, 600).
  3. State precisely what read, write and execute mean on a file versus a directory — the source of most permission surprises.
  4. Change ownership and permissions with chown, chgrp and chmod, and predict what new files get, via the umask.
  5. Explain the three special bits — setuid, setgid, sticky — and why /usr/bin/passwd and /tmp need them.
  6. Describe what makes root special, how sudo grants scoped, audited escalation, and why "just run everything as root" is the cardinal sin.
  7. Apply least privilege: give each human and each service its own account with the minimum rights it needs — the exact hardening you'll do to DevBoard's server.
Where this sits on the map

This lesson attaches meaning to the owner/group/mode columns of Lesson 3.1's ls -l. It is the security spine of the rest of Module 3: Lesson 3.3 (the shell) runs commands as your user, subject to these bits; 3.5 (packages) installs software as root into root-owned directories; 3.6 (systemd) runs DevBoard as an unprivileged service user defined here; 3.7 (SSH) is entirely about who may log in and as whom, and refuses keys whose permission bits are too loose. The project increment for the whole module — a dedicated deploy user, key-only access, DevBoard running without root — is this lesson applied. Get least privilege into your hands now and every later hardening step becomes obvious rather than magic.

1 · Problem Statement

Your server is about to face the public internet. The moment DevBoard is reachable, so is your machine: bots will try your SSH port within minutes, and your own application code — parsing untrusted input from strangers — is one bug away from running an attacker's commands. On a single box you now have several distinct parties whose powers must differ: you (an administrator who occasionally needs to install software), a deploy account that ships new versions, DevBoard's web process (which touches untrusted data all day), PostgreSQL (which owns the database files and nothing else), and the system itself (whose config and binaries no ordinary process should be able to rewrite). The problem this lesson solves is the one that decides whether a single bug is an inconvenience or a total compromise:

  • "Many parties share this one machine — me, a deploy account, the web app, the database, the OS. How do I make sure each can touch only what it must, so a mistake or a break-in is contained rather than catastrophic?"
  • "An attacker exploits a bug in my Express handler. If that process could read /etc/shadow, rewrite the SSH config and delete the database files, I've lost everything. How do I ensure that process runs with almost no power in the first place?"
  • "I need to install a package or restart a service sometimes — genuine admin work. Do I have to log in as an all-powerful account full-time (and risk one fat-fingered command wrecking the box), or can I borrow that power briefly, deliberately, and on the record?"
  • "Three teammates deploy this app. If they share one login, and something gets deleted at 3 a.m., who did it? Can the system even tell me?"
  • "SSH refuses to use my private key, complaining it is 'too open.' Why does the permission bits on a file decide whether I can log in at all?"
The core problem

A server is a shared machine touched by multiple humans and multiple programs, some of them handling hostile input from the entire internet. If every party has full power, then any mistake or any compromise is unbounded: a single bug in one web request can read every secret, rewrite every config, and destroy every file on the box. What we need is a way to give each identity — human or program — a precisely bounded set of rights: the ability to open, modify, or run exactly the things it legitimately needs and nothing more, plus a controlled, recorded way to temporarily exceed those bounds for genuine administration. That containment — small blast radius by default, deliberate escalation by exception — is the whole of this lesson, and its governing principle has a name: least privilege.

The promise: by the end, every ls -l line will read like a sentence — "this file is owned by this user, in this group, and these parties may read/write/run it" — you will be able to run DevBoard as a near-powerless service account, and you will understand exactly why a broken web request on a well-configured box is a bad afternoon rather than a company-ending breach.

2 · Historical Context

Unix permissions are not a bolt-on security product; they were baked into the system from its earliest days because Unix was, from birth, a machine many people shared at once. Each step below added one more piece of the model you use today.

1960s · Time-sharing forces the question

Before time-sharing, a computer ran one program for one person at a time, and access control was a lock on the machine-room door. Systems like MIT's CTSS (Compatible Time-Sharing System, 1961) let many users log in simultaneously to one expensive mainframe — and immediately raised a new question no single-user machine had: how do you stop one user reading or clobbering another's files? CTSS introduced per-user accounts and even the first passwords. The shared computer created the need for permissions.

1969–1971 · Unix bakes identity into every file and process

Thompson and Ritchie's Unix made the model wonderfully small. Every user got a numeric user ID (UID); every running process carried the UID of whoever started it; and every file recorded an owner plus a compact set of permission bits. Access was checked by the kernel on every open. There was no separate "security system" to configure — identity and permission were properties of the same files and processes Lesson 3.1 taught you to read.

1970s · Groups, and the rwx triad

Real organisations aren't just "me" and "everyone." Unix added groups so a set of users could share access to a set of files (the classic example: a "staff" group that can all edit a shared project). The permission model settled into its enduring shape — three classes (owner, group, other) each with three bits (read, write, execute) — nine bits total, the model in §6.2 that has survived essentially unchanged for fifty years.

1973 · setuid — controlled, temporary privilege

Dennis Ritchie invented the setuid bit (patented 1979): a program marked setuid runs with the privileges of its owner, not its caller. This solved a real puzzle — how can an ordinary user change their own password, when the password file must stay unwritable to ordinary users? /usr/bin/passwd is owned by root and setuid, so running it briefly grants exactly the power to update your own line in the file, and nothing else. It is the first "borrow power for a narrow purpose" mechanism, and the ancestor of sudo.

Late 1970s–80s · The superuser, and then sudo

Unix designated UID 0 — root, the superuser — as the identity for which the kernel simply skips permission checks: root can do anything. That is powerful and dangerous, so in 1980 Bob Coggeshall and Cliff Spencer wrote sudo ("superuser do") at SUNY/Buffalo. Instead of logging in as root all day, an administrator runs a single command as root, authenticated by their own password, governed by a policy file, and logged. Least privilege for humans became practical.

1990s–2000s · Beyond all-or-nothing: capabilities, PAM, ACLs, MAC

The coarseness of "ordinary user vs all-powerful root" prompted refinements Linux still carries. POSIX capabilities (Linux 2.2, 1999) split root's monolithic power into ~40 discrete privileges (e.g. CAP_NET_BIND_SERVICE — bind a port below 1024 without being root). PAM (Pluggable Authentication Modules) made "how do we verify a user" configurable. POSIX ACLs added finer per-user grants beyond the nine bits. And mandatory access control — SELinux, AppArmor — added a policy layer above the discretionary model, confining even root. These are the topic of §10's limitations; the nine-bit model plus root plus sudo is the durable core you must master first.

3 · The Previous Solution (in detail)

The instructive "before" here isn't an old operating system — it's the model a working engineer defaults to when they haven't yet internalised least privilege, and it is depressingly common on real servers: one powerful account, used for everything. Provision a VPS and most providers still drop you in as root; the path of least resistance is to just stay there.

The model, stated plainly:

THE "EVERYTHING AS ROOT / ONE SHARED ACCOUNT" MODEL

  Login:      ssh root@server          (or one shared "admin" login for the team)
  Run the app:  node server.js         ← as root, so it "just works," no permission fights
  Deploy:       git pull && restart    ← as root
  Install:      apt install ...         ← as root (fine, this genuinely needs it)
  Teammates:    all share the same password / same key

  Files created: owned by root, often rw for everyone to avoid "permission denied"
  Mindset:       permissions are an OBSTACLE to be silenced with chmod 777, not a tool

The assumptions this model bakes in:

Privilege is binary and permanent
You are either "the admin" (all power, all the time) or locked out. There is no notion of holding minimal power by default and borrowing more briefly.
One identity serves all purposes
The same account edits system config, runs the internet-facing app, and owns the data. The web process's power equals the administrator's power.
Permissions are friction, not a feature
Because everything runs as root (which bypasses checks) or is made world-writable (chmod 777) to stop "permission denied," the bits are treated as noise to be silenced rather than a boundary to be designed.
Accountability is optional
A shared login means the machine cannot attribute an action to a person. "Who ran that?" has no technical answer.

And — crucially — this model works, which is exactly why it persists. The app starts, deploys succeed, nobody fights permissions, and on a private hobby box with one trusted operator the risk may genuinely be acceptable. Its appeal is real: zero friction, nothing to configure, no "permission denied" to debug at 2 a.m. The trouble is that every one of its conveniences is also the removal of a safety boundary — and the bill comes due the instant the machine faces untrusted input or more than one person. The next section is that bill.

4 · Why It Failed (for real servers)

"Failed" is scoped precisely: the all-root model is not wrong to exist — root has to exist, and some tasks truly need it — it fails as a default operating posture for an internet-exposed, multi-person machine. Each assumption becomes a concrete, well-known way to lose a server.

4.1 The blast radius equals the privilege

When the internet-facing process runs as root, a single exploited bug in your request handling grants the attacker root. They can read every secret (/etc/shadow, your .env, TLS private keys), install a backdoor, rewrite the SSH config to lock you out, encrypt the disk for ransom, and pivot to other machines. The same bug, in a process running as a powerless service user, lets them read only what that user could — often just the app's own files. The privilege you grant by default is the damage a compromise can do. This is the single most important sentence in the lesson.

4.2 Mistakes are as unbounded as attacks

Root doesn't only amplify attackers — it amplifies you. The infamous rm -rf / (or, more realistically, rm -rf $VAR/ where $VAR was empty) is annihilating as root and merely annoying as an unprivileged user, because the kernel refuses the unprivileged user permission to delete most of it. Running everyday work as root removes the guard rail that turns a typo into a shrug instead of a catastrophe.

4.3 chmod 777 as a way of life poisons the whole box

When permissions are treated as friction, the reflex fix for any "permission denied" is to make the file world-writable (chmod 777). But a world-writable file or directory means any process — including the compromised web app — can rewrite it. Make a script world-writable and you've handed code execution to anyone on the box; make a config world-writable and an attacker rewrites it to their advantage. The convenience directly manufactures vulnerabilities.

4.4 A shared account destroys accountability

If three people log in as the same root, the system genuinely cannot tell you who did what. Audit logs attribute every action to one indistinguishable identity, so post-incident review, revoking one person's access, and even honest "was that me?" questions become impossible. Security and operations both depend on the machine being able to say which human took an action.

The pattern behind all four failures

Every failure traces to one root cause: power is granted broadly and permanently by default, so the consequence of any bug, typo or break-in is unbounded. The fix is a single principle applied everywhere — least privilege: give each identity the minimum rights it needs, make privilege the exception you request deliberately rather than the state you live in, give every human and every service its own identity, and treat the permission bits as a boundary to design rather than noise to silence. That is precisely the model §5 builds: per-user and per-service identities, the owner/group/other × rwx bits as a real fence, and sudo as the controlled, audited gate for the rare moments you genuinely need more.

5 · The New Solution

The solution is one principle — least privilege — realised by four mechanisms that compose: distinct identities (users & groups) for every human and service; the nine permission bits (owner/group/other × read/write/execute) as the per-file fence; root as a tightly-guarded superuser; and sudo as the audited gate for borrowing root briefly. Vocabulary first — the terms the rest of the module leans on.

5.1 The core vocabulary

User & UID
An identity the system recognises, named for humans but represented internally by a numeric user ID. Every process runs as some user. Regular users start at UID 1000+; system/service users get low UIDs; UID 0 is root.
Group & GID
A named set of users, represented by a numeric group ID, used to grant shared access. Each user has one primary group and may belong to many supplementary groups (e.g. sudo, docker).
Ownership
Every file records an owning user and an owning group. These, plus the mode bits, decide who may do what to it.
Permission bits / mode
Nine bits attached to every file: read (r), write (w), execute (x) — one triad each for owner, group, and other (everyone else). Written symbolically (rwxr-xr-x) or as an octal number (755).
root / superuser (UID 0)
The identity for which the kernel skips permission checks. Root can read, write and execute anything, change any ownership, and bind privileged ports. Necessary, and dangerous — hence least privilege.
sudo
A program that lets an authorised user run one command as root (or another user), authenticated by their own password, governed by /etc/sudoers, and logged. Escalation on demand, not by default.
Least privilege
The governing principle: every identity should hold the minimum rights required for its job, and no more — so the damage from any bug or breach is bounded to that minimum.
Discretionary Access Control (DAC)
The name for this whole model: access is decided by the owner's discretion via ownership and the mode bits. (Contrast: mandatory access control like SELinux in §10, imposed by system policy.)
The one sentence to hold onto

Every process on a Linux machine runs as a numeric user (in one or more groups), and the kernel checks, on every access, the target file's owner/group/other × read/write/execute bits against that identity — except for root (UID 0), which bypasses the checks; the whole craft of operating a server safely is least privilege: give each identity the minimum rights it needs and use sudo to borrow more only briefly and on the record. Nearly every hardening step in this course — a deploy user, a service account, chmod 600 on a key, running DevBoard without root — is a direct application of that sentence.

5.2 The shape of the solution

Picture DevBoard's server the way it should look: several small identities, each fenced to its own job, and root sitting behind a gate you open only on purpose. 

LEAST PRIVILEGE ON DEVBOARD'S SERVER  ("many small identities, one guarded root")

  IDENTITY            RUNS / OWNS                 CAN TOUCH                     POWER
  ─────────────────   ─────────────────────────   ──────────────────────────   ───────────
  you  (uid 1000)     interactive admin login     your files; sudo when asked  low + gate
    └─ in group sudo  ── may borrow root via sudo, with YOUR password, logged ──▶ root (brief)
  deploy (uid 1001)   pulls & restarts releases   /srv/devboard, its releases  low
  devboard (uid 998)  the Express web process      only the app's own files     very low ◀ faces internet
  postgres (uid 111)  the database                 only /var/lib/postgresql     low
  root  (uid 0)       nothing runs here by default installs, service control    TOTAL (guarded)

  A bug in the internet-facing "devboard" process gets the attacker "devboard" —
  which can touch almost nothing. THAT is the blast radius you designed on purpose.

Now re-answer §1's questions in one line each. Contain each party? Yes — separate users, each fenced by ownership and mode bits. A web-app bug becomes root? No — the web process runs as the near-powerless devboard user, so the break-in inherits its tiny rights. Admin work without living as root? Yes — sudo, per-command, per-person, logged. Who deleted it at 3 a.m.? The audit log, because each human has their own account. Why does SSH reject a loose key? Because a private key readable by others is a private key you must assume is compromised — the bits are the policy. One principle, four mechanisms, a small blast radius by design.

6 · Internal Mechanics

Now the machine in detail. We will (6.1) locate identity — UIDs, GIDs and the files that define them; (6.2) decode the nine permission bits from ls -l; (6.3) master the octal shorthand; (6.4) pin down the crucial file-vs-directory meaning of rwx; (6.5) change ownership and mode, and predict new files via the umask; (6.6) explain the three special bits; (6.7) dissect root and sudo; and (6.8) turn it all into a least-privilege playbook for DevBoard.

6.1 Identity: who a process is, and where users are defined

Every process carries a user identity, and the kernel makes decisions against it. You can read your own and inspect the definitions: 

$ id
uid=1000(deploy) gid=1000(deploy) groups=1000(deploy),27(sudo),999(docker)
   │              │                └─ SUPPLEMENTARY groups (extra memberships)
   │              └─ primary group (GID) — the group new files you create get
   └─ your user ID (UID) — the identity your processes run as

$ whoami            # just the username
$ ps -o user,pid,cmd -C nginx    # what USER a given process runs as

Where do these identities live? In three plain text files under /etc (Lesson 3.1's FHS home for config) — themselves subject to the permissions this lesson teaches:

FileHoldsReadable by
/etc/passwdOne line per user: name, UID, primary GID, home dir, login shell. (Despite the name, no passwords anymore.)Everyone (world-readable) — it's just the name↔UID map.
/etc/groupOne line per group: name, GID, and its supplementary members.Everyone.
/etc/shadowThe actual hashed passwords and password-aging policy.root only (mode 640, group shadow) — the crown jewels.

A single /etc/passwd line reads like a record: deploy:x:1000:1000:Deploy User:/home/deploy:/bin/bash — username, an x placeholder (the hash lives in shadow), UID, GID, a comment, the home directory, and the login shell. A subtle but vital detail: giving a service account the shell /usr/sbin/nologin means nobody can log in as it interactively — exactly what you want for the devboard and postgres users, which should run a program, never a session. That the kernel identifies users by number (not name) matters later: inside a container (Module 7) UID 0 is still root even though the name mapping differs, which is why a container running as root is a genuine host concern.

6.2 Reading the nine bits from ls -l

Return to Lesson 3.1's ls -l line, and now read the part we skipped — the ten leading characters and the two names: 

-rwxr-x---  1  deploy  devs   8402  server.js
│└┬┘└┬┘└┬┘     └──┬──┘ └─┬─┘
│ │  │  │         │      └─ owning GROUP:  members of "devs"
│ │  │  │         └──────── owning USER:   "deploy"
│ │  │  └─ OTHER  (everyone else):  --- = no access at all
│ │  └──── GROUP  (the "devs" group): r-x = read + execute, not write
│ └─────── OWNER  (deploy):           rwx = read + write + execute
└───────── file TYPE (Lesson 3.1): - regular, d dir, l symlink, …

  The kernel picks ONE triad and stops:
     are you the owner?  → use the owner triad, done.
     else in the group?  → use the group triad, done.
     else                → use the other triad.

That last rule surprises people: the classes are checked owner, then group, then other, and the first matching class wins — the kernel does not "add up" permissions across classes. A consequence that feels backwards: a file with mode r--rw---- (owner=r, group=rw) means the owner can only read it even though group members can write — because once you match as the owner, that triad is final. You rarely write such a mode, but knowing the algorithm explains every "why can't the owner…?" puzzle.

6.3 The octal shorthand: 644, 755, 600

Typing rwxr-xr-x is tedious, so each triad is written as one octal digit: read=4, write=2, execute=1, summed. This is the notation you will actually use with chmod every day: 

   r w x   value            THREE digits = owner, group, other
   4 2 1                       ┌── owner
   ───────                     │ ┌── group
   r w x = 4+2+1 = 7           │ │ ┌── other
   r - x = 4+0+1 = 5           ▼ ▼ ▼
   r - - = 4+0+0 = 4           7 5 5   →  rwxr-xr-x   (a program / a directory)
   - - - = 0                   6 4 4   →  rw-r--r--   (an ordinary file)
                               6 0 0   →  rw-------   (a private file: SSH key, .env)
                               7 0 0   →  rwx------   (a private directory: ~/.ssh)
The four you must know cold

644 — normal file (owner edits, everyone reads). 755 — program or directory (owner edits, everyone may run/enter). 600 — private file, owner-only (SSH private keys, .env secrets). 700 — private directory, owner-only (~/.ssh). Almost everything you set by hand is one of these four; 777 (world-writable, world-executable) should make you flinch — it is the §4.3 anti-pattern.

6.4 What rwx means on a file vs a directory

This is the highest-value paragraph in the lesson, because the meaning of the three bits changes between files and directories, and the difference is the source of most real-world permission confusion. Recall from Lesson 3.1 that a directory is itself a file — one whose contents map names to inodes — and the bits suddenly make sense:

BitOn a regular fileOn a directory
r (read)read the file's contentslist the names inside (ls) — but not necessarily use them
w (write)modify the file's contentscreate, rename or delete entries inside — note: deleting a file needs write on its directory, not the file!
x (execute)run it as a programenter / traverse it (cd, and access anything inside by name)

Two consequences trip up nearly everyone. First: to reach /a/b/c.txt you need execute on /, /a and /a/b — execute on a directory is "permission to pass through." A directory can be r without x (you can ls the names but can't open any of them) or x without r (you can open a file if you already know its exact name, but can't list what's there — a common trick for "reachable but not browsable" directories). Second: whether you can delete a file has nothing to do with the file's own bits — it depends on write permission on the containing directory, because deleting is editing the directory's name→inode table. This is why you can delete a read-only file you own the directory of, and why the sticky bit (§6.6) exists to stop that in shared directories like /tmp.

6.5 Changing ownership and mode — and predicting new files (umask)

Three commands cover almost everything. Note that changing ownership generally requires root (only root may give a file away), while changing mode is the owner's prerogative: 

chmod 640 secrets.env          # set exact octal mode  → rw-r-----
chmod u+x deploy.sh            # SYMBOLIC: add execute for the owner (u=user,g,o,a)
chmod g-w,o-r report.txt       # remove group-write and other-read
chmod -R 755 /srv/www          # recurse into a tree (careful: applies x to files too)

chown deploy:devs server.js    # set owner=deploy, group=devs   (needs root)
chgrp devs shared.log          # change only the group
chown -R devboard: /srv/devboard   # give a whole tree to the service user

But what mode do new files get, when you never set one? Every process has a umask — a set of bits to subtract from the default. Programs create files with a base mode of 666 (files) or 777 (directories), then the umask masks off the bits it names. The near-universal default umask is 022, which removes write from group and other: 

  new FILE:  base 666  minus umask 022  →  644  (rw-r--r--)
  new DIR:   base 777  minus umask 022  →  755  (rwxr-xr-x)

  A tighter umask 077 (remove ALL rights from group+other) gives:
  new FILE:  666 - 077 →  600            new DIR:  777 - 077 → 700
  → use umask 077 for accounts that handle secrets, so files are private by default.

The umask is why a file you just created is readable by others without you asking — the default 022 chose that. Understanding it turns "why is this world-readable?" from a mystery into a one-line answer, and setting a service account's umask to 077 is a quiet but real hardening step.

6.6 The three special bits: setuid, setgid, sticky

Beyond the nine, three more bits handle cases the basic model can't. They occupy the "missing" high octal digit (a fourth digit, e.g. chmod 4755) and appear in place of an x in ls -l:

setuid (u+s, octal 4000) — on an executable
The program runs with the privileges of its owner, not its caller (§2's Ritchie invention). ls -l /usr/bin/passwd shows -rwsr-xr-x owned by root: an ordinary user running it briefly gains root's power for that program only, so they can update their line in /etc/shadow. Powerful and risky — a bug in a setuid-root binary is a privilege-escalation hole, which is why they are audited and minimised.
setgid (g+s, octal 2000) — on an executable or a directory
On a program: run with the owning group's rights. On a directory, far more useful: new files created inside inherit the directory's group instead of the creator's primary group — the standard trick for a shared project folder where everything must stay group-devs readable.
sticky bit (+t, octal 1000) — on a directory
In a directory with the sticky bit, a user may only delete their own files, even if the directory is world-writable. This is exactly why /tmp (mode 1777, ls -l shows drwxrwxrwt) lets everyone create scratch files but stops one user deleting another's — fixing the §6.4 "delete depends on directory write" hazard for shared spaces.

6.7 root and sudo: the guarded gate

Root (UID 0) is special by a single rule: the kernel's permission check returns "allowed" immediately for it, without consulting the mode bits. That's the whole magic — root isn't listed in every file's permissions; it simply skips the test. Which is why the goal is never to remove root (impossible and pointless) but to ensure almost nothing runs as it, and that reaching it is deliberate. sudo is that gate: 

$ apt install nginx
E: Could not open lock file ... - open (13: Permission denied)   ← you're not root

$ sudo apt install nginx
[sudo] password for deploy:  ____        ← YOUR password, not root's
   → sudo checks /etc/sudoers: is "deploy" allowed to run this?
   → if yes: runs the ONE command as root, then drops back to you
   → and writes a line to the auth log: who, when, which command

Four properties make sudo the least-privilege tool for humans. It is per-command (you return to your ordinary self immediately after — you are not "in a root session"). It authenticates with your own password, so there is no shared root password to leak. It is policy-controlled by /etc/sudoers (edited only with visudo, which validates syntax so a typo can't lock everyone out) — and that policy can be narrow: "user deploy may run only systemctl restart devboard, without a password" is a legitimate, tightly-scoped grant. And it is logged, restoring the accountability §4.4 lost. Membership in the sudo group (Debian/Ubuntu) or wheel (RHEL) is what marks a user as allowed to sudo at all.

sudo su and sudo -i: the habit to break

sudo -i (or sudo su -) opens a full interactive root shell — and now you are living as root again, every command unlogged in its specifics and every typo catastrophic. It is occasionally justified for a long maintenance session, but reaching for it reflexively throws away most of what sudo bought you. Prefer sudo <one command>. If you find yourself wanting a root shell "to save typing sudo," that is usually a sign a command should be added to your sudoers policy instead.

6.8 Least privilege in practice: the DevBoard playbook

Everything above assembles into the module's project increment — hardening the server. The moves, and the reasoning behind each:

  • A human account per person, not shared root. Create deploy (or one per teammate), add it to the sudo group, and stop using the root login. Now actions are attributable and everyday work has guard rails.
  • A dedicated, no-login service user for the app. DevBoard's Express process runs as devboard (shell /usr/sbin/nologin, owning only its own files under /srv/devboard). A break-in through a web request inherits this user's near-zero power — the §4.1 blast radius, shrunk on purpose. Postgres already ships this way (the postgres user owns only its data dir).
  • Secrets are 600, owned by the account that needs them. The .env, TLS private keys and SSH keys are readable by exactly one user. This is not paranoia: it is the reason a leaked read-only bug can't necessarily read your database password.
  • The app never needs root to serve traffic. "But it must bind port 80/443!" — that is the one classic reason people run web apps as root, and the correct fix is not root: either put Nginx in front (Module 5) and let the app listen on a high port, or grant just CAP_NET_BIND_SERVICE (§2's capabilities). Never trade the whole machine's safety for one port number.
  • Narrow sudoers grants for automation. The deploy pipeline (Module 10) may be allowed to run only the exact restart command, passwordless — power scoped to a single verb, not a blank cheque.

7 · Real Industry Examples

SSH refuses your key because its permissions are too open

You try to log in and SSH prints Permissions 0644 for 'id_ed25519' are too open ... this private key will be ignored. This isn't pedantry: a private key readable by other users on the machine must be treated as compromised, so ssh refuses to use it until it is chmod 600 and its ~/.ssh directory is 700 (§6.3). It is the purest demonstration in daily life that the permission bits are the security policy — the tool enforces least privilege on your behalf. You will meet this exact message in Lesson 3.7.

A compromised web app that couldn't do much — because of the service user

The recurring good-news story of production security: an application server is exploited through an unpatched dependency, but because the process ran as an unprivileged, no-login service user owning only its own directory, the attacker landed in a near-empty sandbox — no access to other apps' data, system config, or secrets outside that user's reach. The breach is contained to what that user could touch (§4.1). The same exploit against an app running as root is a full server takeover. The single decision "run it as a dedicated low-privilege user" is what separated the two outcomes.

The chmod -R 777 that opened a hole

An engineer hits "permission denied" on an upload directory and fixes it with chmod -R 777 /var/www. Now the web application's own scripts are world-writable — and the same web process, once it has any file-write bug, can overwrite its own code and achieve remote code execution. The "fix" manufactured the vulnerability (§4.3). The correct fix was to chown the upload directory to the service user and grant only the write it needed — least privilege, not maximum permission.

Scoped, passwordless sudo for a deploy robot

DevBoard's CI/CD (Module 10) needs to restart the service after a deploy, but must not have a shell or broad root. The sudoers policy grants the deploy identity exactly one line — deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart devboard — so automation can perform that one privileged verb without a password and nothing else. This is least privilege applied to a machine actor, and it is standard practice in real deployment pipelines.

10 · Limitations

The classic Unix model is durable, but it is coarse, and its edges are worth knowing.

Root is all-or-nothing
The base model has only "ordinary" and "god." A process that needs one privileged thing (bind port 80) traditionally had to be full root. POSIX capabilities (§2) split root into ~40 pieces to fix this, but the default mental model is still binary.
Only three classes — owner, group, other
You cannot express "these two specific users may write, that one may only read" with the nine bits alone; you get one owner, one group, and everyone else. POSIX ACLs (setfacl/getfacl) add per-user/per-group grants, at the cost of complexity that's easy to overlook.
It's discretionary — the owner can always widen access
DAC lets a file's owner grant it to the world at will, and root can override anything. For environments needing enforced, un-overridable policy (even against root), mandatory access control — SELinux, AppArmor — layers a system-imposed policy on top. That's a whole discipline beyond this course's core.
Misconfiguration is silent and common
Nothing warns you that a secret is world-readable or a script world-writable until it's exploited. The model enforces the bits faithfully — including the wrong ones you set. Auditing (§15) is a real, ongoing task.
Numeric UIDs cross boundaries in surprising ways
UID 0 in a container is UID 0 to the host kernel unless remapped (user namespaces, Module 7). "It's just a container" is not, by itself, a privilege boundary — a lesson that bites teams who run containers as root.

11 · Common Misconceptions

"chmod 777 fixes 'permission denied' — it's the safe universal solution."

It "fixes" the error by removing the boundary entirely: 777 means every user and process — including a compromised web app — can read, write and execute the file (§4.3). The real fix is to set the correct owner (chown) and the minimum bits the legitimate user needs (usually 644, 600, or 755). 777 should trigger suspicion, not relief.

"To delete a file you need write permission on the file."

You need write permission on the file's directory, not the file (§6.4) — because deleting is editing the directory's name→inode table. That's why you can delete a read-only file in a directory you can write, and why /tmp uses the sticky bit to stop users deleting each other's files despite the directory being world-writable.

"Running the app as root is fine — it's my server and root is convenient."

Convenience is exactly the trap. The privilege the process holds is the damage a single bug or exploit can do (§4.1). As root, one vulnerability in your request handling hands an attacker the whole machine — secrets, SSH config, other services. As a dedicated low-privilege user, the same bug is contained to almost nothing. Least privilege is not ceremony; it is the difference between an incident and a catastrophe.

"/etc/passwd stores passwords, so it must be secret."

Despite the name, /etc/passwd holds no passwords — just the name↔UID map, home dirs and shells — and is deliberately world-readable so the system can translate UIDs to names. The actual hashed passwords live in /etc/shadow, which is root-only (mode 640, §6.1). Confusing the two leads people to either over-protect a harmless file or misjudge where the real secret is.

"sudo and logging in as root are basically the same thing."

They differ in every way that matters (§6.7). sudo is per-command (you drop back to yourself immediately), authenticated by your own password, governed by policy (which can be scoped to specific commands), and logged against your identity. A root login is a full unbounded session, unattributed, with no guard rails — everything sudo was built to avoid. Reflexive sudo -i throws the benefits away.

"Group and other permissions don't matter if I'm the only user."

They matter enormously, because a server is never really "one user" — it runs many service accounts and, once exposed, hostile code running as some of them. "Other" is precisely the class a compromised process falls into for files it doesn't own. A world-readable .env is readable by the very web process an attacker might hijack. On a networked machine, the group/other bits are your defence against lateral movement.

12 · Practical Use Cases

Locking down secrets and keys

DevBoard's .env (database password, session secret), its TLS private key, and your SSH private key are each set to 600 and owned by exactly the account that uses them (§6.3). This one habit means that even a process that can read files it shouldn't is stopped at the boundary — and it is what makes ssh willing to use your key at all (§7).

Running every service as its own unprivileged user

The web app runs as devboard, the database as postgres, each a no-login account owning only its own data (§6.8). Compromise of one service can't reach another's files, and none can touch system config. This is the pattern Lesson 3.6's systemd units make declarative (User=devboard), and the whole reason a breach stays small.

A shared project directory that "just works" for a team

Give a directory to group devs, set it 2775 (group-writable + setgid), and every file created inside automatically belongs to devs (§6.6) — so teammates can all read and edit shared files without anyone running chgrp by hand or resorting to 777. Least privilege that is also convenient.

Granting automation exactly one privileged action

The deploy pipeline is allowed, via a single NOPASSWD sudoers line, to run only systemctl restart devboard (§7). CI can ship and restart the service without a password and without any other root power — the least-privilege pattern for machine actors that Module 10 relies on.

13 · Summary

  • Every process runs as a user (a numeric UID) belonging to one or more groups (GIDs); the kernel checks each access against the target's ownership and permission bits. Identities are defined in /etc/passwd, /etc/group and (hashes only) the root-only /etc/shadow.
  • Every file has an owning user, an owning group, and nine permission bits — read/write/execute for owner, group, other. The kernel uses the first matching class and stops; it does not add rights across classes.
  • The octal shorthand (r=4, w=2, x=1) gives the four modes to know cold: 644 (normal file), 755 (program/dir), 600 (private file), 700 (private dir). 777 is a red flag.
  • rwx means different things on directories: read = list names, write = add/rename/delete entries, execute = enter/traverse. Deleting a file depends on write to its directory, not the file — the reason the sticky bit exists for /tmp.
  • chown/chgrp set ownership (usually root-only); chmod sets mode (owner's right). New files' default mode comes from the process's umask (default 022 → 644/755; use 077 for secret-handling accounts).
  • Three special bits: setuid (run as file's owner — how passwd works), setgid (run as group, or make a directory's new files inherit its group), and the sticky bit (only delete your own files in a shared, world-writable dir).
  • root (UID 0) is special because the kernel skips permission checks for it. The goal is not to remove root but to ensure almost nothing runs as it and that reaching it is deliberate.
  • sudo grants root per-command, authenticated by your own password, governed by /etc/sudoers (edit only with visudo; grants can be narrowly scoped), and logged — restoring accountability. Prefer sudo <command> over a root shell.
  • Least privilege is the governing principle: each human and each service gets its own identity with the minimum rights it needs, so any bug or breach is contained. It is the whole of Module 3's project increment.
  • The model is durable but coarse: root is all-or-nothing (→ capabilities), only three classes (→ ACLs), discretionary (→ SELinux/AppArmor for mandatory policy), and silently misconfigurable (→ audit your bits).

umask                        # see WHY they came out that way (§6.5)
chmod 600 app.env            # lock the secret to owner-only

For each file, write its final permission string, its octal, and one sentence on who can now do what. Explain, using your umask, why app.env was not already 600 when created.

E3Watch the kernel enforce the bits — file vs directory

Prove the §6.4 file-vs-directory distinction, including the delete surprise:

cd ~/perm-lab
mkdir vault && echo "top secret" > vault/data.txt
chmod 000 vault/data.txt          # remove ALL bits on the FILE
cat vault/data.txt                # denied — you can't read it…
rm  vault/data.txt                # …yet you CAN delete it. Why? (you own the DIR)
mkdir locked && echo hi > locked/x
chmod 600 locked                  # dir has r+w but NO execute (traverse)
ls locked                         # you can LIST the name…
cat locked/x                      # …but can't OPEN it: no traverse (x) on the dir
chmod 700 locked                  # restore, then clean up

Explain, using the §6.4 table, (a) why you could delete a 000 file you couldn't read, and (b) why removing x from a directory blocked cat locked/x even though r still let you ls it.

needs sudo Feel the difference between ordinary and borrowed privilege (§6.7):

                                  # find the log line recording what you just ran

Explain why cat /etc/shadow failed but sudo cat /etc/shadow succeeded (what makes root special, §6.7), and find the audit line proving the machine recorded who escalated. Note that you authenticated with your password, not root's.

16 · Quiz

How to use this

Answer in your own words before revealing the model answer. Two or three sentences each. You're ready for Lesson 3.3 (the shell) when you can answer Q1, Q3, Q5 and Q8 cold and have completed E1–E5 on a real machine.

An ls -l line reads -rw-r----- 1 deploy devs ... app.env. Who can do what, and how does the kernel decide?

Owner deploy can read and write (rw-); members of group devs can read only (r--); everyone else gets nothing (---). On any access the kernel checks classes in order — owner, then group, then other — and uses the first matching class and stops; it never sums rights across classes. So a devs member who is not deploy is judged solely by the group triad. (Octal: mode 640.)

Translate 755, 644 and 600 to rwx form, and say when you'd use each.

755 = rwxr-xr-x — owner full, others read+execute: a program or a directory everyone may run/enter. 644 = rw-r--r-- — owner edits, everyone reads: an ordinary file. 600 = rw------- — owner only: a secret (SSH private key, .env, TLS key). The digits come from r=4, w=2, x=1 summed per triad (owner, group, other).

Explain what read, write and execute each mean on a directory — and why deleting a file doesn't need write on the file.

On a directory: read = list the names inside (ls); write = add, rename or delete entries; execute = enter/traverse it (cd, and open items by name). Deleting a file is editing the directory's name→inode table, so it requires write on the containing directory, not on the file — which is why you can delete a read-only file in a directory you can write, and why /tmp needs the sticky bit to prevent users deleting each other's files.

You create a file and it comes out 644 though you set no mode. Where did that come from?

From the process's umask. Programs create files with a base mode of 666 (directories 777), then the umask subtracts the bits it names. The default umask 022 removes write from group and other, so 666 − 022 = 644 for files and 777 − 022 = 755 for directories. Setting a tighter umask like 077 makes new files owner-only (600) by default — useful for accounts handling secrets.

What makes root special, and why is "just run the app as root" dangerous?

Root is UID 0, the identity for which the kernel skips the permission check entirely — it is always allowed. That's why it's dangerous as a default: the privilege a process holds is the damage a bug or exploit can do. An internet-facing app running as root turns one vulnerability into a full machine takeover (secrets, SSH config, other services). Run as a dedicated low-privilege user, the same bug is contained to that user's tiny rights — the essence of least privilege.

How is sudo apt install nginx different from logging in as root and running apt install nginx?

sudo runs that one command as root and immediately returns you to your own identity — you're never "in a root session." It authenticates with your own password, is authorised by /etc/sudoers (which can scope you to specific commands), and is logged against your name. A root login is an unbounded session, unattributed, with no guard rails on typos — exactly the risks (blast radius + lost accountability) that sudo exists to remove.

Why does /usr/bin/passwd need the setuid bit, and what does it do?

An ordinary user must be able to change their own password, but the password store (/etc/shadow) is writable only by root. The setuid bit makes passwd run with the privileges of its owner (root) rather than the caller, so for the duration of that one program the user has exactly the power to update their own entry — and nothing else. It's controlled, narrow privilege escalation, and the ancestor of sudo. (Setuid-root binaries are risky and audited precisely because a bug in one is a privilege-escalation hole.)

Why is chmod 777 a bad reflex fix for "permission denied," and what should you do instead?

777 grants every process — including a compromised web app — read, write and execute on the file, removing the boundary entirely; a world-writable script is a remote-code-execution waiting to happen. The correct fix is to identify which account legitimately needs access, set the file's owner/group with chown, and grant the minimum bits (usually 644, 600 or 755). Least privilege, not maximum permission.

What is the "blast radius" of a compromise, and how do users/groups let you control it?

The blast radius is everything an attacker can reach once they've taken over a process. Because a process runs as a user and can only touch what that user's ownership/permission bits allow, running each service as its own dedicated, low-privilege, no-login account confines a break-in to that account's files. A hijacked devboard web process can't read the database's data dir, other services' files, or system config — you designed the blast radius small. Running the same process as root makes the blast radius the whole machine.

Give three least-privilege steps you'd take to harden DevBoard's server, and the reason for each.

Examples (any three): (1) per-person accounts in the sudo group instead of shared root — restores accountability and adds guard rails to daily work. (2) Run the app as a dedicated nologin service user owning only its files — shrinks the blast radius of a web-app compromise to near zero. (3) chmod 600 on secrets and keys, owned by the one account that uses them — so a stray read bug can't leak the database password or private key. (4) Don't run as root to bind port 80; put Nginx in front or grant CAP_NET_BIND_SERVICE — never trade the machine's safety for a port number. (5) Scope automation's sudo to one exact command (NOPASSWD) — the deploy robot gets one verb, not a blank cheque.
