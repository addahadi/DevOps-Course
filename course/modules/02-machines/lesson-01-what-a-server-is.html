Module 2 · Lesson 2.1

What a server actually is: CPU, RAM, disk, NIC — from bare metal to instance types

At the bottom of the map you drew in Module 1 sat one box: the runtime — a server. In a few lessons you will rent one for $5 a month and start running commands on it. Before you do, open the box. This lesson is the physical machine: the four parts every server is made of, how they cooperate to run your code, why the gaps between their speeds decide everything about performance, and how "renting a server" in the cloud maps back onto real silicon.

~70 min read Prerequisites: Module 1 (esp. 1.5) Conceptual · hands-on at the end Opens Module 2 · Milestone 2
Learning objectives

By the end of this lesson you will be able to:

  1. Name the four core components of any server — CPU, RAM, disk, NIC — and state what each does and its size/speed/volatility trade-off.
  2. Explain how a program stored on disk becomes a running process executing on the CPU.
  3. Reproduce the memory hierarchy and explain why the latency gaps between its levels drive almost every performance decision you will ever make.
  4. Explain what bare metal, hypervisor, virtual machine and instance mean, and how one physical host is sliced into many.
  5. Read a cloud instance spec sheet — vCPU, GiB RAM, storage type, network Gbps — and know what you are paying for and where the catch is.
Where this sits on the map

Lesson 1.5 ended by pointing at the runtime node — "the machine where the process actually runs" — and promising Module 2 would open it. This is that lesson. Everything here is the hardware underneath every other node: the CI runner is one of these machines, the registry runs on these machines, and your production container runs on one too. Module 2.2 then puts the operating system on top of this hardware; for now we stay at the level of the metal.

1 · Problem Statement

You are about to pay a stranger $5 a month for "a server", type an IP address into an SSH client, and start running your production software on a machine you will never physically see. That is a strange thing to do without knowing what the thing is. And the gaps in that knowledge are not academic — they show up as the exact questions you will be unable to answer in your first month of operating real infrastructure:

  • "The spec says 1 vCPU, 1 GB RAM, 25 GB SSD. Is that a lot? Enough for what? What breaks first when it isn't?"
  • "My app was fine, then it got slow. Is it out of CPU, out of memory, or waiting on the disk? These have completely different fixes, and I can't tell them apart."
  • "The process got killed and the logs say Out of memory. What ran out, exactly? Why does running out of memory kill things when running out of disk usually just returns an error?"
  • "Two instances have the same price but one is 'burstable' and one is 'dedicated'. My app was fast for twenty minutes and then fell off a cliff. What happened?"
  • "Why is reading from the database across the network thousands of times slower than reading a variable, when both are 'just reading data'?"
The core problem

A server is not one thing; it is four very different things wired together, each with wildly different speed, capacity and cost, and each of which can independently become the bottleneck. If you treat "the server" as a single opaque unit — the way most developers do — then performance is a mystery, capacity is a guess, cost is a dartboard, and every incident is unfalsifiable. This lesson replaces the opaque box with four labelled parts and, crucially, the ratios between them.

Here is the promise. By the end you will look at 1 vCPU / 1 GB / 25 GB SSD / 1 TB transfer and read it the way a mechanic reads an engine spec: not as trivia, but as a set of limits that tell you what this machine can and cannot be asked to do. That is the foundation for every capacity, cost and performance decision in the rest of the course.

2 · Historical Context

The word "server" has drifted so far that it now means three different things, and untangling them is half the battle. Watching the history happen is the cleanest way to separate them.

The three meanings of "server"

Server as a role
A program that waits for requests and answers them — a web server, a database server. This is software. It is the meaning implied by "client/server".
Server as a physical machine
A computer built to run those programs continuously: rack-mounted, redundant power, lots of RAM and cores. This is hardware you could stub your toe on.
Server as a rented instance
A slice of a physical machine, rented by the hour, that behaves like its own computer. This is what you will actually buy, and it is a relatively recent invention.

This lesson is mostly about the second meaning (the hardware) so that the third meaning (your instance) stops being magic. Keep the distinction sharp: when someone says "restart the server", you should always ask which sense.

1950s–1970s · One machine, one program at a time

Early computers ran one job at a time for one organisation. The machine was the computing resource; the idea of "renting a fraction of one" made no sense because a single job used the whole thing. But the pressure to share an expensive machine produced the first important idea we will meet again: time-sharing — letting several users interleave on one machine so fast it feels dedicated to each. Hold that thought; the cloud is time-sharing with a business model.

1980s–1990s · Commodity hardware and the client/server split

Cheap microprocessors turned computers into commodities. Businesses filled rooms with x86 machines, and software split into clients (on desktops) talking to servers (in the back room). "A server" became a specific box you bought, named, racked, and cabled. Its four parts — processor, memory, disk, network card — are exactly the four parts your cloud instance still has today. The vocabulary you are about to learn is thirty years old and unchanged, because the physics didn't change.

2000s · Virtualization breaks "one box, one server"

A physical server spent most of its life nearly idle — a machine bought to handle the busy hour wastes the other twenty-three. VMware and others made virtualization practical on commodity hardware: software called a hypervisor could carve one physical machine into many isolated virtual machines, each believing it owned a whole computer. Suddenly one expensive box could host dozens of "servers", and the tie between "a server" and "a physical object" was cut for good.

2006–present · The cloud rents the slices by the hour

Amazon launched EC2 (Elastic Compute Cloud) in 2006 and turned virtualization into a utility: an API call gives you a virtual machine — an instance — in seconds, billed by the hour, on hardware you never see or own. This is the direct answer to Module 1's story: once a server is created by an API call rather than a purchase order, operations becomes programming, and the whole pipeline you mapped becomes possible. Your $5 VPS is a small instance on someone else's very large physical machine — and the point of this lesson is that "very large physical machine" is still just CPU, RAM, disk and NIC.

3 · The Previous Solution (in detail)

Before the cloud, "getting a server" meant acquiring and operating a physical machine yourself — on-premises (in your own building) or colocated (your machine in a rented rack in someone's data centre). This is not a museum piece: banks, hospitals and plenty of companies still do it, often for good reasons. Take it seriously so you can see exactly what the cloud changed.

The lifecycle of one pre-cloud server:

1. FORECAST   Estimate peak load for the next 3 years (you will be wrong).
2. SPECIFY    Choose CPU sockets, RAM, disks, RAID, NICs, power supplies.
3. PROCURE    Purchase order → vendor → 4–12 week lead time. Capital expense.
4. RACK       Mount it, cable power (usually two feeds) and network, label it.
5. PROVISION  Install an OS from disc/PXE, patch it, configure it by hand.
6. OPERATE    Monitor temperature, disks, PSUs. Replace failed parts yourself.
7. DEPRECIATE Run it ~3–5 years. Pay for power + cooling + rack space the whole time.
8. DISPOSE    Wipe disks, decommission, e-waste. Buy the replacement (goto 1).

The controls and assumptions baked into this model:

Capacity is bought up front, for the peak
You size for the busiest moment you can imagine, then pay for that capacity 24/7 forever, even though you use it for an hour a day.
The unit of failure is the whole box
One machine has one set of power supplies, one motherboard. When it dies, everything on it dies together, and recovery means physical hands.
Provisioning is slow and manual
Weeks from "we need a server" to "the server exists", then hours of hand-configuration — the snowflake server from Module 1 is born right here.
Cost is capital, not usage
You spend a large lump sum to own the machine (CapEx), rather than paying for what you use (OpEx). Idle capacity is money already spent.

Every one of these was a sensible answer when a server was a physical asset. And for steady, predictable, high-utilisation workloads, owning the metal is still often cheaper than renting it. The model didn't become wrong; it became a bad fit for the workload most of us actually have — spiky, uncertain, and changing faster than a procurement cycle.

4 · Why It Failed (for most workloads)

Five pressures pushed the industry from owning boxes to renting slices. Notice that most of them are about the ratio between capacity you bought and capacity you use — the same batch-size-style waste you saw in Module 1, in a different costume.

4.1 Utilisation: you pay for the peak and use the trough

A machine sized for Black Friday sits 5–15 % utilised the rest of the year. You bought 100 % of a machine to use 10 % of it on average. Industry-wide, pre-virtualization server utilisation was notoriously low — rooms full of expensive metal, mostly idle, all drawing power. That gap between purchased and used capacity is pure waste, and it is structural, not a failure of discipline.

4.2 Capacity mismatch cuts both ways

Guess too high and you waste money on idle metal. Guess too low and you cannot serve your users until a new machine is procured, racked and provisioned — weeks later. There is no dial; capacity comes in the granularity of "one whole physical server bought months ago." For a workload whose demand you cannot predict, both errors are expensive and one of them is fatal.

4.3 Lead time throttles everything

When a new environment takes weeks to appear, you stop creating environments. No throwaway staging box, no per-feature test machine, no "let me just spin one up to try this." The friction of provisioning silently shapes your entire engineering culture toward long-lived, precious, hand-tended servers — the exact opposite of the disposable, reproducible infrastructure Module 1 argued for.

4.4 The whole box is one failure domain

Redundancy in the physical world is expensive and coarse: to survive a machine failure you buy a second whole machine and hope they don't fail together. Fine-grained resilience — "run three copies of just this one service across three failure domains" — is impractical when your unit of infrastructure is a $6,000 box with a 6-week lead time.

4.5 Capital and specialised labour raise the floor

Owning servers means capital tied up in depreciating hardware, plus people who can rack, cable, cool and repair them, plus the building to hold them. For a small team or a solo engineer, that floor is prohibitive. The cloud converts all of it into a per-hour line item you can start and stop at will.

What virtualization actually fixed

Slicing one physical machine into many rentable virtual ones attacks every item above at once: idle capacity is resold to other tenants (utilisation), you rent exactly the slice you need and change it in minutes (mismatch and lead time), copies can be spread across many physical hosts (failure domains), and you pay by the hour with no capital outlay (cost). The catch — and there is always a catch — is that you are now sharing a physical machine with strangers, which §6.7 and §7 will make you feel in your latency graphs.

5 · The New Solution

The "solution" here is really two things: a clear model of what the hardware is, and a clear model of how that hardware gets sliced and rented. Definitions first, because every one of these words will be on your cloud provider's pricing page.

5.1 The four parts of any server

CPU — the Central Processing Unit
The part that actually executes instructions: arithmetic, comparisons, moving data around. Measured in cores (independent execution units) and clock speed (GHz, cycles per second). This is "how fast can I do work".
RAM — Random Access Memory (main memory)
Fast, volatile working memory that holds the code and data of everything currently running. "Volatile" = its contents vanish when power is lost. Measured in gigabytes. This is "how much can I be working on at once".
Disk — persistent storage (HDD or SSD)
Slow, non-volatile storage that keeps data when the power is off: the OS, your files, the database on disk. Measured in gigabytes/terabytes. This is "how much can I keep, and how durably".
NIC — the Network Interface Card
The hardware link to the network, and through it the internet. Measured in bandwidth (Gbps). This is "how fast can I talk to the outside world" — the on-ramp for the entire request path from Module 1.

There is also a motherboard tying them together with buses (the wiring data travels on), and a power supply and cooling. But for reasoning about software, those four parts and the speeds between them are the whole story.

5.2 The words on the pricing page

Bare metal
A whole physical machine, dedicated to you, no virtualization layer. Maximum performance and isolation; minimum flexibility.
Hypervisor
The software layer that divides one physical machine into many isolated virtual machines and shares the real CPU/RAM/disk/NIC among them. Also called a virtual machine monitor.
Virtual machine (VM)
A software-defined computer running on a slice of a physical host, with its own OS, that believes it has its own CPU, memory, disk and network.
Instance
A cloud provider's name for a VM you rent. An instance type (e.g. t3.micro) is a named bundle of vCPU + RAM + network specs at a price.
vCPU (virtual CPU)
The unit of CPU you rent. Usually one hardware thread of a physical core — not a whole physical CPU, and often not even a dedicated core. This word hides more than any other on the page; §6.7 dissects it.
Image
A snapshot of a disk (OS + preinstalled software) used to create an instance's starting state — the ancestor of the container image from Module 1.

With this vocabulary, "renting a server" decodes cleanly: a hypervisor on a big physical machine hands your instance a slice of real CPU (measured in vCPUs), a slice of real RAM, a slice of real disk, and a share of a real NIC — and bills you by the hour. The rest of the lesson is about what those slices can actually do, which comes down to speed.

6 · Internal Mechanics

Now the machine in motion. We will (6.1) watch the CPU run an instruction, (6.2) confront the single most important table in this course — the memory hierarchy and its latencies — then walk (6.3) RAM, (6.4) disk, (6.5) the NIC, (6.6) how all four cooperate on one real request, and finally (6.7–6.8) how the hypervisor slices them and how to read the resulting spec sheet.

6.1 The CPU: fetch, decode, execute, repeat

A CPU does something almost insultingly simple, a few billion times per second. It repeats a cycle:

  1. Fetch the next instruction from memory (the address is held in a register called the program counter).
  2. Decode it — what operation is this, on what operands?
  3. Execute it — add two numbers, compare them, load a value, jump elsewhere.
  4. Advance and repeat.

The clock speed is how many such cycles happen per second: 3 GHz is three billion cycles per second, i.e. one cycle roughly every 0.3 nanoseconds. Some vocabulary you will meet on spec sheets:

Core
A complete, independent execution unit. A 4-core CPU can genuinely run 4 streams of instructions at the same instant. This is real parallelism.
Thread / hyper-threading (SMT)
A trick where one physical core exposes two logical processors, interleaving two instruction streams to use idle moments in the core's pipeline. It is not two cores' worth of work — typically a 15–30 % boost, not 100 %. And a "vCPU" you rent is usually one of these threads.
Register
A tiny, blazing-fast storage slot inside the core (there are only a few dozen). Operands must be in registers to be computed on. This is the fastest memory that exists.
Cache (L1/L2/L3)
Small, fast memory on the CPU chip that holds recently-used data so the core doesn't have to wait for slow main memory. L1 is smallest and fastest; L3 is largest and slowest; all are far faster than RAM.

Why all these layers of memory? Because of one brutal fact: the CPU is far, far faster than the memory it reads from. A 3 GHz core can do an addition in a fraction of a nanosecond, but fetching a value from main memory takes ~100 nanoseconds — hundreds of cycles the core would otherwise spend waiting. Every cache exists to hide that wait. And that gap is best understood as a table.

6.2 The memory hierarchy — the most important table in this course

Each level of storage is faster but smaller and more expensive per byte as you go up, slower but larger and cheaper as you go down. The raw latencies span nine orders of magnitude. To make that graspable, the right-hand column scales every latency by the same factor (≈ 1 billion, so "1 ns → 1 second") to translate machine time into human time.

Read this table as a set of instincts

Look at the human-time column and let a few facts land. Reading from RAM (1.5 min) instead of cache (1 s) is a real cost. Reading from an SSD (5.5 hours) instead of RAM is a different universe. Crossing the network to another continent (nearly 5 years!) dwarfs everything the machine does locally. This is why caching in RAM is transformative, why a database query over the network is the expensive part of most requests, and why the entire discipline of performance is, at bottom, "stay as high up this table as you can, as often as you can." You will meet Redis (a RAM cache) in the project for exactly this reason.

6.3 RAM: the workbench where running things live

RAM is where the code and data of every running program sit while they run. When you launch your API, the OS loads it from disk into RAM and the CPU runs it from there. RAM is fast (~100 ns) and volatile: cut the power and it is blank. Two consequences drive everything later:

  • It is finite and shared. Every process wants some. When the total demanded exceeds what exists, something has to give — the OS starts swapping to disk (catastrophically slow, per the table) or the OOM killer terminates a process outright. That is the Out of memory from §1, and Lesson 2.4 is devoted to it.
  • It does not survive a restart. Anything you want to keep must be written to disk. This is precisely why a database has an on-disk representation and why "it was in memory" is never a durability guarantee.

A useful mental image: RAM is your desk. A big desk lets you keep many documents open at once; a small desk forces you to keep fetching from the filing cabinet (disk). The desk's size is your RAM in gigabytes; the cost of walking to the cabinet is the RAM→SSD cliff in the table.

6.4 Disk: durable, slow, and measured in more than gigabytes

Disk keeps data when the power is off. Two families, and the difference is enormous:

HDD (hard disk drive)
Spinning magnetic platters with a moving head. Cheap per gigabyte, but a random read means physically moving the head — hence the brutal ~10 ms seek in the table. Great for cold, large, sequential data; terrible for random access.
SSD (solid-state drive)
Flash memory, no moving parts. Orders of magnitude faster for random access (~20–100 µs). NVMe SSDs (connected over the fast PCIe bus) are faster still. Almost all cloud instance storage today is SSD.

Crucially, disk performance is three numbers, not one, and confusing them causes real outages:

Latency
How long one operation takes (the table's figures). Matters for a single small read.
IOPS (I/O operations per second)
How many separate reads/writes per second. A database doing many tiny random reads lives or dies by IOPS. Cloud disks often cap IOPS, and hitting that cap looks exactly like "the app got mysteriously slow."
Throughput (bandwidth)
How many megabytes per second for large sequential transfers. Matters for streaming big files or bulk copies.

And one more property that has no speed at all: durability — the probability your data survives. A single disk fails; production data lives on redundant storage (replication, RAID, or cloud block storage that is transparently replicated) precisely because one disk's durability is not enough. Lesson 2.5 goes deep here.

6.5 The NIC: the on-ramp to everything remote

The network interface connects the machine to the network, and it has the same two-numbers story as everything else:

  • Bandwidth — how much data per second (Gbps). This is what "1 Gbps network" on a spec sheet means, and what your monthly "1 TB transfer" allowance meters.
  • Latency — how long a round trip takes, dominated by physical distance and the speed of light. Look again at the table: same-datacenter is ~0.5 ms, cross-continent ~150 ms. No amount of bandwidth fixes latency; they are different problems.

The NIC is where Module 1's request path physically enters and leaves this machine, and where Module 4 (networking) will plug in. For now, just register that talking to anything off this box — the database on another host, an API across the internet — is the slowest thing in the table by a wide margin, and therefore usually the first thing to optimise or cache.

6.6 How the four parts cooperate on one real request

Put it together. A user hits your API endpoint that looks up a task by id. Watch which component does the work and, roughly, where the time goes: 

1. NIC      packet arrives from the network         ← request path enters here
2. CPU+RAM  the OS and your process (already in RAM) wake to handle it
3. CPU      your code runs: parse the request, decide what to do   (nanoseconds)
4. RAM      read variables, request objects — fast                 (~100 ns each)
5. ??? the data isn't in memory, so you query the database:
      · if the DB is on THIS box, hit its cache in RAM             (~100 ns)
      · if it must read the DB's disk                              (~20–100 µs)
      · if the DB is on ANOTHER host, add a network round trip     (~0.5 ms)
6. CPU      format the response                                    (nanoseconds)
7. NIC      send the response back out                             ← request path leaves

The lesson of the walkthrough is stark: steps 3, 4 and 6 — "your code" — are essentially free compared to step 5. In almost every real web service, the request spends the overwhelming majority of its time waiting: on the database's disk, or on the network to another host. This is why "my code is slow" is usually wrong and "my code is waiting" is usually right, and it is the single most useful instinct this lesson can give you.

6.7 Virtualization mechanics: how one machine becomes many

Now the slicing. A hypervisor sits between the physical hardware and the virtual machines and hands each VM a controlled illusion of its own hardware.

Type 1 (bare-metal) hypervisor
Runs directly on the hardware (e.g. KVM, Xen, VMware ESXi). This is what clouds use — thin, fast, and the VMs run nearly at native speed.
Type 2 (hosted) hypervisor
Runs as an app inside a normal OS (e.g. VirtualBox on your laptop). Convenient for development; more overhead.

How each resource is shared, and where the catch hides:

  • CPU: the hypervisor time-slices physical cores/threads among VMs — the 1970s time-sharing idea, industrialised. A vCPU is a schedulable share of a hardware thread. If your VM is promised "1 vCPU" but the host is busy, your VM waits its turn — visible as CPU steal (time the CPU was ready but the hypervisor gave the physical core to someone else).
  • RAM: partitioned among VMs. Some hosts overcommit — promising more total RAM than physically exists, betting not everyone uses it at once. When the bet is wrong, performance collapses.
  • Disk & NIC: shared too, which is why cloud disks and networks come with quotas (IOPS caps, bandwidth caps, transfer allowances) — the provider must stop one tenant starving the others.
The noisy neighbour, and why "1 vCPU" is slippery

Because you share a physical host with strangers, their load can steal cycles, cache and disk bandwidth from you — the noisy neighbour problem. And "1 vCPU" almost never means "one dedicated core you always have": it usually means "a scheduled share of one hardware thread, subject to the host's other tenants." Burstable instance types make this explicit and cheap: they let you briefly exceed a low baseline using CPU credits, then throttle you hard to the baseline once the credits run out. That is the "fast for twenty minutes, then a cliff" mystery from §1 — you spent your credits.

Read that not as "small and cheap" but as "a machine whose first limit is RAM, whose CPU is a shared thread, and whose disk and network have quotas." That single sentence will explain the majority of the operational surprises you meet in the next few modules — and you could not have written it before this lesson.

7 · Real Industry Examples

The $5 droplet / VPS, decoded

Providers like DigitalOcean, Hetzner, Linode and Vultr sell entry instances at roughly this tier: 1 shared vCPU, 1 GB RAM, ~25 GB SSD, ~1 TB transfer. It is a genuine Linux machine, and it is enough to run a small containerised app, a database and a reverse proxy — which is exactly what the course project will do. The art, which this lesson has equipped you for, is knowing that on this box RAM is the scarce resource and planning accordingly.

AWS t3.micro vs m5.large: the burstable trap

A t3.micro (2 vCPU burstable, 1 GB) looks like a bargain next to an m5.large (2 vCPU, 8 GB). But the t3 earns CPU credits slowly while idle and spends them fast under load; a sustained-CPU workload drains its credits and gets throttled to a low baseline — the classic "our benchmark was great, production fell off a cliff after 20 minutes." The m5 gives you its vCPUs continuously. Same "2 vCPU" on the spec sheet; completely different machines under sustained load. This is §6.7 made concrete, and it costs teams real money and real incidents every day.

The noisy-neighbour incident

A common war story: an app's latency mysteriously doubles for an hour, with no code change and no traffic spike, then recovers on its own. The cause is invisible from inside the VM — another tenant on the same physical host ran a heavy batch job, stealing CPU, cache and disk bandwidth. The tell is CPU steal showing up in metrics (Module 12). The fix is often to move to a dedicated-CPU instance type. You cannot even suspect this cause without the mental model of a shared physical host from §6.7.

Why "the database is on another server" is a design decision, not a detail

Look again at §6.6 step 5 and the table: putting your database on a separate host adds a network round trip (~0.5 ms in-datacenter) to every query, versus a RAM hit (~100 ns) if it were local. Teams still do it — for isolation, independent scaling and durability — but it is a deliberate trade of latency for operational flexibility, and the latency table is exactly why that trade is real and why caching (Redis) exists to soften it.

10 · Limitations

This is a deliberately simplified model. Know its edges before you over-trust it.

Real CPUs are far more complex than fetch-decode-execute
Modern cores pipeline, execute out of order, predict branches and speculate. The simple loop is a true mental model, not an accurate microarchitectural one. You rarely need the details — until you profile very hot code.
The latency numbers are order-of-magnitude, and they move
Exact figures vary by chip, generation and vendor, and improve over time. Trust the ratios and their stability, not the specific nanoseconds.
NUMA and multi-socket effects are ignored
On big machines, memory is not uniformly fast from every core (non-uniform memory access). Irrelevant on your 1-vCPU box; real on the 64-core host it lives on.
The cloud abstracts the hardware on purpose
You usually cannot know which physical CPU or disk you are on, and it can change under you (live migration). The model tells you what is possible; the provider decides specifics.
Serverless and managed services hide it further
With Lambda/Cloud Run or a managed database, you may never pick an instance at all. The hardware is still there and still bound by this table — you have simply delegated the sizing. Knowing the model is how you keep those services from being black boxes.

11 · Common Misconceptions

"1 vCPU means one whole CPU (or one whole core) that's always mine."

A vCPU is usually a single hardware thread (half of one physical core's throughput, via hyper-threading), and on shared/burstable types it is only a scheduled share of that thread — you get it when the hypervisor grants it. "2 vCPU burstable" and "2 vCPU dedicated" can perform very differently under sustained load. Read the fine print about burst credits and dedicated vs shared.

"More GHz always means faster."

Clock speed is one factor. Work-per-second also depends on instructions per cycle, core count, cache sizes, and — most often — whether the CPU is even the bottleneck. A 3.5 GHz core waiting on a database is no faster than a 2.5 GHz one waiting on the same database. Find the bottleneck before optimising the clock.

"RAM and disk (storage) are basically the same kind of memory."

They differ on two axes that matter constantly: speed (RAM is ~100–1000× faster) and volatility (RAM is wiped on power loss; disk persists). "8 GB of memory" and "256 GB of storage" describe completely different things. Anything you must not lose has to reach the disk; anything you are actively working on lives in RAM.

"The cloud means there are no physical servers anymore."

"The cloud is just someone else's computer." Every instance runs on a real physical machine with real CPUs, RAM, disks and NICs in a real building. The cloud abstracts ownership and provisioning, not the hardware. The physics of the latency table is unchanged and inescapable.

"SSDs are so fast now they're basically as good as RAM."

Fast SSDs are ~20–100 microseconds; RAM is ~100 nanoseconds — a 100–1000× gap that the human-time column renders as "5 hours vs 1.5 minutes." SSDs are transformative compared to spinning disks, but the RAM→SSD cliff is still one of the largest in the table, which is exactly why in-memory caches exist.

"My VM is a whole computer that's fully isolated from everyone else."

It is logically isolated (you can't see other tenants' data), but it is physically shared — you contend for the same cores, caches, disk and network. That contention is the noisy-neighbour effect, and it is why the same instance can be fast one hour and slow the next with no change on your side.

"If the app is slow, I need a faster CPU / more vCPUs."

Usually not. Most web workloads are I/O-bound — waiting on the database, disk or network — not CPU-bound. Adding vCPUs to an I/O-bound app buys nothing; you must first identify which of the four resources is the actual limit (Module 12's job). "Slow" is a symptom with at least three different diseases.

12 · Practical Use Cases

Sizing your first box

For the course project — a small React/Express/Postgres/Redis app — the $5 tier (1 vCPU, 1 GB) is a deliberate, instructive choice: it is enough to run everything, and tight enough that you will feel RAM as the constraint and have to reason about it. That discomfort is the point; it teaches capacity thinking that a giant box would hide.

Choosing burstable vs dedicated

A personal project, a low-traffic internal tool, a staging box: burstable is ideal — cheap, and your rare spikes are covered by credits. A service under sustained CPU load (video processing, a busy API doing real computation): dedicated, or you will hit the credit cliff in production. Match the instance's CPU personality to your load's shape, not just the vCPU count.

Naming the bottleneck before spending money

When something is slow, resist "make it bigger." Ask which resource is saturated: CPU near 100 % (compute-bound → more/faster CPU or better algorithms), RAM full and swapping (memory-bound → more RAM or smaller working set), disk at its IOPS cap (I/O-bound → faster disk or caching), or network saturated (bandwidth/latency → caching, closer regions, a CDN). Each disease has its own cure; the model tells them apart. You will do this for real with metrics in Module 12.

Reading any pricing page in ten seconds

Scan for the four numbers (vCPU, RAM, storage type+size, network), then find the three catches: is the CPU shared/burstable, are the IOPS capped, and is network transfer metered? Those three footnotes are where the surprises — and the real cost differences between look-alike instances — hide.

13 · Summary

  • "Server" means three things — a software role, a physical machine, and a rented instance. Always know which one is meant.
  • Every server is four parts: CPU (executes instructions), RAM (fast volatile working memory), disk (slow durable storage), NIC (the link to the network). Each can independently be the bottleneck.
  • A CPU repeats fetch→decode→execute billions of times a second; cores give real parallelism, threads (SMT) give a partial boost, and a rented vCPU is usually one hardware thread — often only a scheduled share of one.
  • The memory hierarchy spans nine orders of magnitude in latency. Every step down (register → cache → RAM → SSD → network) is ~10–100× slower. This table is the root of nearly all performance reasoning.
  • RAM is finite and volatile: exceed it and the OS swaps or the OOM killer strikes; lose power and it's gone — so durable data must reach the disk.
  • Disk is three numbers (latency, IOPS, throughput) plus durability — not one. Cloud disks cap IOPS, and hitting the cap looks like a mystery slowdown.
  • The NIC is the request path's on-ramp; talking to anything remote is the slowest thing in the table, which is why caching and data locality dominate design.
  • On one real request, "your code" is nearly free; the request mostly waits on the database's disk or the network. "Slow" usually means "waiting", not "computing".
  • A hypervisor time-slices one physical host into many VMs/instances, sharing real CPU/RAM/disk/NIC — enabling the cloud, at the cost of noisy neighbours, CPU steal, and burstable-credit cliffs.
  • You can now read 1 vCPU / 1 GB / 25 GB SSD / 1 TB as a set of real limits — RAM-first, shared CPU, quota'd disk and network — which explains most of the operational surprises in the modules ahead.

16 · Quiz

How to use this

Answer in your own words before revealing the model answer. Two or three sentences each. You're ready for Lesson 2.2 (what the operating system does with this hardware) when you can answer Q1, Q3, Q5 and Q7 cold and have completed E1 and E2 on a real machine.

Name the four core components of a server and, in one phrase each, what each is for.

CPU — executes instructions (does the work). RAM — fast, volatile working memory holding what's currently running. Disk — slow, durable storage that survives power loss. NIC — the network link to everything off the machine. Each can independently be the bottleneck, which is why "the server is slow" is never a complete diagnosis.

Explain the difference between RAM and disk on the two axes that matter, and give one consequence of each difference.

Speed: RAM (~100 ns) is roughly 100–1000× faster than even a fast SSD (~20–100 µs) — consequence: hot data is cached in RAM to avoid the disk cliff. Volatility: RAM is wiped on power loss, disk persists — consequence: anything you must not lose (a database's data) has to be written to disk; "it was in memory" is never durability.

Why does the memory hierarchy exist at all — why not just make everything as fast as registers?

Because fast memory is small and extremely expensive per byte, and slow memory is large and cheap. You cannot afford terabytes of register-speed memory, and the CPU is far faster than affordable large memory. The hierarchy is a compromise: keep a little very-fast memory close to the CPU (registers, caches) holding the hottest data, backed by progressively larger, slower, cheaper layers. Caching works because programs reuse the same data (locality).

Using the latency table, explain why a database query to another server in the same datacenter is "expensive" even though it's fast in human terms.

A same-datacenter round trip is ~0.5 ms. That sounds tiny, but compared to a RAM read (~100 ns) it is roughly 5,000× slower, and compared to a CPU operation it is millions of cycles the machine spends waiting. In the human-time scaling (1 ns → 1 s), it's ~6 days versus ~1.5 minutes for RAM. So in a request that otherwise runs in nanoseconds, the network query dominates the total time — which is why caching results in RAM (e.g. Redis) is so effective.

What is a vCPU, really? Why can two instances both advertising "2 vCPU" perform very differently?

A vCPU is the unit of CPU you rent — usually a single hardware thread (via SMT/hyper-threading), which is roughly half a physical core's throughput, and on shared/burstable types only a scheduled share of that thread. Two "2 vCPU" instances differ because one may be burstable (a low baseline plus CPU credits that deplete under sustained load, then throttle hard) while the other is dedicated (continuous access). Same spec-sheet number, different behaviour under sustained load.

Your app is "slow." Name the three main hardware suspects and how you'd distinguish them.

CPU-bound: CPU near 100 % — the machine is computing flat out (fix: faster/more CPU, better algorithms). Memory-bound: RAM full and the system swapping to disk, or the OOM killer firing (fix: more RAM or a smaller working set). I/O-bound: CPU low but requests waiting, disk at its IOPS cap or the network saturated (fix: faster disk, caching, closer regions). You distinguish them with metrics (Module 12) — CPU utilisation, memory/swap usage, disk IOPS/latency, network throughput — not by guessing. Most web apps are I/O-bound.

What is a hypervisor, and what does it enable and cost?

A hypervisor is software that divides one physical machine into many isolated virtual machines, time-slicing the real CPU and partitioning the real RAM/disk/NIC among them. It enables the cloud: high utilisation (idle capacity resold to other tenants), per-hour rental, fast provisioning, and spreading copies across hosts. It costs a little overhead and, more importantly, introduces sharing — noisy neighbours, CPU steal, and burstable-credit throttling — because you no longer have the physical machine to yourself.

Decode "1 vCPU, 1 GB RAM, 25 GB SSD, 1 TB transfer" — which resource is the likely first constraint for a small web app, and why?

RAM (1 GB) is the likely first constraint. The OS itself consumes a few hundred MB, leaving only a few hundred for your app plus a database plus a cache — so you can hit the OOM killer well before you exhaust the CPU, the 25 GB SSD (ample for a small app) or the 1 TB transfer (generous unless serving large files). The vCPU is a shared thread and will be your ceiling under real CPU load, but for a typical small app memory pressure bites first.

Someone says "the cloud means there are no more physical servers." Correct them.

Every cloud instance runs on a real physical machine — CPUs, RAM, disks, NICs — in a real data centre; "the cloud is just someone else's computer." What the cloud abstracts away is ownership and provisioning: you rent a hypervisor-managed slice by the hour instead of buying and racking hardware. The physics of the latency table and the four components is entirely unchanged and inescapable.

Why is "add more vCPUs" often the wrong fix for a slow web service?

Because most web services are I/O-bound, not CPU-bound — the request spends its time waiting on the database, disk, or network, not computing. Adding vCPUs to a workload that isn't CPU-limited buys nothing; the extra cores sit idle while requests still wait on the same slow database. You must identify the actual saturated resource first (CPU vs memory vs disk IOPS vs network) and relieve that one. Scaling the wrong resource costs money and fixes nothing.
