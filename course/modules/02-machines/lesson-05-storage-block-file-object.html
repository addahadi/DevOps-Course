Module 2 · Lesson 2.5

Storage: block vs file vs object, filesystems, inodes, IOPS and durability

Lesson 2.4 ended with two loose threads that both fell off the edge of RAM and landed on the disk: swap lives on a disk, and the page cache is RAM standing in for a disk. This lesson is that disk — the fourth and last of Lesson 2.1's hardware parts, and the one that keeps your data alive when the power dies. We start at raw spinning platters and flash cells, build up through the block device, the filesystem, and the inode, and finish at the three storage models — block, file and object — you will actually rent from a cloud. Along the way we answer the questions that decide whether DevBoard loses a customer's data: what an IOPS number really buys you, why your database begs the kernel for fsync, and why "the write returned successfully" is not the same sentence as "the data is safe."

~75 min read Prerequisites: Lessons 2.1–2.4 Conceptual · hands-on at the end Module 2 · Milestone 2
Learning objectives

By the end of this lesson you will be able to:

  1. Distinguish a block device from a filesystem from a file, and explain what each layer adds on top of the one below it.
  2. Explain what an inode is, why a filename is not a file, and how hard links, directories and "no space left" despite free bytes all fall out of that one fact.
  3. Describe the write path from your write() call to durable media — the page cache, dirty pages, write-back, fsync, the drive's own cache, and the flush — and pinpoint exactly where data can be lost.
  4. Define durability precisely, distinguish it from availability, and reason about what RAID, replication and backups each do and do not protect against.
  5. Read a storage spec sheet: IOPS, throughput (MB/s), latency, block size and queue depth — and predict which one bottlenecks your database.
  6. Choose between block, file and object storage for a given job, and explain what a cloud provider is really selling under each name (EBS, EFS/NFS, S3).
Where this sits on the map

This closes Module 2's tour of the four hardware resources named in Lesson 2.1: CPU (2.3, shared in time), RAM (2.4, shared in space), and now storage — shared, addressed and made to survive. It is the direct sequel to 2.4: the page cache you met there is the same buffer that makes disk writes feel fast and disk writes risky here, and every major fault from swap was a trip to the device this lesson describes. It hands forward to Module 3 (the Linux filesystem hierarchy and "everything is a file" are the inode idea made into a user interface), to Module 6 (cloud block, file and object storage, and their price/IOPS trade-offs), and to Module 8, where DevBoard's PostgreSQL is entrusted with real data on a real volume and fsync stops being trivia.

1 · Problem Statement

Return one final time to the $5 box from Lesson 2.1. It has a CPU (shared in time, Lesson 2.3) and RAM (shared in space, Lesson 2.4) — but RAM is volatile: cut the power and every byte in it vanishes. DevBoard's entire reason to exist is the opposite of that. A user creates a task, closes their laptop, flies across an ocean, and expects the task to still be there next week — through reboots, deploys, crashes and a power outage in the data centre. That expectation is called persistence, and it is the whole job of storage: hold data on a medium that keeps it without power, and keep holding it correctly for years.

Persistence sounds simple until you try to build it honestly. A disk is, at bottom, an enormous but utterly dumb array of numbered fixed-size slots. It knows nothing of files, folders, users or your customer's task; it can only "store these bytes in slot 91,442" and "give me back the bytes in slot 91,442." Between that brute array and DevBoard's tasks.json or a Postgres row sits a tower of questions, none of which the hardware answers for you:

  • "A disk is millions of anonymous numbered slots. How do I turn that into named files in folders, growable and deletable, that I can find again by path?"
  • "My file is 10 MB but the free space on the disk is scattered in fragments. How does one file get assembled from slots all over the disk, and how does the system remember which slots belong to it?"
  • "The disk is thousands of times slower than RAM (Lesson 2.1's latency ladder). If every write waited for the platter, DevBoard would crawl. How do we make it fast — and what do we risk by doing so?"
  • "When my code calls write() and it returns success, is the data actually safe on the disk — or just sitting in a buffer that a power cut would erase? Who guarantees it, and how do I force the guarantee when it matters?"
  • "Disks fail. Not 'might' — will. How do I keep data alive when the physical device it lives on dies, and why isn't a copy on the same machine enough?"
  • "The cloud sells me 'a volume', 'a shared filesystem' and 'a bucket' at wildly different prices. What am I actually renting under each, and which one fits a database vs an upload vs a log archive?"
The core problem

A raw storage device is a flat array of fixed-size, anonymous, numbered blocks with two operations — read a block, write a block — and one dangerous property: it is slow, and it can lie about being done. From that we must build, in order, an organised system (named files and directories laid out over scattered blocks), a fast one (buffered in RAM so the slow device isn't on the critical path of every operation), a correct one (survives crashes without corrupting itself, and lets an application force data to durable media when correctness demands it), and a durable one (survives the physical death of the device itself). Each layer we add — block device, filesystem, page cache, journal, replication — buys one of those properties and imposes a cost. This lesson is that stack, bottom to top, and the vocabulary to reason about every storage decision DevBoard will ever face.

The promise of this lesson: by the end, "I saved the file" will stop being one act and resolve into a precise pipeline — application, page cache, dirty page, write-back, filesystem, block layer, device cache, media — and you will be able to point at the exact link in that chain where a power cut costs you data, the exact spec number that caps your database's throughput, and the exact reason a single-machine copy is not a backup.

2 · Historical Context

Storage abstractions, like memory ones, were assembled by adding one layer at a time, each hiding a pain the previous layer exposed. The through-line is a steady retreat from physical geometry: early programmers addressed storage by its shape; today you address a URL and a provider hides an ocean of disks behind it.

1950s–1960s · Addressing storage by its physical geometry

The first disks were addressed the way they were built: by cylinder, head and sector (CHS) — literally "which track, which platter surface, which slice." A program had to know the drive's physical dimensions to find its data. There was no filesystem; a program owned raw regions of the disk and remembered their locations itself. Storage was geometry, and every program re-invented its own bookkeeping.

1960s–1970s · The filesystem: names instead of numbers

Operating systems introduced the filesystem: a layer that let programs refer to named files and gave the OS the job of tracking which physical blocks held each one. Unix (1969 onward) crystallised the model that still rules today — the inode (a small record describing one file: its size, owner, permissions and the list of blocks holding its data), directories as just files that map names to inode numbers, and the radical simplification "everything is a file," so that devices, pipes and terminals all wore the same read/write interface. This is the layer you meet in Module 3, and its inode is the heart of §6.

1970s–1980s · The block device abstraction

The kernel grew a clean internal boundary: the block device. Above it, the filesystem thinks in fixed-size numbered blocks and never touches hardware; below it, a driver translates "read block N" into whatever the specific disk requires. This decoupling is why the same ext4 filesystem runs unchanged on a 1980s spinning disk, a modern SSD, a USB stick, a RAID array, or a cloud volume that is really software pretending to be a disk. The filesystem stopped caring what the storage physically was — the same decoupling move virtual memory made for RAM in Lesson 2.4.

1980s–1990s · RAID and the durability problem

As businesses put critical data on disks that failed regularly, the 1987 Berkeley RAID (Redundant Array of Inexpensive Disks) paper formalised combining many cheap disks into one logical device that survives a disk death — by mirroring or by parity. This is the moment the field separated two ideas that beginners still conflate: making storage fast/big and making it survive failure. RAID is §6's durability story in hardware.

2000s · Flash and the end of "disk = spinning platter"

Solid-state drives (SSDs) replaced spinning platters with flash memory, collapsing random-access latency by orders of magnitude and destroying the old intuition that random I/O is catastrophically slower than sequential. But flash brought its own quirks — it wears out, it can't overwrite in place, it needs garbage collection — which is why the IOPS and write-endurance numbers in §6 exist and why cloud disks are priced the way they are.

2006 · Object storage and the cloud

Amazon S3 (2006) introduced object storage at planetary scale: not files on a filesystem you mount, but named objects in flat buckets, reached over HTTP, with durability quoted in eleven nines and effectively unlimited capacity. It abandoned the filesystem interface entirely to win scale and durability. Today your storage decision is usually a choice among three cloud products — a block volume, a shared file service, and an object store — each descended from one of the layers above, and §5–6 give you the model to choose correctly.

3 · The Previous Solution (in detail)

To feel what the filesystem-and-page-cache stack buys you, look hard at the honest alternative: an application talking directly to a raw block device, managing its own on-disk layout, with no filesystem and no caching underneath. This is not a straw man — high-end databases genuinely run on "raw devices" for exactly this control, and understanding it shows you precisely which jobs the filesystem is doing on your behalf.

The model, stated plainly:

RAW-BLOCK-DEVICE MODEL  (application owns the disk, no filesystem)

  A block device = a flat array of fixed-size blocks (say 512 B or 4 KB):

    block:  0      1      2      3      4      5     ...   N
          ┌──────┬──────┬──────┬──────┬──────┬──────┬─────┐
          │      │      │      │      │      │      │ ... │
          └──────┴──────┴──────┴──────┴──────┴──────┴─────┘
    ops:  read_block(n) -> bytes      write_block(n, bytes)

  · No names. No folders. No "grow this file." Just numbered slots.
  · The APPLICATION must remember: my data lives in blocks 40..87,
    my index in 88..91, and free space is 92..N.
  · Every write goes straight to the slow device — no buffering.

The assumptions this model bakes in:

The application is the bookkeeper
There is no OS-provided map from a name to a set of blocks. The program itself must track which blocks hold which data, which are free, and how to grow a region — reinventing a filesystem, badly, inside every application.
No sharing between programs
Two programs on the same disk have no common notion of "files," so they cannot coordinate. One program's blocks are invisible to another except by out-of-band agreement. The disk is owned, not shared.
Every access hits the device
With no cache in the middle, every read and every write pays the full device latency (Lesson 2.1's ladder), even when the same block is touched a thousand times a second.
Durability is all-or-nothing and manual
The application alone decides ordering and gets no crash-consistency help: a power cut mid-update can leave its private on-disk structures in a state only it knows how to (or fails to) repair.

And it genuinely works — a database that wants total control over layout and caching (it has its own buffer pool and its own crash-recovery log) can run faster on a raw device precisely because the filesystem isn't second-guessing it. Its virtue is control. But that virtue is only affordable to a team that will build the filesystem's services themselves. For everyone else — every ordinary program that just wants to open tasks.json and read it — this model is a catastrophe: it forces every application to become a storage engine. The next section is exactly why that fails.

4 · Why It Failed

Push the raw-block model onto ordinary software sharing one machine and each of its assumptions turns into a concrete failure. These are the pains the filesystem, the page cache and the journal were invented to erase.

4.1 Every program must reinvent a filesystem

Without a shared naming-and-layout layer, each program has to track its own blocks, free lists and growth by hand. This is enormous, subtle, security-critical code — allocation, fragmentation, corruption recovery — that has nothing to do with the program's actual job. Multiply it across every application on the machine and you have thousands of buggy, incompatible mini-filesystems. The waste and the bug surface are both intolerable.

4.2 Programs can't share, and humans can't navigate

With only numbered blocks, there is no way for two programs to agree on "the file at /etc/nginx/nginx.conf," and no way for a human to list, find, move or reason about what is on the disk. There are no directories, no paths, no permissions. Collaboration between programs and administration by people both become impossible. A shared machine needs a shared namespace, and raw blocks provide none.

4.3 Raw device speed is unusable for real workloads

A disk is thousands of times slower than RAM. A program that reads the same configuration block, or appends to the same log, or re-reads a hot index, would pay full device latency every single time. Interactive software would be unbearable. The obvious fix — keep recently-used blocks in RAM — is itself a whole caching subsystem no application should have to build, and if every application built its own, they would fight over RAM and cache the same blocks many times.

4.4 Crashes corrupt structure, silently

Updating any on-disk structure usually means writing several blocks. A power cut between them leaves the structure half-updated — a directory pointing at a block that was never written, a free list that thinks a used block is free. With no crash-consistency mechanism, the disk comes back corrupt, and the only recovery is a full scan-and-guess (the historical fsck) that can take hours and still lose data. Correctness under crash is not something an application should have to solve alone.

The pattern behind all four failures

Every failure traces to one root cause: the raw device offers no shared abstraction between the dumb block array and the program's need for named, safe, fast, shareable storage. The fix is to insert exactly such a layer into the kernel — one, built once, correct once, used by everyone — that maps names to blocks (the filesystem, so no program reinvents layout and humans get paths), buffers blocks in RAM (the page cache, so the slow device leaves the critical path), and makes updates crash-consistent (the journal, so a power cut can't corrupt structure). That layered stack — block device → filesystem → page cache → application — is the whole of §5.

5 · The New Solution

The solution is a layered stack, each layer hiding the one below and adding exactly one capability. Definitions first — these are the working vocabulary for the rest of the lesson, for Module 3's Linux filesystem, and for Module 6's cloud storage.

5.1 The core vocabulary

Block / sector
The smallest unit the storage device reads or writes at once — historically a 512-byte sector, now typically 4 KB. You cannot read or write half a block; it is atomic at the hardware level. Everything above is built out of blocks.
Block device
The kernel's abstraction of "a thing you can read and write in fixed-size blocks, addressed by block number." A hard disk, an SSD, a partition, a USB stick and a cloud volume all present as block devices (/dev/sda, /dev/nvme0n1 on Linux). The layer that lets one filesystem run on any medium.
Filesystem
The software layer (ext4, XFS, Btrfs, ZFS, NTFS, APFS…) that turns a block device's flat block array into named files and directories — deciding which blocks hold which file, tracking free space, and enforcing permissions. It is formatted onto a block device (mkfs) and mounted at a path to become usable.
Inode
The filesystem's record for one file: its metadata (size, owner, permissions, timestamps) and the pointers to the data blocks that hold its contents. Crucially, the inode does not contain the filename. The number of inodes is usually fixed when the filesystem is created.
Directory
Just a special file whose contents are a list mapping names to inode numbers. "A folder" is a table of (name → inode). This is why a filename is a label pointing at a file, not the file itself.
Page cache
The same RAM cache from Lesson 2.4: the kernel keeps recently-read and about-to-be-written file blocks in memory, so repeated access is served at RAM speed and writes can be batched. It sits between the application and the block device and is why disk I/O usually feels fast.
Dirty page & write-back
A page in the cache that has been written to but not yet saved to the device is dirty. The kernel flushes dirty pages to storage later, in the background — write-back. This is the speed win and the durability risk of §6.
fsync
The system call an application makes to say "do not return until this file's data is actually on durable media." It forces the write-back the kernel would otherwise defer, and is how a database guarantees a committed transaction survives a crash.
Journal
A reserved area where the filesystem first records what it is about to do before doing it, so that after a crash it can replay or discard partial operations and come back consistent — instead of scanning the whole disk. The crash-consistency mechanism that killed the multi-hour fsck.
The one sentence to hold onto

Storage is a stack: a dumb block device exposes numbered fixed-size blocks; a filesystem maps human names to sets of those blocks via inodes; the page cache buffers blocks in RAM so the slow device leaves the critical path; and fsync plus the journal let you trade that speed back for the guarantee that data is durable and structure is consistent after a crash. Almost every storage behaviour in this lesson — fast writes, lost writes on power failure, "no space left" with free bytes, the block/file/object split — is a consequence of that stack.

5.2 The shape of the solution

Each layer speaks only to its neighbours. Your application says "write these bytes to this file"; it never names a block. The filesystem translates the file and offset into block numbers. The page cache answers from RAM when it can and defers writes. The block layer schedules the actual device I/O. The device stores bytes on media: 

THE STORAGE STACK  ("each layer adds one capability")

  ┌─────────────────────────────────────────────────────────────┐
  │  APPLICATION      open("/data/tasks.json"); write(fd, buf)   │  names + bytes
  ├─────────────────────────────────────────────────────────────┤
  │  FILESYSTEM       name → inode → which blocks; permissions;  │  organisation
  │  (ext4 / XFS …)   free-space tracking; journal for crashes    │  + consistency
  ├─────────────────────────────────────────────────────────────┤
  │  PAGE CACHE       recently used blocks kept in RAM;           │  speed
  │  (kernel)         writes buffered as "dirty" pages            │  (+ durability risk)
  ├─────────────────────────────────────────────────────────────┤
  │  BLOCK LAYER      schedules/queues read/write of block N      │  device-independence
  ├─────────────────────────────────────────────────────────────┤
  │  DEVICE DRIVER    turns "block N" into this hardware's cmds   │
  ├─────────────────────────────────────────────────────────────┤
  │  MEDIA            SSD flash cells / HDD platters (+ own cache)│  persistence
  └─────────────────────────────────────────────────────────────┘

  Read: often answered by the page cache (RAM) — never reaches media.
  Write: lands in the page cache (fast return); reaches media LATER,
         unless the app calls fsync() to force it NOW.

Now re-answer §1's questions, one line each. Numbered slots into named files? The filesystem maps a path through a directory to an inode to a set of blocks — organisation. A 10 MB file from scattered slots? The inode holds a list of block pointers that can point anywhere on the device — no contiguity needed. Slow disk made fast? The page cache serves reads from RAM and buffers writes — speed. Is a returned write() safe? Not until it leaves the page cache; fsync forces it — durability on demand. Surviving a dead device, and what the cloud sells, are §6.6 and §6.8. The layered stack answers nearly all of them, and each answer names the exact place a failure can hide.

6 · Internal Mechanics

Now the machine in motion. We will (6.1) look inside the media — HDD vs SSD — because the physics sets the numbers; (6.2) dissect the inode and see filenames, links and directories fall out of it; (6.3) watch a path resolve to data blocks; (6.4) walk the write path from write() to media and find where data dies; (6.5) explain fsync, journals and crash consistency; (6.6) define durability and how RAID and replication provide it; (6.7) decode the performance numbers — IOPS, throughput, latency; and (6.8) split storage into block, file and object.

6.1 What the media actually is: HDD vs SSD

Storage physics sets every number you will later pay for, so start at the media. A hard disk drive (HDD) stores bits as magnetic regions on spinning platters, read by a head on a moving arm. To reach a given block, the arm must seek to the right track and then wait for the platter to rotate the block under the head — mechanical motions measured in milliseconds. This is why HDDs are savage at random access (each access pays a seek) but decent at sequential access (one seek, then stream). A solid-state drive (SSD) stores bits in flash cells with no moving parts; any block is reachable in microseconds, so random access is only modestly slower than sequential. That single difference — moving arm vs electronics — is why an SSD can do tens of thousands of random operations per second and an HDD only a couple hundred, and why the old rule "sequential is far faster than random" is decisive on HDDs and merely a nudge on SSDs. Flash has its own catch: a cell must be erased (in large blocks) before it can be rewritten, and it wears out after many writes, so SSDs constantly shuffle data (wear levelling, garbage collection) behind the scenes — the reason write-endurance appears on their spec sheets.

6.2 The inode: why a filename is not a file

The inode is the hinge of the whole filesystem, and the single idea that explains a dozen puzzling behaviours. An inode is a small fixed record describing exactly one file's contents and metadata — everything except its name: 

  INODE #4412 (one file)                 DIRECTORY /data (itself a file)
  ┌───────────────────────────┐          ┌──────────────────────┬────────┐
  │ type: regular file         │          │ name                 │ inode  │
  │ permissions: rw-r--r--     │          ├──────────────────────┼────────┤
  │ owner / group: deploy      │          │ tasks.json           │ 4412   │
  │ size: 10 MB                │◀─────────│ tasks.bak            │ 4412   │ ← hard link!
  │ timestamps: atime/mtime…   │          │ notes.txt            │ 5001   │
  │ link count: 2              │          └──────────────────────┴────────┘
  │ block pointers ─────────┐  │
  └─────────────────────────┼──┘   the NAME lives in the directory,
        ▼   ▼   ▼   ▼        ▼      the FILE lives in the inode.
     [blk 91][blk 4][blk 77][blk 200] ... (data, scattered across the device)

Read the diagram and the puzzles dissolve. A filename lives in a directory, not in the file — a directory is just a table of (name → inode number). So a hard link is simply a second directory entry pointing at the same inode: two names, one file, one copy of the data; the inode's link count tracks how many names point at it, and the data blocks are freed only when that count hits zero. This is why "deleting" a file is really unlink — you remove a name, and the data survives if another name still references it, or if a running process still holds the file open (the classic "I deleted the huge log but the disk is still full" from Lesson 2.4's neighbourhood). It is also why renaming or moving a huge file within one filesystem is instant: you only rewrite a directory entry, never the data. And it is why a filesystem can run out of inodes while gigabytes of space remain — millions of tiny files exhaust the fixed inode table even though the data blocks are mostly empty, producing the infamous "No space left on device" with df showing free bytes but df -i showing 100% inodes used.

6.3 Resolving a path to data

Opening /data/tasks.json is a walk down the inode/directory structure, one component at a time, starting from a known fixed inode for the root: 

  open("/data/tasks.json")
    │
    ├─ start at ROOT inode (a directory; its inode number is fixed, e.g. 2)
    ├─ read root's data → find entry "data" → inode 300
    ├─ read inode 300 (a directory) → find entry "tasks.json" → inode 4412
    ├─ read inode 4412 (a regular file) → check permissions for this user
    └─ now reads/writes use inode 4412's block pointers to find the bytes
          read(offset 0..4096) → block pointer[0] → block 91 → (page cache or device)

Every component of the path is a directory lookup; every lookup is itself a small file read (usually already cached). This is what "everything is a file" buys you in Module 3, and why deep paths and huge directories have a measurable cost. Once the file is open, the kernel hands your program a small integer — a file descriptor — that indexes into the block pointers, so subsequent reads and writes skip the path walk entirely.

6.4 The write path: where your data actually goes (and dies)

This is the most consequential mechanism in the lesson. When your code calls write(fd, buf, n), the bytes do not go to the disk. They are copied into the page cache in RAM, the page is marked dirty, and write() returns success almost immediately — at RAM speed. The data is now safe against your program crashing (it lives in the kernel, not your process) but not against the power failing, because it is still only in volatile RAM. Some time later — seconds, by default — the kernel's write-back flushes the dirty page to the block device. And even then, many devices have their own volatile write cache, so the bytes may sit in the drive's buffer before finally reaching durable flash or platter: 

  write(fd, buf, n)
     │  copy bytes into RAM
     ▼
  [ PAGE CACHE ]  page marked DIRTY   ── write() RETURNS here (fast!) ──▶ your code continues
     │            (safe from process crash · NOT safe from power loss)
     │  kernel write-back, later (or on fsync now)
     ▼
  [ BLOCK LAYER → DEVICE ]
     │
     ▼
  [ DRIVE'S OWN CACHE ]  (often volatile too!)  ── power loss here still loses data ──┐
     │  drive flush / FUA                                                              │
     ▼                                                                                 ▼
  [ DURABLE MEDIA ]  now, and only now, is the data truly safe        ✗ pull the plug
                                                                         anywhere above
                                                                         this line = data
                                                                         gone, even though
                                                                         write() said "ok"
The sentence that ruins careers

"write() returned successfully" means "the kernel accepted your bytes into RAM," not "the data is on the disk." Between that return and durable media sit the page cache and often the drive's own cache — both volatile. A power cut in that window loses data your program was told it had saved. This is not a bug; it is the deliberate trade that makes storage fast. The only way to close the window is to ask for it explicitly — fsync.

6.5 fsync, journals and crash consistency

Two different things can break in a crash, and they need two different fixes. The first is your data being lost in the cache — fixed by fsync(fd), which blocks until the file's dirty pages (and, on a correct system, the drive cache) have reached durable media, then returns. A database calls fsync (or O_DSYNC, fdatasync, and friends) at every transaction commit: that is precisely the moment it promises the user "your task is saved," so it must pay the full durable-write latency there and cannot defer it. The cost is real — an fsync can be milliseconds, thousands of times slower than the cached write — which is why database write throughput is often fsync-bound and why storage with fast durable-write latency is worth paying for.

The second thing that breaks is the filesystem's own structure. Creating a file touches several blocks — a new inode, updated free-space maps, a new directory entry — and a crash between them would leave the filesystem inconsistent (§4.4). The fix is the journal: the filesystem writes a description of the intended change to a reserved log first, and only then applies it. After a crash, the filesystem replays the journal (finish committed operations) or discards incomplete ones, returning to a consistent state in seconds instead of an hours-long fsck. Note the crucial distinction: the journal, by default, protects the filesystem's metadata (its structure), not necessarily your file's data — keeping the structure consistent is a separate guarantee from keeping your bytes, and only fsync gives you the latter.

6.6 Durability: surviving the death of the device

fsync gets your data onto one device. But devices die — an SSD wears out, a platter fails, a controller fries. Durability is the probability that data, once stored, is not lost over time, and it is a different axis from everything above: you can have perfect crash-consistency on a single disk and still lose everything when that disk dies. Surviving device death means keeping more than one copy on more than one device:

RAID (redundancy within one machine)
Combines several disks into one logical device that survives a disk failure. RAID 1 mirrors every byte onto two disks; RAID 5/6 spread data plus parity across many, so any one (or two) can die and be rebuilt. RAID buys availability through a disk failure — but it is not a backup: it faithfully replicates your rm -rf, a corrupting bug, or ransomware to every mirror instantly.
Replication (redundancy across machines)
Copies data to other machines, often in other racks, data centres or regions, so the loss of a whole server or site doesn't lose data. This is how cloud object stores reach "eleven nines" — every object is stored on many devices across many failure domains automatically.
Backups (redundancy across time)
Point-in-time copies kept separately, so you can recover from events that redundancy happily propagates: accidental deletion, corruption, a bad migration, a compromise. RAID and live replication protect against hardware failure; only backups protect against you and against logical damage. A copy that updates in lockstep with the original is not a backup.
Durability is not availability, and RAID is not backup

Keep three axes distinct. Availability is "can I reach the data right now" (a dead disk in a RAID array doesn't take you offline). Durability is "will the data still exist later" (survives device death via extra copies). Backups are the only thing that survives logical loss — deletion, corruption, attack — because redundancy replicates those faithfully. DevBoard needs all three, and Module 11 makes you run a real restore drill, because a backup you have never restored is a hope, not a backup.

6.7 The performance numbers: IOPS, throughput, latency

Storage performance is not one number, and confusing the numbers is how people buy the wrong disk. Three measurements matter, and different workloads are bounded by different ones:

IOPS (I/O operations per second)
How many separate read/write operations the device can complete per second. This is the number that matters for small, random I/O — exactly what a database doing many little row reads/writes does. An HDD does ~75–200 random IOPS (bounded by seek time); an SSD does tens of thousands to millions.
Throughput / bandwidth (MB/s)
How many bytes per second the device can move for large, sequential I/O — copying a big file, streaming a backup, a video. A workload can be nowhere near the IOPS limit yet saturate throughput, or vice versa.
Latency
How long a single operation takes to complete. This is what an fsync-per-commit database feels directly: even at high IOPS, if each durable write has high latency, transaction rate suffers. Sub-millisecond on good SSDs; milliseconds on HDDs and network storage.

The trap: IOPS and throughput trade off against block size. IOPS × block size ≈ throughput, so a device rated for huge sequential throughput can still choke on a database's tiny random operations, and a device with plenty of IOPS can still be slow for one latency-sensitive fsync. There is also queue depth — how many operations you keep in flight at once; devices (especially SSDs and network volumes) hit their rated IOPS only when fed many concurrent requests, so a single-threaded synchronous workload may see a fraction of the spec. When Module 6 quotes you a cloud volume at "3,000 IOPS, 125 MB/s," you will know that the first number caps your database's small random operations, the second caps your backups and log streaming, and neither tells you the per-operation latency your commits will feel.

6.8 Three storage models: block, file, object

Finally, the split that governs your cloud bill. The same underlying media is sold under three interfaces, each exposing a different layer of §5's stack:

Block storage
You rent a raw block device — a virtual disk. It has no filesystem until you put one on it; it attaches to one machine at a time; you get the lowest latency and full control. This is what a database's data directory lives on. Cloud examples: AWS EBS, GCP Persistent Disk, a DigitalOcean Volume. It is §5's block-device layer, sold directly.
File storage
You rent a ready-made filesystem you mount over the network, shared by many machines at once, with familiar paths and permissions (the NFS protocol underneath). Convenient for shared files across several servers; higher latency than block because it is network-hopped. Cloud examples: AWS EFS, GCP Filestore, plain NFS. It is §5's filesystem layer, sold as a shared service.
Object storage
You store whole objects (a blob of bytes + metadata) under a key in a flat bucket, reached over HTTP, not mounted as a disk. No filesystem, no partial in-place edits (you replace whole objects), effectively unlimited capacity, extreme durability via automatic cross-device replication, and low cost per gigabyte — at the price of higher per-request latency. Perfect for uploads, backups, static assets, logs. Cloud examples: AWS S3, GCP Cloud Storage, Cloudflare R2. It is the layer §2 said abandoned the filesystem entirely to win scale.

DevBoard uses all three, and correctly: PostgreSQL's data on a block volume (needs low latency and one owner); user-uploaded avatars and attachments in object storage (cheap, durable, served directly); and — if several app servers ever needed to share a directory — a file service, though good architecture avoids that by pushing shared state into the database and object store instead. Choosing the wrong model is a classic, expensive mistake: putting a database on network file storage makes it slow and fragile; trying to run a database on object storage is impossible; storing millions of uploads on a block volume is needlessly costly and caps you at one machine.

7 · Real Industry Examples

"The database was fast, then a deploy made it 50× slower"

A team moves PostgreSQL from a local SSD to a network file mount (or a cheap cloud volume with low IOPS) to "make storage shared and easy." Throughput on big reads looks fine, so the volume seems healthy — but every transaction commit is an fsync (§6.5), and each now pays network + low-IOPS latency instead of local-SSD microseconds. Write throughput collapses because it is fsync-latency-bound, not bandwidth-bound. The lesson tells you exactly which number to check (per-operation durable-write latency and IOPS, §6.7) and why the "shared and easy" file model (§6.8) is the wrong layer for a database.

"df says there's space, but writes fail with 'No space left on device'"

An application that creates millions of tiny files (a cache, a mail spool, session files) suddenly can't write, yet df -h shows plenty of free gigabytes. The culprit is inode exhaustion (§6.2): the fixed inode table is full even though data blocks are free. df -i shows 100% inodes used. Knowing the inode is a fixed-count resource separate from bytes turns a baffling outage into a one-command diagnosis.

"We had RAID, so we didn't need backups" — the sentence before the disaster

A team runs RAID 1 and feels safe. Then a bad migration (or an rm -rf, or a bug) corrupts the data — and RAID faithfully mirrors the corruption to both disks instantly (§6.6). RAID protected them from a disk dying; it did nothing against logical loss, which only backups (redundancy across time) survive. This exact conflation of availability, durability and backup causes real, permanent data loss, and it is why Module 11 makes a tested restore mandatory.

The "eleven nines" of object storage, and where the number comes from

When AWS S3 advertises 99.999999999% durability, that number is manufactured by exactly §6.6's mechanism at scale: every object is automatically replicated across many devices in multiple physical facilities, so the simultaneous loss of enough independent devices to destroy an object is astronomically unlikely. It is not magic hardware; it is redundancy across failure domains, priced so cheaply per gigabyte that it is almost always the right home for uploads, backups and logs — the object model of §6.8 doing what a single block volume never could.

10 · Limitations

The storage stack is not free, and its edges are where production surprises live.

The page cache makes writes a lie by default
The very buffering that makes I/O fast means a returned write() is not durable. Any code that must not lose data has to call fsync and accept the latency — and code that forgets will pass every test and lose data only during a real power failure, the worst time to learn this.
fsync is expensive and unavoidable where it matters
Durable writes cost milliseconds; a database that commits often is throughput-limited by fsync latency, no matter how much bandwidth the device has. You cannot cache your way out of a durability requirement.
The journal protects structure, not necessarily your data
Default filesystem journaling keeps metadata consistent after a crash but does not guarantee your file's contents survived — a subtlety that lulls people into thinking "journaled = safe." Only fsync protects your bytes.
RAID and replication are not backups
Redundancy across devices/sites survives hardware failure but faithfully propagates deletion, corruption and attacks. Confusing durability/availability with backup is a recurring cause of permanent data loss.
Spec numbers describe ideal conditions
Rated IOPS often require high queue depth and a specific block size; your real, latency-sensitive, single-threaded workload may see a fraction of it. And cloud volumes throttle or "burst" — sustained performance can be far below the headline number.
This is a simplified model
Real systems add copy-on-write filesystems (ZFS/Btrfs) with checksums and snapshots, LVM, encryption at rest, tiered/burst storage, SSD write amplification and TRIM, and distributed filesystems. The block→filesystem→cache picture is a true, load-bearing map — not the entire territory.

11 · Common Misconceptions

"If write() returned success, my data is safely on the disk."

No. The bytes are in the volatile page cache in RAM (§6.4); write() returns before they reach durable media. A power cut in that window loses data your program was told it saved. Only fsync (and a drive that honours flushes) guarantees durability — which is exactly why databases call it at every commit.

"A filename is the file."

A filename is a label in a directory pointing at an inode, which is the actual file (metadata + data-block pointers). That's why two names can point at one file (hard links), why "deleting" is unlink-ing a name, and why moving a huge file within a filesystem is instant — you only rewrite a directory entry, never the data.

"df shows free space, so I can always write more files."

Not if you're out of inodes (§6.2). The inode table is a fixed-count resource separate from data blocks; millions of tiny files can exhaust it while gigabytes of space remain, giving "No space left on device" despite free bytes. Check df -i, not just df -h.

"We have RAID (or a live replica), so our data is backed up."

RAID and replication protect against hardware failure by keeping copies in sync — and therefore instantly propagate deletion, corruption and ransomware to every copy. A backup is a separate point-in-time copy that survives logical loss. Availability, durability and backup are three different guarantees (§6.6); you need all three.

"More IOPS means my database will be faster."

Only if IOPS is your bottleneck. A commit-heavy database is often bound by per-operation fsync latency, not operation count; and a backup job is bound by throughput, not IOPS. IOPS, throughput and latency are distinct numbers (§6.7) — buying more of the wrong one changes nothing.

"Random and sequential access are basically the same speed now."

On SSDs the gap is small; on HDDs it is enormous, because each random access pays a mechanical seek (§6.1). Even on SSDs, tiny random I/O at low queue depth can fall well short of the rated throughput. The workload's access pattern still decides which spec number you actually hit.

"Object storage (like S3) is just a network drive I can mount and edit files on."

No. Object storage has no filesystem, no partial in-place edits, and higher per-request latency — you PUT and GET whole objects by key over HTTP (§6.8). It's ideal for uploads, backups and assets, and wrong for a database or anything needing a mounted filesystem with in-place updates. That's what block and file storage are for.

12 · Practical Use Cases

Choosing where each part of DevBoard's data lives

This lesson turns storage placement from guesswork into a decision. PostgreSQL's data directory goes on block storage (low latency, one owner, fsync honoured); user-uploaded attachments and avatars go in object storage (cheap, durable, served directly, unbounded); shared files across app servers — if ever truly needed — go on file storage, though you'll usually design that need away. Getting this right (§6.8) is the difference between a fast, cheap, durable system and a slow, fragile, expensive one.

Diagnosing a "full disk" that has free space

When writes fail with "No space left on device" but df -h shows room, you now check df -i for inode exhaustion (§6.2), and check for a deleted-but-still-open huge file (space not reclaimed until the last file descriptor closes). Two commands replace an afternoon of confusion.

Making a database's writes actually safe and fast enough

Understanding the write path lets you reason about the real levers: is the volume's durable-write latency low enough for your commit rate (§6.7)? Is the drive/volume honouring flushes so fsync means what it says? Should you batch commits to amortise fsync? These are the storage-side of Module 8's PostgreSQL work and Module 11's reliability work, and they all start from §6.4–6.5.

Designing a backup and restore strategy you can defend

Because you can now separate availability, durability and backup (§6.6), you can design deliberately: redundancy (RAID/replication) for hardware failure, off-box backups (ideally in object storage) for logical loss, and — the part everyone skips — a tested restore, because an unverified backup is a guess. This is exactly the restore drill Module 11 will make you run on DevBoard.

13 · Summary

  • Storage's job is persistence: hold data on media that survives power loss, correctly, for years. A raw device is only a flat array of numbered, fixed-size blocks with read-block/write-block — everything else is built on top.
  • Talking to the raw device directly forces every program to reinvent layout, blocks sharing and navigation, pays full device latency on every access, and corrupts silently on crashes (§4). The fix is a layered stack built once in the kernel.
  • The filesystem maps human names to sets of blocks via inodes. A filename is a directory entry pointing at an inode, not the file itself — which explains hard links, instant renames, unlink-style deletion, and inode exhaustion (df -i) despite free bytes.
  • The page cache buffers file blocks in RAM (the same cache from Lesson 2.4), serving reads at memory speed and letting writes return immediately as dirty pages flushed later. This is the speed win — and the durability risk.
  • A successful write() means "the kernel took your bytes into RAM," not "the data is on disk." Between it and durable media sit the page cache and often the drive's own volatile cache — a power cut there loses acknowledged data.
  • fsync is the only call that forces your bytes to durable media on demand; databases call it at every commit and are often fsync-latency-bound. The journal keeps the filesystem's structure crash-consistent — but protects metadata, not necessarily your data.
  • Durability (data survives device death) is a different axis from availability (reachable now). Extra copies across devices (RAID) and machines (replication) give both — but neither is a backup: only point-in-time copies survive deletion, corruption and attack.
  • Performance is three numbers, not one: IOPS (small random ops — databases), throughput MB/s (large sequential — backups/streaming), and latency (a single op — felt by every fsync). Queue depth and block size decide which you actually hit.
  • The cloud sells the same media as three models: block (a raw disk, one machine, lowest latency — for databases), file (a shared network filesystem — for genuinely shared directories), and object (HTTP buckets, huge scale and durability — for uploads, backups, assets).
  • This closes Module 2's four resources: CPU (2.3), RAM (2.4), and storage (2.5). Every one of these — inodes, the write path, fsync, block/file/object — returns in Module 3 (Linux), Module 6 (cloud), Module 8 (PostgreSQL) and Module 11 (reliability).

mkdir ~/storage-lab && cd ~/storage-lab

E3Feel the page cache: the second read is free

# make a ~500MB file
dd if=/dev/zero of=big.bin bs=1M count=500
# (optional, needs root) drop caches so the first read is cold:
sync; echo 3 | sudo tee /proc/sys/vm/drop_caches

time cat big.bin > /dev/null    # WARM: served from the page cache (RAM)

E4Watch the write path: buffered vs durable (fsync)

See the difference between a returned write and a durable one:

# buffered write returns almost instantly (lands in page cache):
time dd if=/dev/zero of=buffered.bin bs=1M count=200
# force every write to durable media (fsync at the end):
time dd if=/dev/zero of=synced.bin bs=1M count=200 conv=fdatasync
# or oflag=sync to sync every block — even slower

Compare the times. Explain, using §6.4–6.5, why the plain dd returns faster (data is in the volatile page cache) and why the fdatasync/sync version is slower but actually durable — and what this implies for a database calling fsync at every commit.

16 · Quiz

How to use this

Answer in your own words before revealing the model answer. Two or three sentences each. You've finished Module 2 when you can answer Q1, Q3, Q4 and Q7 cold and have completed E1–E4 on a real machine.

Distinguish a block device, a filesystem and a file. What does each layer add?

A block device is the raw abstraction of storage: a flat array of numbered, fixed-size blocks with read-block/write-block, and nothing else — no names, no folders. A filesystem is the software layer formatted onto a block device that maps human names (paths, via directories and inodes) to sets of blocks, tracks free space, and enforces permissions. A file is one named unit within that filesystem — really an inode (metadata + block pointers) that the filesystem assembles from scattered blocks. Each layer adds one thing: organisation/naming, then a specific stream of bytes.

What is an inode, and why is a filename not the same thing as a file?

An inode is the filesystem's record for one file: its metadata (size, owner, permissions, timestamps, link count) and the pointers to the data blocks holding its contents — everything except the name. The name lives in a directory, which is just a table mapping names to inode numbers. So a filename is a label pointing at an inode; two names can point at one inode (a hard link), "deleting" removes a name (unlink) and frees data only when the link count hits zero, and renaming within a filesystem is instant because only the directory entry changes, never the data.

Your code calls write() and it returns success. Is the data on the disk? Explain the write path.

No. A successful write() means the kernel copied your bytes into the volatile page cache in RAM and marked the page dirty; it returns before touching the device. The kernel flushes dirty pages to storage later (write-back), and even then the data may sit in the drive's own volatile cache before reaching durable media. So the data is safe against your process crashing but not against power loss until it crosses the durability line — which only fsync (and a drive that honours flushes) forces on demand.

What does fsync do, and why does a database call it at every commit?

fsync(fd) forces a file's dirty pages (and, correctly configured, the drive cache) out to durable media and blocks until that's done — turning "in RAM" into "on disk." A database calls it at each transaction commit because commit is the exact moment it promises the user "your data is saved," so it must guarantee the data survives a crash then, not eventually. The cost is real (an fsync is milliseconds, far slower than a cached write), which is why database write throughput is often bound by fsync latency rather than bandwidth.

What does a filesystem journal protect against, and what does it not protect?

The journal records an intended change in a reserved log before applying it, so after a crash the filesystem can replay committed operations or discard incomplete ones and come back structurally consistent in seconds — instead of a multi-hour fsck. But by default it protects the filesystem's metadata (its structure), not necessarily your file's data: your bytes can still be lost in the page cache on a crash. Structural consistency and data durability are separate guarantees; only fsync gives you the second.

df -h shows free space but writes fail with "No space left on device." What's going on?

You've almost certainly run out of inodes, not bytes. The inode table is a fixed-count resource created with the filesystem, separate from data blocks; millions of tiny files can exhaust it while gigabytes of data space remain free. df -h reports free bytes; df -i reports free inodes — check the latter. (A second cause is a large file that was deleted but is still held open by a process, so its space isn't reclaimed until the file descriptor closes.)

Distinguish availability, durability and backup. Why isn't RAID a backup?

Availability is "can I reach the data right now" — RAID keeps you online through a disk death. Durability is "will the data still exist later" — achieved by keeping copies across devices (RAID) and machines/sites (replication). A backup is a separate point-in-time copy that survives logical loss: deletion, corruption, bad migrations, ransomware. RAID/replication keep copies in sync, so they faithfully and instantly propagate those events to every copy — which is exactly why they can't stand in for a backup. You need all three.

What are IOPS, throughput and latency, and which matters for a database vs a backup job?

IOPS is how many separate operations/second the device completes — the number that matters for small, random I/O, which is what a database does (many little row reads/writes). Throughput (MB/s) is bytes/second for large, sequential I/O — what a backup or log stream cares about. Latency is how long one operation takes — felt directly by an fsync-per-commit database. So a database is usually IOPS- and latency-sensitive, a backup is throughput-sensitive, and buying more of the wrong number (they trade off via block size and queue depth) changes nothing.

Compare block, file and object storage, and give the right job for each.

Block storage is a raw virtual disk you format yourself, attached to one machine, with the lowest latency — right for a database's data directory (EBS, Persistent Disk). File storage is a ready-made filesystem you mount over the network, shared by many machines with normal paths (NFS/EFS) — for genuinely shared directories across servers, at higher latency. Object storage keeps whole objects under keys in flat buckets over HTTP, with no filesystem, huge scale and extreme durability — right for uploads, backups, static assets and logs (S3, GCS, R2). Match the model to the job; putting a database on file or object storage is a classic, painful mistake.

Why is random access so much slower than sequential on an HDD but not on an SSD?

An HDD reaches a block by mechanically seeking the head to a track and waiting for the platter to rotate the block under it — milliseconds per access, paid on every random jump, while sequential access pays one seek then streams. An SSD has no moving parts; any block is reachable in microseconds via electronics, so random access is only modestly slower than sequential. That single physical difference is why HDDs do only a couple hundred random IOPS while SSDs do tens of thousands, and why the "sequential ≫ random" rule is decisive on HDDs but a minor effect on SSDs.
