Module 2 · Lesson 2.4

Memory: virtual address spaces, paging, swap, and the OOM killer that ate your API

Lesson 2.3 was the kernel sharing one CPU among many processes in time. This lesson is the kernel sharing one pool of RAM among the same processes in space — and it is where a huge fraction of real production incidents actually live. Every process on your server believes it owns a vast, private, contiguous memory that starts at address zero. That belief is a lie the hardware tells on purpose, and understanding exactly how the lie is maintained explains process isolation, why fork() is cheap, why "free memory" is almost never really free, why a machine can grind to a crawl without ever crashing, and why one night the Linux kernel walks up to your Express API and kills it with signal 9 — the OOM killer that ate your API.

~75 min read Prerequisites: Lessons 2.1–2.3 Conceptual · hands-on at the end Module 2 · Milestone 2
Learning objectives

By the end of this lesson you will be able to:

  1. Explain what a virtual address space is, why every process gets its own, and how that single mechanism delivers isolation, relocation and the illusion of contiguous memory.
  2. Describe paging: pages, frames, page tables, the MMU and the TLB — and trace a virtual address being translated to a physical one.
  3. Define a page fault, distinguish minor from major faults, and explain demand paging, copy-on-write and the page cache.
  4. Explain what swap is, when it helps, and what thrashing is — why a box can get slow instead of crashing.
  5. Explain memory overcommit and the OOM killer: why Linux hands out memory it doesn't have, how it chooses a victim, and how to read the kernel log that records the execution.
  6. Read a process's real memory footprint (RSS vs VSZ) and reason about container memory limits (OOMKilled) you will meet in Module 7.
Where this sits on the map

This is the third of Module 2's "kernel, one job at a time" lessons. Lesson 2.2 named the kernel's memory manager as one row in its table of jobs; this lesson is that row. Lesson 2.3 shared the CPU in time; this lesson shares RAM in space. It leans on Lesson 2.1's fact that RAM is finite, fast and volatile, and it hands directly to Lesson 2.5 (disk) — because swap and the page cache are exactly where memory and disk meet. Everything here pays off again in Module 7, where a container's memory limit is enforced by the very machinery (cgroups, the OOM killer) you meet below.

1 · Problem Statement

Back to the $5 box from Lesson 2.1: one pool of RAM — say 1 GB — and, on top of it, the same crowd from Lesson 2.2 all resident at once: your Express API, PostgreSQL, Redis, Nginx, an SSH session, and a scatter of background tasks. Each of those programs was compiled independently, by people who never spoke to each other, and each was compiled as if it owns the whole machine — its code expects to live at certain addresses, its data at others, with no knowledge that anything else exists. Now they must all fit in the same physical RAM, at the same time, without stepping on each other.

Left to run directly against physical memory, this produces a pile of impossible questions — the spatial twin of Lesson 2.2's list:

  • "Postgres was compiled to put a variable at address 0x4000. So was my API. There is only one physical address 0x4000. Who gets it, and what stops one from reading or clobbering the other's data?"
  • "My API needs to grow its heap while it runs. The memory right after it is Postgres's. How does it grow without colliding with a neighbour it can't see?"
  • "I want to run a program that needs more memory than the machine physically has. Is that simply impossible, or can the OS fake it?"
  • "Nginx starts, uses 30 MB, then its worker exits. That RAM is now scattered in the middle of physical memory. The next program needs one contiguous 40 MB block. How, when free memory is in fragments?"
  • "All six programs together ask for more memory than exists — but most of them aren't using most of what they asked for. Do I deny them up front, or let them overcommit and hope? And what happens the day the hope runs out?"
  • "When memory genuinely runs out, who decides which program dies, and why did it pick my API and not the leaky background script?"
The core problem

Many independently-compiled, mutually-distrusting programs must share one finite pool of physical RAM safely (none can read or corrupt another's memory), flexibly (each can grow and shrink without knowing about the others, and none needs to know where in physical RAM it actually landed), and elastically (the machine should be able to run programs whose combined appetite exceeds physical memory, degrading gracefully rather than simply refusing). Raw physical addressing — every program naming real memory cells directly — provides none of this. We need an indirection layer between the addresses a program uses and the physical cells they land in, and we need the hardware to enforce it on every single memory access, billions of times a second, at essentially zero cost.

The promise of this lesson: by the end, "the machine ran out of memory" will stop being a single vague event and resolve into a precise chain — virtual addresses, page tables, page faults, the page cache, swap, overcommit, and finally the OOM killer's victim-selection — each of which you can observe on your own VPS and each of which explains a different real-world failure you will otherwise misdiagnose.

2 · Historical Context

Like the kernel itself, virtual memory was not designed in the abstract; it was assembled from a sequence of increasingly clever answers to "how do we fit more programs into too little RAM without them destroying each other." Each step fixed the previous step's fatal flaw.

1940s–1950s · Physical addressing, one program

The earliest machines had no memory management at all. A program named physical memory cells directly, and since only one program ran at a time (Lesson 2.2), there was no one to collide with. Memory was simply an array of numbered cells your program owned entirely. This is the baseline: an address in the program was an address in the hardware, one-to-one.

1950s–1960s · Fixed partitions and the relocation problem

Multiprogramming (Lesson 2.2) put several programs in RAM at once by carving memory into fixed partitions — program A in the first 32 KB, program B in the next, and so on. This immediately exposed two problems that drive the rest of the story. First, relocation: a program compiled to run at address 0 now has to run at address 32768, so every address inside it is wrong. Second, protection: nothing stopped program A from reading or writing into program B's partition. Both are the §1 questions in their first, crude form.

1960s · Base-and-bound registers — the first indirection

The first hardware fix added two registers per program: a base (added to every address the program used, so a program written for address 0 could physically live anywhere) and a bound (the maximum offset, so an access past the end of your region faulted). Base-and-bound solved relocation and gave crude protection — but it forced each program to occupy one contiguous physical block, which is the seed of the fragmentation problem in §4.

1962 · The Atlas machine and demand paging

The Atlas computer at the University of Manchester introduced the idea that defines this lesson: break both the address space and physical memory into fixed-size blocks (pages and frames), keep a table mapping one to the other, and — crucially — let some pages live on the drum (disk) instead of in core (RAM), fetching them on demand when touched. This is virtual memory and demand paging in embryo: a program could be larger than physical memory, and its pieces could be scattered anywhere, because the page table hid all of it.

1960s–1970s · Paging hardware becomes standard

Through time-sharing systems and the Unix lineage, dedicated hardware — the Memory Management Unit (MMU) — was added to the CPU to perform the page-table lookup on every memory access at hardware speed, with a small cache (the TLB) to keep it fast. By the time Unix matured, "each process has its own paged virtual address space" was simply how serious machines worked.

Today · Why this is your everyday reality

Your $5 VPS runs a 64-bit Linux kernel driving a hardware MMU with multi-level page tables and a TLB, doing demand paging, copy-on-write, a unified page cache, optional swap, memory overcommit, and an OOM killer of last resort — every mechanism in this history, all at once, on every memory access your Express handler makes. When Module 7's container "gets OOMKilled," it is this 60-year-old lineage, wrapped in a 2000s-era cgroup, doing exactly what Atlas's designers set out to do: fit too much into too little, safely, and decide what gives when it can't.

3 · The Previous Solution (in detail)

To feel what virtual memory buys you, look hard at the best pre-virtual model: several programs in RAM at once, each relocated into one contiguous physical region by base-and-bound registers, with whole programs swapped out to disk when memory got tight. This is a real, workable model — early Unix ran this way — and its specific pains are precisely what paging was built to remove.

The model, stated plainly:

CONTIGUOUS-ALLOCATION MODEL  (base + bound, whole-program swapping)

  Physical RAM (one flat array of cells):
  0                                                          1 GB
  ├──────────┬───────────────┬──────────┬────────────────────┤
  │  kernel  │  Postgres     │  API     │      (free)         │
  └──────────┴───────────────┴──────────┴────────────────────┘
        base_API ─┘   bound_API ─┘

  · Each program occupies ONE contiguous physical block.
  · CPU adds base to every address; faults if offset > bound.
  · Out of room? Copy an ENTIRE program out to disk (swap it),
    free its block, load another. All-or-nothing.

The assumptions this model bakes in:

Contiguity is mandatory
A program's memory must be one unbroken physical block. There is no way to assemble a program's address space from scattered free fragments.
The whole program is the unit
You bring in or evict an entire program. You cannot keep only its hot 10% in RAM and leave the cold 90% on disk; it is all-in or all-out.
Size is bounded by physical RAM
A single program can be no larger than the physical memory available to hold it. "Bigger than RAM" is simply impossible.
Protection is coarse
Base-and-bound gives one region per program with one boundary. There is no notion of "this part is read-only code, that part is writable data," and no fine-grained sharing.

And it genuinely worked — it ran real multi-user systems for years, and its virtues are real: the address translation is trivially cheap (one addition, one comparison), and the model is simple enough to reason about completely. For a workload of a few similarly-sized, long-lived programs, it is a reasonable fit. It becomes a catastrophic fit the moment programs are many, differently-sized, short-lived, larger than RAM, or want to share memory — which is to say, the moment you have a real server. The next section is exactly those failures.

4 · Why It Failed

Push the contiguous-allocation model onto a busy, general-purpose server and each of its four assumptions turns into a distinct, well-known failure. These are the exact pains paging was invented to erase.

4.1 External fragmentation wastes memory you can't use

Programs of different sizes start and exit over time, leaving free gaps between the survivors. Soon you have, say, 200 MB free in total — but split into a 40 MB gap here, a 70 MB gap there, a 90 MB gap over there. A new program needing one contiguous 150 MB block cannot start, even though 200 MB is "free." This is external fragmentation: the free memory exists but is unusable because it isn't contiguous. The only remedies — compacting memory by shuffling running programs around, or careful allocation policies — are expensive and never fully solve it.

4.2 You can't run a program bigger than RAM

Because a program must fit entirely in a physical block, a 2 GB program simply cannot run on a 1 GB machine. Yet most programs, most of the time, are only actively using a small fraction of their memory — the current working set. Being forced to hold all of a program in RAM to run any of it wastes the machine's most precious resource on cold data that is never touched.

4.3 Swapping is all-or-nothing and brutal

When memory is tight, the only lever is to evict an entire program to disk and reload it later — copying megabytes out and megabytes back, even though the program only needed a few kilobytes of its memory to make progress. The granularity is wrong by orders of magnitude, so the cost of relieving memory pressure is enormous and the machine stalls hard whenever it happens.

4.4 Sharing and fine-grained protection are impossible

With one contiguous region and one boundary per program, there is no way to say "these two copies of Nginx should share one physical copy of the identical read-only code" — so identical code is duplicated in RAM per process. Nor is there a way to mark the code region read-only and the data region writable within a single program, so a stray write into the program's own instructions goes undetected. Memory is neither shared where it should be nor protected as finely as it should be.

The pattern behind all four failures

Every failure traces to one root cause: the program's memory is bound directly and contiguously to physical memory. Contiguity causes fragmentation; the direct binding forces all-or-nothing residency and blocks sharing. The fix is to break that binding — insert a translation layer so that the addresses a program uses are decoupled from the physical cells they land in, and make the unit of that mapping small and fixed-size so memory can be assembled from scattered pieces, partially resident, and shared page-by-page. That layer is virtual memory, built on paging, and it is the whole of §5.

5 · The New Solution

The solution is one idea applied ruthlessly: give every process its own private virtual address space, and translate every access through a page table the hardware consults on the fly. Definitions first — these words are the working vocabulary for the rest of the lesson and for Module 7.

5.1 The core vocabulary

Virtual address
An address as the program sees it. When your code holds a pointer, that number is a virtual address, meaningful only inside this one process. It is not where the data physically lives.
Physical address
An actual location in the RAM chips. Only the kernel and the MMU deal in these; your program never sees one.
Virtual address space
The full range of virtual addresses one process can use — on 64-bit systems, an enormous, private, sparse range that every process gets its own copy of. Two processes can both use virtual address 0x4000 and it maps to two different physical cells. This is the isolation from §1, delivered.
Page
A fixed-size chunk of a virtual address space — typically 4 KB on x86-64. The address space is divided into pages; the page is the unit of mapping.
Frame (page frame)
A fixed-size chunk of physical RAM, the same size as a page. Physical memory is divided into frames. A page is mapped to a frame (or to nowhere yet, or to disk).
Page table
The per-process data structure the kernel maintains that records, for each virtual page, which physical frame it maps to (and its permissions, and whether it is currently resident). The map from "what the program says" to "where it really is."
MMU (Memory Management Unit)
Hardware on the CPU that performs the page-table lookup on every memory access, translating virtual to physical automatically and enforcing the permission bits — at hardware speed.
Page fault
What happens when a program touches a virtual page that isn't currently mapped to a resident frame. The MMU traps into the kernel, which decides what to do (fetch it, allocate it, or kill the process). Not always an error — often just normal, lazy work.
Swap
Disk space the kernel can use to hold pages evicted from RAM, so RAM can hold something else. Lets total in-use memory exceed physical RAM, at the cost of disk-speed access to the swapped-out pages.
The one sentence to hold onto

A virtual address space is a per-process illusion of a huge, private, contiguous memory, implemented by mapping small fixed-size pages onto physical frames (or onto disk, or onto nothing yet) through a page table that the MMU consults on every access. Almost every memory behaviour in this lesson — isolation, lazy allocation, cheap fork(), swap, the page cache, overcommit — is a consequence of that one design.

5.2 The shape of the solution

The move inverts the contiguous model. Instead of each program getting one real, contiguous slab of physical RAM, each program gets its own virtual space that looks contiguous and private, while the page table quietly scatters its pages across whatever physical frames happen to be free — or leaves them unmapped until first touched, or parks them on disk: 

VIRTUAL MEMORY MODEL  ("every process has its own private map")

  API's virtual space        Postgres's virtual space
  (private, looks contiguous) (private, looks contiguous)
  ┌──────┐ page 0             ┌──────┐ page 0
  │      │──┐                 │      │──────────┐
  ├──────┤  │  page 1         ├──────┤          │ page 1
  │      │  │ ─────┐          │      │───┐      │ ──────┐
  └──────┘  │      │          └──────┘   │      │       │
   page tables (per process) map pages → frames (or disk, or nothing)
            ▼      ▼                     ▼      ▼       ▼
  ┌───────────────────────────────────────────────────────────┐
  │ PHYSICAL RAM (frames, scattered)   │  SWAP (on disk)        │
  │  [API p0][PG p1][free][API p1][PG p0] │  [PG cold page]     │
  └───────────────────────────────────────────────────────────┘

  Same virtual address in two processes → different frames.
  Contiguity is faked; fragmentation is gone; growth just adds pages.

Now re-answer §1's impossible questions, one line each. Who gets physical 0x4000? Both programs use virtual 0x4000; their page tables send those to different frames, so there is no conflict and no way to see each other's data — isolation. How does the API grow without colliding? It maps another page anywhere a free frame exists; the neighbour is irrelevant — no fragmentation, free growth. Bigger than RAM? Keep only the hot pages resident and leave the rest on disk — demand paging + swap. Scattered free memory? Any free frame will do; contiguity is only virtual — fragmentation solved. Overcommit and the day it runs out? §6.7 and §6.8. The single design move — a per-process page table the hardware enforces — answers nearly all of them.

6 · Internal Mechanics

Now the machine in motion. We will (6.1) lay out a process's virtual address space, (6.2) translate a virtual address through the page table, (6.3) meet the TLB that keeps translation fast, (6.4) walk a page fault end to end, (6.5) see demand paging and copy-on-write make allocation lazy, (6.6) understand the page cache — why "free" RAM is a lie, (6.7) explain swap and thrashing, and (6.8) face overcommit and the OOM killer that ate your API.

6.1 The anatomy of a process's address space

A process's virtual space is not one undifferentiated blob; the kernel lays it out in regions (Linux calls them VMAs, virtual memory areas), each with its own permissions. From low addresses to high, roughly: 

  high addr ┌────────────────────────┐
            │  stack   ↓ grows down   │  local variables, call frames (per thread)
            │        ...              │
            │        (gap)            │
            │        ...              │
            │  mmap region           │  shared libraries, mmap'd files, big mallocs
            │        ...              │
            │  heap    ↑ grows up     │  malloc/new: dynamic allocation
            ├────────────────────────┤
            │  BSS                    │  zero-initialised globals
            │  data                   │  initialised globals
            │  text (code)  read-only │  the program's machine instructions
  low addr  └────────────────────────┘

Notice the permissions: text (your compiled code) is mapped read-only and executable, so a stray write into it faults instead of silently corrupting your program — the fine-grained protection §4.4 lacked. The heap (where malloc/Node's allocations live) grows up; each thread's stack grows down. The vast space between is unmapped — touching it is the classic segmentation fault. This layout is per process, private, and identical-looking to every process even though each lands on totally different frames.

6.2 Translating one address through the page table

A virtual address splits into two parts: a page number (the high bits — which page) and an offset (the low bits — how far into the page). With 4 KB pages, the low 12 bits are the offset (212 = 4096) and the rest select the page. Translation replaces the page number with a frame number and keeps the offset: 

  virtual address:  [  virtual page number  ][  offset (12 bits)  ]
                              │                        │
                              ▼   page table lookup     │  (unchanged)
                     [ physical frame number ]          │
                              │                         │
                              ▼                         ▼
  physical address: [ physical frame number ][  offset (12 bits)  ]

A flat table with one entry per 4 KB page of a 64-bit space would be astronomically large, so real hardware uses a multi-level page table — a tree, typically 4 levels on x86-64 — where only the branches that are actually used exist. That keeps the table small for a sparse address space (most of the 64-bit range is unmapped), at the cost of several memory lookups per translation — which is exactly why the TLB exists.

6.3 The TLB: making translation nearly free

If every memory access required walking a 4-level page table, every access would cost several extra memory reads — crippling. So the MMU keeps a small, very fast cache of recent virtual→physical translations called the Translation Lookaside Buffer (TLB). On each access the MMU checks the TLB first; a hit gives the frame instantly, and only a miss triggers the full page-table walk (after which the result is cached). This is the same locality principle from Lesson 2.1's cache hierarchy, applied to translations: programs touch a small set of pages repeatedly, so a small TLB catches the vast majority. It is also why a context switch (Lesson 2.3) has a hidden cost we can now name precisely — switching address spaces can invalidate TLB entries, so the new process starts with TLB misses until it warms up again.

6.4 The page fault, end to end

The page fault is the pivot of this whole lesson: it is how a not-yet-resident page becomes resident, and it is routine, not exceptional. When the MMU finds no valid mapping for a touched page, it traps to the kernel, which inspects the situation and takes one of several paths: 

  program touches virtual address X
        │
        ▼
  MMU checks page table ── mapping present & allowed? ──▶ yes ─▶ access proceeds
        │ no / not resident
        ▼   PAGE FAULT → trap into kernel
  kernel asks: what SHOULD be at X?
    ├─ valid page, never used yet   → allocate a zeroed frame, map it     (minor fault)
    ├─ valid page, on swap/disk     → read it from disk into a frame      (MAJOR fault)
    ├─ valid page, copy-on-write    → copy the shared frame, map writable (minor fault)
    └─ NOT a valid address for you  → SIGSEGV: segmentation fault → killed
Minor (soft) fault
The page can be satisfied without touching the disk — e.g. allocate a fresh zeroed frame, or point at a page already in the page cache. Cheap: microseconds.
Major (hard) fault
The page's contents must be read from disk — from swap, or from a file being demand-loaded. Expensive: the cost of a disk read (Lesson 2.1's latency ladder), thousands of times slower than a minor fault. A rising major-fault rate is a red flag your working set no longer fits in RAM.
Invalid access
The address isn't part of any region the process is allowed to touch. The kernel sends SIGSEGV; your program crashes with "segmentation fault." The protection §4.4 lacked, enforced on every access.

6.5 Demand paging and copy-on-write: laziness as strategy

The page fault enables the kernel's central efficiency trick: do nothing until forced. When your program asks for memory, or launches, the kernel does not immediately find and zero physical frames for all of it. It merely records that the region is valid and leaves the pages unmapped. Only when the program actually touches a page does a minor fault fire and a real frame get allocated. This is demand paging, and it is why a program can malloc gigabytes instantly and cheaply — until it writes to them.

The same laziness makes fork() — the syscall that creates a new process by duplicating the current one (you met it as the basis of processes in Lesson 2.3) — nearly free. Instead of copying the parent's entire memory to the child, the kernel gives the child the same frames, marked read-only and flagged copy-on-write (COW). Both processes read the shared frames happily. The instant either one writes a shared page, a fault fires, the kernel copies just that one page, and each side gets its private copy. Pages that are only ever read are shared forever. This is how a Node cluster or an Nginx master forking workers duplicates a large process almost instantly and without doubling RAM — and it is a direct answer to §4.4's "identical code is duplicated per process."

6.6 The page cache: why "free memory" is a lie

Here is the fact that confuses more engineers than any other in this lesson. The kernel uses otherwise-idle RAM to cache the contents of files it has read from disk, so the next read is served from RAM at memory speed instead of disk speed. This is the page cache, and on a healthy server it will grow to fill nearly all "unused" RAM. So when free -h shows almost no "free" memory, that is usually correct and good: the RAM isn't wasted, it's caching your files, and the kernel will instantly hand it back to any program that needs it (cached file pages are clean and can be dropped without a disk write). The number that actually matters for pressure is available, not free — free means "cells holding nothing," available means "cells a new program could get," which includes all the reclaimable cache. Panicking at low "free" is the single most common memory misreading, and §7 shows you the exact command.

6.7 Swap and thrashing

When real demand for anonymous memory (heap, stack — memory not backed by a file) exceeds RAM, the kernel can evict some pages to swap on disk, freeing frames for hotter pages. Swap is a shock absorber: it lets total in-use memory exceed physical RAM and lets the kernel push genuinely cold pages out of the way. Accessing a swapped-out page later causes a major fault (§6.4) to read it back.

The danger is thrashing: when the active working set is larger than RAM, the kernel spends more time swapping pages in and out than doing real work. Every page it brings in forces another out, which is needed again immediately. Throughput collapses; the CPU sits mostly idle waiting on disk; the machine becomes unresponsive without ever crashing. This is the answer to "why did my server get slow instead of dying?" — it was thrashing. It is also why many modern production setups run with little or no swap and prefer a fast, clean kill (the OOM killer) over a slow, agonising thrash: a crashed process restarts in seconds; a thrashing box can be unreachable for minutes.

6.8 Overcommit and the OOM killer that ate your API

Because of demand paging (§6.5), programs routinely reserve far more memory than they ever touch. If Linux refused every allocation the moment total promises exceeded RAM+swap, it would deny memory that would never actually be used and waste the machine. So by default Linux overcommits: it says "yes" to allocations optimistically, betting that not everyone will cash in their promise at once. Usually the bet pays off.

The day the bet fails — processes actually touch enough of what they were promised that RAM and swap are genuinely exhausted, and there are no reclaimable pages left — the kernel is stuck: some running process is about to touch a valid page and there is no frame to give it. Rather than fail that access (which would crash a random process at a random instruction), the kernel invokes the OOM (out-of-memory) killer: it scores every process by a heuristic (dominated by how much memory each is using, adjustable via oom_score_adj), picks the one whose death frees the most memory for the least importance, and kills it with an unblockable SIGKILL (signal 9). It records the whole execution in the kernel log.

Why it "ate your API" and not the leaky script

The OOM killer optimises for freeing the most memory, and your Express/Node API — with its V8 heap, loaded modules and buffers — is frequently the single biggest memory user on a small box. So a memory leak in a tiny background task can push the machine over the edge, and the kernel's response is to kill the largest resident process to recover the most RAM: your API. The victim of an OOM event is very often not the culprit. Recognising this — and knowing you can protect a critical process with oom_score_adj, or better, cap the real culprit's memory — is the difference between blaming the wrong service and fixing the actual leak. In Module 7 this exact mechanism, scoped to one container by a cgroup, is what an OOMKilled pod or container status means.

7 · Real Industry Examples

Reading the OOM killer's report in dmesg

Every OOM kill is logged. On your VPS, dmesg (or journalctl -k) shows the kernel's account of exactly what happened — the machinery of §6.8, made visible: 

$ sudo dmesg | grep -i -A1 'killed process'
[12345.678] Out of memory: Killed process 8123 (node) total-vm:2101344kB,
            anon-rss:912004kB, file-rss:0kB, shmem-rss:0kB, ... oom_score:812
[12345.679] oom_reaper: reaped process 8123 (node) ...

Read it like a coroner's report: the machine ran out of memory, the kernel picked PID 8123 (node — your API) because its anon-rss (resident heap/stack) of ~890 MB made it the biggest, highest-scoring target, and killed it. If your API "just disappears" with no application error and exit code 137 (128 + 9, i.e. SIGKILL), this log is where the truth is. No stack trace in your app will ever mention it, because your app didn't crash — the kernel executed it from the outside.

OOMKilled containers and cgroup memory limits

When you run DevBoard's containers in Module 7 with a memory limit (--memory=512m, or a Kubernetes limits.memory), the kernel enforces that limit with a cgroup — and the OOM killer runs scoped to that one container. Exceed the limit and the container's main process is SIGKILLed, the container exits with code 137, and Docker/Kubernetes reports the status as OOMKilled. This is the whole of §6.8 confined to a box: same overcommit logic, same victim-selection, same signal — just walled to one container so it can't take the host down. Knowing the mechanism now means "why is my pod OOMKilled?" is not a mystery later; it's "its working set exceeded its cgroup limit."

Node's heap limit vs the machine's RAM

A recurring confusion: a Node process dies with "JavaScript heap out of memory" on a box that has plenty of free RAM. That is not the OOM killer — it's V8's own internal heap cap (historically ~1.5–2 GB unless raised with --max-old-space-size), a user-space limit the runtime enforces before the kernel is ever involved. The mirror case — the process killed by the kernel (exit 137, nothing in the app log) with RAM exhausted — is the OOM killer. Same symptom ("out of memory"), two completely different mechanisms at two different layers; this lesson lets you tell them apart instantly.

RSS vs VSZ: the number that lies and the number that counts

Look at any process in ps or top and you see two memory numbers, straight out of §5–6. VSZ (virtual size) is how much virtual address space the process has mapped — including demand-paged regions it never touched and shared-library pages shared with everyone. It is often huge and mostly meaningless for "how much RAM is this using." RSS (resident set size) is how many of its pages are actually resident in physical frames right now — the number that matters for memory pressure, though it still double-counts shared pages across processes. Engineers who panic at a multi-gigabyte VSZ, or who add up RSS across forked workers and double-count their shared COW pages, are misreading these; §6 tells you why the numbers look the way they do.

10 · Limitations

Virtual memory is not free, and its edges are where production surprises live.

Translation has real cost
Every access is translated; a TLB miss forces a multi-level page-table walk. Workloads with poor locality (random access over huge data sets) suffer TLB thrashing — one reason huge pages exist. The abstraction is cheap, not free.
Major faults are disk-speed
A page that must come from swap or disk costs a disk read — thousands of times a resident access. A workload whose working set doesn't fit in RAM pays this constantly, and no cleverness in your code repeals it.
Thrashing degrades before it fails
Under memory pressure a machine can become unusably slow long before anything crashes, and a slow box is often harder to diagnose and recover than a crashed one. Swap can turn a fast failure into a long outage.
Overcommit means allocation can lie
A successful malloc does not guarantee the memory is really there; the reckoning is deferred to first touch, where an OOM kill can strike a process that did nothing wrong. Success at allocation is not a promise of delivery.
The OOM killer is a blunt instrument
It kills a whole process with an uncatchable signal, often the biggest rather than the guilty one, with no graceful shutdown. It is a last resort that prevents total lockup, not a resource-management strategy.
This is a simplified model
Real systems add huge pages, NUMA (memory attached to specific CPUs, with distance costs), memory compaction, per-cgroup accounting, zram/compressed swap, and more. The page-and-frame picture is a true, load-bearing map — not the entire territory.

11 · Common Misconceptions

"Low 'free' memory means my server is about to run out."

Almost always false. The kernel deliberately fills idle RAM with the page cache (§6.6) to speed up file access, and hands it back instantly when a program needs it. The meaningful number is available (which counts reclaimable cache), not free. A healthy server runs with almost no "free" memory by design.

"A pointer in my program is an address in the RAM chips."

It's a virtual address, meaningful only inside your process, translated to a physical frame by the MMU on every access. Two processes can hold the identical pointer value pointing at completely different physical memory. Your code never sees a physical address.

"malloc (or allocating a big array) reserves that much physical RAM immediately."

No. Thanks to demand paging (§6.5), allocation just marks a region valid; physical frames are assigned lazily, only as you actually touch pages. You can allocate more than exists and pay nothing until you write to it — which is exactly why overcommit and the OOM killer exist.

"My API crashed, so there's a bug in my code."

If it vanished with exit code 137 and nothing in the application log, the kernel killed it (SIGKILL) during an OOM event — your code never threw. The truth is in dmesg/journalctl -k, not your stack traces. And the victim is often the biggest process, not the one that leaked.

"Adding swap always makes a memory-tight server more reliable."

Swap helps when it parks genuinely cold pages. But if the active working set exceeds RAM, swap causes thrashing (§6.7): the box gets crawlingly slow instead of failing fast. Many production setups prefer little/no swap plus a clean OOM kill and auto-restart over a machine that thrashes for minutes.

"VSZ is how much memory my process uses."

VSZ is virtual size — address space mapped, including untouched demand-paged regions and shared libraries. It's often huge and misleading. RSS (resident set size) is the pages actually in physical RAM, and it's the number to watch — while remembering RSS still double-counts pages shared between processes.

"'JavaScript heap out of memory' means the server ran out of RAM."

Usually not. That's V8's own heap cap being hit inside the Node process, before the kernel is involved — raise it with --max-old-space-size (or fix the leak). The kernel's OOM killer is a different event: exit 137, silent in your logs, RAM genuinely exhausted. Same words, different layer.

12 · Practical Use Cases

Diagnosing "my service keeps disappearing"

A container or process restarts with no application error and exit code 137. Straight to the memory story: check dmesg/journalctl -k for an OOM kill, look at the process's RSS trend over time (a steady climb is a leak; a spike matches a heavy request), and compare peak RSS against the machine's RAM or the container's cgroup limit. The lesson tells you the exact chain to walk (§6.8) instead of guessing.

Right-sizing a server and container limits

Deciding "how much RAM does DevBoard need?" becomes concrete: measure each service's steady-state and peak RSS (not VSZ), add headroom for the page cache and for request spikes, and set container memory limits above real peak working set — not so tight that normal traffic triggers OOMKilled, not so loose that a leak takes the whole host down. This is the reasoning behind Module 6's cost model and Module 7's container limits.

Reading free, top and /proc correctly

When someone says "the server's out of memory," you now check available memory, the page-cache size, the swap-in/swap-out rate, and the major-fault rate — not the scary-but-normal "free ≈ 0." You can distinguish "healthy box with a full page cache" from "box thrashing on swap" from "box one request away from an OOM kill," which are three completely different situations that look superficially similar.

Protecting the process that must not die

When one process is critical (say the database) and another is expendable (a batch worker), you can tilt the OOM killer's choice with oom_score_adj so it sacrifices the worker first — or, better, cap the memory-hungry culprit with a cgroup so it hits its own limit before the host is ever endangered. Understanding victim-selection (§6.8) turns the OOM killer from a random assassin into a policy you can set.

13 · Summary

  • Many independently-compiled processes must share one finite RAM safely, flexibly and elastically. Binding program addresses directly and contiguously to physical memory (base-and-bound) causes fragmentation, forces all-or-nothing residency, and blocks sharing.
  • The fix is virtual memory: every process gets its own private virtual address space, and every access is translated through a per-process page table by the hardware MMU. Isolation is the absence of a mapping, not a check.
  • Memory is managed in fixed-size pages (≈4 KB) mapped to physical frames. Contiguity is faked, so scattered free frames are fully usable and growth just maps more pages — external fragmentation is gone.
  • The TLB caches recent translations so translation is nearly free; a miss forces a multi-level page-table walk. Context switches can cost TLB warmth (a hidden cost from Lesson 2.3).
  • A page fault is routine, not an error: minor faults allocate a frame or hit the cache (fast); major faults read from disk/swap (slow); an invalid access is SIGSEGV.
  • Demand paging allocates frames only on first touch (so malloc is cheap and lazy); copy-on-write makes fork() nearly free and shares read-only code across processes.
  • The page cache uses idle RAM to cache disk contents, so low "free" memory is normal and good — watch available, not free.
  • Swap parks cold pages on disk to stretch RAM; if the working set exceeds RAM the machine thrashes — slow, not dead. Many setups prefer a fast OOM kill to a long thrash.
  • Linux overcommits memory (says yes optimistically because most promises are never cashed). When RAM+swap truly run out, the OOM killer SIGKILLs the highest-scoring process — often the biggest, not the guilty one. That's why it "ate your API" (exit 137, logged in dmesg).
  • Read RSS (resident, what matters) not VSZ (virtual, misleading). In Module 7 the same OOM machinery, scoped by a cgroup, is what OOMKilled means.

16 · Quiz

How to use this

Answer in your own words before revealing the model answer. Two or three sentences each. You're ready for Lesson 2.5 (storage) when you can answer Q1, Q3, Q6 and Q8 cold and have completed E1–E3 (and, on a disposable box, E4) on a real machine.

What is a virtual address space, and how does it give each process isolation?

It's the private range of virtual addresses one process uses, with its own page table mapping those addresses to physical frames. Because each process has its own map, the same virtual address in two processes resolves to different frames, and a process cannot even express an address that lands in another's memory. Isolation is the absence of a mapping, enforced by the MMU on every access — not a check the kernel runs each time.

Why break memory into fixed-size pages and frames instead of variable-size contiguous regions?

Because fixed-size pages let any free frame back any page, so a process's memory can be assembled from scattered free frames — eliminating external fragmentation (§4.1). It also makes the page the small, uniform unit of residency, eviction, sharing and protection, so the kernel can bring in, swap out, share or protect exactly what's needed rather than the whole program. Contiguity becomes purely virtual.

What is a page fault? Distinguish a minor fault from a major fault.

A page fault fires when a program touches a virtual page with no valid resident mapping; the MMU traps to the kernel, which decides what to do. A minor fault is resolved without disk — allocate a zeroed frame, satisfy a copy-on-write, or point at a page already in the page cache (microseconds). A major fault requires reading the page from disk/swap (a disk-latency operation, thousands of times slower). A rising major-fault rate signals the working set no longer fits in RAM.

Why is malloc-ing a huge array nearly instant, and how does that make fork() cheap?

Demand paging: allocation just marks the region valid; no physical frames are assigned until you actually touch a page (each first touch is a minor fault). So allocating gigabytes costs almost nothing until you write to them. The same laziness makes fork() cheap via copy-on-write: parent and child share the same frames marked read-only, and only a page that gets written is copied — read-only pages (like program code) stay shared forever.

Your free -h shows almost no free memory. Is the server in trouble? Explain.

Almost certainly not. The kernel fills idle RAM with the page cache (cached file contents) to speed up I/O, and reclaims it instantly when a program needs memory. So low "free" is normal and healthy. The number that reflects real headroom is available (which includes reclaimable cache), not free. You'd only worry if available were low and swap activity or major faults were climbing.

What is swap, and what is thrashing? Why might you run a server with little or no swap?

Swap is disk space the kernel uses to hold pages evicted from RAM, letting in-use memory exceed physical RAM by parking cold pages on disk (fetched back via major faults). Thrashing is when the active working set is larger than RAM, so the kernel spends more time swapping pages in and out than doing work — throughput collapses and the box crawls without crashing. Some setups prefer little/no swap plus a fast OOM kill and auto-restart, because a crashed process recovers in seconds while a thrashing box can be unreachable for minutes.

What is memory overcommit, and why does Linux do it?

Overcommit means the kernel grants allocations optimistically even when total promised memory exceeds RAM+swap, because — thanks to demand paging — most processes never touch most of what they reserve. Refusing every over-promise would deny memory that would never actually be used and waste the machine. The bet usually pays off; the risk is that if enough processes do cash in their promises, the kernel is forced into an OOM kill.

The OOM killer killed your Node API, but a tiny background script had the memory leak. Explain.

The OOM killer's goal is to free the most memory for the least importance, so it scores processes largely by how much RAM they're using and kills the highest scorer. A small leak in a background task can push the machine over the edge, but the kernel then kills the biggest resident process to recover the most RAM — often your API (large V8 heap, modules, buffers). So the victim is frequently not the culprit. You can bias the choice with oom_score_adj or, better, cap the real culprit's memory with a cgroup so it fails first.

Your service vanished with exit code 137 and nothing in its logs. What happened, and where do you look?

Exit code 137 = 128 + 9, meaning the process received SIGKILL — almost always the kernel's OOM killer during memory exhaustion (or, in a container, its cgroup limit being hit → OOMKilled). Your app didn't throw, so there's nothing in its logs; the kernel executed it from the outside. Look in dmesg / journalctl -k for the "Out of memory: Killed process" line, which names the victim and its RSS.

A process shows VSZ of 2 GB but RSS of 80 MB. Which tells you its real RAM use, and why the gap?

RSS (resident set size) — the pages actually in physical frames — is the real RAM figure; here that's ~80 MB. VSZ (virtual size) is all the address space mapped, including demand-paged regions never touched and shared-library pages shared with other processes, so it's far larger and mostly meaningless for "how much RAM." The gap is exactly demand paging and shared mappings: lots is mapped, little is resident. (Caveat: RSS still double-counts pages shared across processes.)
