Module 1 · Lesson 1.5

What really happens between git push and production

The whole map. Between the moment you press Enter on git push and the moment a stranger on another continent sees your change, a dozen distinct systems each do one job and hand off to the next. Most engineers treat that entire chain as a single opaque step called "deploy". This lesson makes it a map you can draw from memory — because you cannot debug, plan, or learn what you cannot locate.

~70 min read Prerequisites: Lesson 1.1 Conceptual · the map for the whole course Module 1 capstone · Milestone 1
Learning objectives

By the end of this lesson you will be able to:

  1. Draw the end-to-end path a change takes from your keyboard to a user, and name every stage on it.
  2. Distinguish the delivery path (code becomes a running service) from the request path (a user's request reaches that service and gets a response).
  3. Say precisely what git push does — and, more usefully, what it does not do.
  4. Place any failure, and any topic in Modules 2–14, at a specific node on the map.
  5. Explain, at map level, what an artifact, a registry, a reverse proxy, a load balancer and DNS each contribute.
Where this sits

Lesson 1.1 gave you the why: small, frequent, reversible changes with fast feedback. This lesson gives you the where — the actual route those changes travel. Lessons 1.2–1.4 (the lifecycle, the roles, the metrics) are placeholders for now and are not required reading for this one; 1.5 is written next because it is the map every later module fills in.

1 · Problem Statement

You already know how to build software. You finish a change, you commit it, you run git push. Then you wait. A few minutes later — if nothing went wrong — a user somewhere loads a page and sees your change. Between those two events lies a chain of systems that most competent software engineers cannot name.

That gap is usually collapsed into one word: "deploy". And treating it as one opaque step is exactly what makes DevOps feel like a bewildering pile of unrelated tools — Docker, GitHub Actions, nginx, DNS, TLS, load balancers, registries — with no skeleton to hang them on. The opacity has three concrete costs:

  1. You cannot debug what you cannot locate. "The site is down" is not actionable until you can ask where on the path it is down — the build? the deploy? DNS? the proxy? the database? Without a map, every incident is a panicked flail.
  2. You cannot plan what you cannot see. "Do I need a load balancer yet? A staging environment? A registry?" are unanswerable if you do not know what those nodes do or where they sit.
  3. You cannot learn a pile. A curriculum is only navigable if you know how the pieces connect. The map is the table of contents for everything that follows.
The core problem

The journey from git push to a served request is not one step — it is roughly a dozen, each performed by a different system, each able to fail independently. The problem this lesson solves is illegibility: without a shared mental map of the whole path, you cannot reason about failure, scope, or learning. Every other lesson in this course is a high-resolution zoom into one region of the map you are about to draw.

There is a second, subtler confusion buried in the word "deploy", and clearing it up is half of this lesson. There are actually two different journeys, and they run in different directions at different times:

Happens when you push

The delivery path

How your source code becomes a running process on a machine somewhere: build, test, package, ship, start. It runs once per change. Left to right, keyboard to server.

Happens on every visit

The request path

How a user's request physically reaches that running process and comes back with a response: DNS, the network, the load balancer, the proxy, your app, the database. It runs millions of times, long after the deploy. Right to left, user to server and back.

Hold both at once. The two paths meet at exactly one place — the running service — and almost every "it works on my machine but not in production" mystery lives in the gap between them. This lesson walks the delivery path first, then the request path, then shows where they join.

2 · Historical Context

The map did not always have a dozen nodes. It grew one node at a time, and the pattern of that growth tells you what each node is for. In every era, the human did some manual step; in the next era, that step got a name and was handed to a machine. The map got longer, but the human's job got shorter.

~1995 · Push and production were the same action

Early web deployment was literal file copying. You opened an FTP client, dragged your .html and .cgi files onto a server, and that was the deploy. There was no build, no test, no artifact, no separate "release" — the files you edited were the files being served. "Push" and "production" were one gesture. This is worth remembering: the entire elaborate pipeline you are about to learn is a stack of solutions to problems that this one gesture created.

Early 2000s · The manual terminal deploy

As sites gained databases and server-side code, deployment became: ssh into the box, git pull (or scp the files up), install dependencies, restart the process. The path was still just "a human in a terminal", but now it had implicit stages — fetch, build, restart — that nobody had separated yet. Most solo projects still deploy this way, and §3 dissects it in detail because it is the whole map compressed into five commands.

Mid 2000s · Deployment becomes a script

Tools like Capistrano (2006) encoded the terminal steps into a repeatable script: check out this revision, run these commands, symlink the new release, restart, and keep the last few releases so you can roll back. This is the first time the delivery path was written down as code rather than performed from memory. The moment a step is written down, it can be reviewed, reused, and — crucially — automated.

2005–2011 · A machine watches your pushes

Continuous integration servers (Hudson/Jenkins, 2005 onward) added a new node: a machine that subscribes to your pushes and runs the build and tests automatically on every one. Now the path had a gate that no human had to remember to open. Around the same time, cloud (Amazon EC2, 2006) turned "the server" from a physical box you owned into an API call — which meant the deploy target itself became programmable.

2013–present · The path becomes a standard pipeline

Docker (2013) standardised the artifact — a container image — so the thing you build, test, ship and run is one identical, portable object. Container registries standardised where artifacts live. Managed CI/CD (GitHub Actions, GitLab CI) standardised the trigger and the stages. Orchestrators (Kubernetes) standardised running many copies. The result is the map this lesson draws: the same stages that a 1995 webmaster did by hand, now each a named, automated node — which is precisely why the number of nodes went up while the amount of human work went down.

The through-line

Every node on the modern map is a manual step from an earlier era that got named and automated. When a node looks like pointless ceremony, ask "what manual mistake does this prevent?" — the answer is always in this history.

3 · The Previous Solution (in detail)

Before drawing the full map, let us look hard at the compressed version, because you have almost certainly used it and because every stage of the real map is an expansion of something hidden inside it. Here is the canonical solo-developer deploy — still extremely common, and not contemptible: 

# on your laptop
git push origin main                 # 1. upload commits to GitHub

# then, by hand:
ssh deploy@203.0.113.10              # 2. connect to the one server
cd /var/www/app                      # 3. go to where the code lives
git pull                             # 4. fetch + merge the new commits
npm ci                               # 5. install dependencies
npm run build                        # 6. compile/bundle on the server
pm2 restart app                      # 7. restart the process
# 8. tail the logs, reload the site in a browser, hope

These eight commands secretly contain the entire map. Name what each one is really doing:

Step 1 — the only automated hop
git push moves your commits to a hosted Git server. Notice it is the only step that happens because of the push; everything else is you, manually, afterward.
Steps 2–4 — transport & source
You are the network and the trigger. You personally carry the change from the Git host onto the runtime, by hand, at a time you chose.
Steps 5–6 — build, on the production box
Dependencies are installed and the code is compiled on the same machine that serves users, using whatever versions of Node, system libraries and tools happen to be on that box today.
Step 7 — deploy and release, fused
restart both puts the new code in place and immediately exposes it to all users, in one irreversible motion. There is no moment where the new version exists but is not yet live.
Step 8 — observability, done by eyeball
You are the monitoring system: you look at logs and reload the page. If you close the laptop, monitoring stops.

This is a complete delivery path. It has a source, a transport, a build, a deploy, a release and an observation step — every stage the fancy version has. The difference is that here they are fused, manual, and invisible. The real map does not add stages that were not there; it separates the stages that were already there so each can be made reliable independently. Keep this compressed version in mind — the rest of the lesson is largely the act of pulling it apart.

4 · Why It Failed

The compressed path works right up until it doesn't, and its failure modes are worth tracing one by one, because each failure is precisely the reason a corresponding node exists on the full map.

4.1 "Build on the box" makes production non-reproducible

Because npm ci and npm run build run on the server, the running code depends on the server's exact state: its Node version, its system libraries, its environment variables, its disk contents. Two servers built at different times are subtly different — the snowflake server problem from Lesson 1.1. And if the build fails halfway (a network blip during install), you are left with a server that is neither the old version nor the new one. The full map fixes this by building exactly once, somewhere clean, into a sealed artifact.

4.2 No artifact means "what is in production?" has no precise answer

Ask the compressed-path operator "what exactly is running right now?" and the honest answer is "whatever main looked like the last time I happened to pull, plus whatever those dependencies resolved to that day." There is no name for the running thing. You cannot store it, copy it to a second server, or prove that staging and production are identical — because there is no "it". The full map fixes this with an immutable, content-addressed artifact (a container image) that has a precise identity.

4.3 No gate means broken code reaches users

Nothing runs between git pull and restart. There is no automated point at which a failing test can say "stop, do not ship this." The first system to discover a bug is your users. The full map fixes this by inserting a verification gate that the change must pass before it can proceed.

4.4 Fused deploy-and-release means every change is a visible blip

restart drops in-flight connections and exposes the new code instantly, to everyone, at once. There is no way to put the new version in place quietly, send it 1% of traffic, watch, and then widen — because deploying and releasing are the same button. Downtime on every deploy trains you to deploy rarely, which (per Lesson 1.1) makes batches larger and failures worse. The full map fixes this by separating deploy from release and using a rollout strategy.

4.5 Rollback is a rebuild, so it is slow and unproven

To undo, you git checkout the old SHA and rebuild — but that rebuild happens now, with today's dependency resolution, so your "rollback" is actually a brand-new, never-tested state. Under incident pressure, this is the worst possible time to be running an untested build. The full map fixes this by keeping the previous artifact ready to re-release instantly.

4.6 It is invisible and unrecorded

There is no record of who deployed what, when, or whether it succeeded. No health check gates the release; no alert tells you it broke at 3 a.m. The full map fixes this with an observability return-channel that closes the loop back to you.

The pattern

Every failure above comes from fusing stages that should be separate. The full pipeline is not bureaucracy bolted onto a simple process — it is the same process with its seams made explicit, so that each seam can be given a guarantee. Read the rest of this lesson as "here is the seam, and here is the guarantee it buys."

5 · The New Solution

The solution is to make the whole path explicit: a named sequence of transformations, each followed by a gate, ending in a running service that a request path can reach. Here is the mental model in one sentence, and then the vocabulary you need to read the map.

A deployment pipeline is a series of transformations that turn a commit into a running service, with a gate after each transformation that is allowed to stop the line — and it is the only road to production.
The one-sentence definition of everything in Modules 7–12.

Define the nouns before we use them, because each names a place on the map:

Source / Git host
The hosted server that holds your repository's history (GitHub, GitLab). git push deposits commits here. It is the map's origin and its single source of truth.
CI runner
An ephemeral machine — created fresh, thrown away after — that the Git host summons on each push to run your build and tests. "Ephemeral" is the point: a clean room means the build cannot silently depend on yesterday's leftovers.
Artifact
The single, immutable output of the build — for this course, a container image: your code plus its exact dependencies plus a minimal OS, sealed into one file that runs identically anywhere. It is built once and never rebuilt.
Registry
A storage service for artifacts, addressed by a content digest (a hash of the exact bytes). "What is in production?" now has a precise answer: a digest.
Environment
A place an artifact can run — typically staging (a production-like rehearsal) and production (real users). Same artifact, different configuration.
Deploy vs release
Deploy = place the artifact on the runtime and start it. Release = direct user traffic to it. Keeping them separate is what makes canaries, blue-green and feature flags possible.
The runtime
The machine(s) where the process actually runs: a virtual server (Modules 2, 6), its operating system (Modules 2, 3), and possibly an orchestrator that schedules copies of it (Module 13).
The edge
Everything a user's request meets before it reaches your process: DNS (Module 4), the network and TLS (Module 4), a load balancer and a reverse proxy such as nginx (Module 5).
Observability
The return channel: logs, metrics and traces emitted by the running service, plus the alerts and postmortems that carry what they reveal back to you (Module 12).

With those in hand, the map is just: Source → CI runner → Artifact → Registry → Deploy → Runtime (the delivery path), and then User → Edge → Runtime → Data → back (the request path), joined at the running service, with an observability arrow running from the service back to you. Section 6 walks every arrow; Section 8 draws it whole.

6 · Internal Mechanics

Now the tour. We follow one specific change — you rename a button in the course project from "Log in" to "Sign in" — from your keyboard all the way to a user in another country seeing it, naming every system it passes through and, in brackets, the module that zooms into it. First the delivery path (§6.1–6.7), then the request path (§6.8), then the return loop (§6.9).

6.1 Your machine, before the push

You edit Login.jsx, save, and run git commit. A well-configured repo runs pre-commit hooks here — formatter, linter, type-checker — the fastest, cheapest feedback rung there is (Lesson 1.1, §6.4). This is still all on your laptop; nothing has left your machine. Then: 

git push origin main

Here is the single most clarifying fact in this lesson. All git push does is upload your new commits to a branch on the Git host. It transfers objects over the network and updates a pointer (the main ref) on a server. That is the entire operation. It does not build your code, run your tests, or deploy anything. Everything that follows is triggered by the push but not done by it.

Define: ref

A ref is a named pointer to a commit — main is a ref. Pushing moves the commit objects to the host and advances the remote's main to point at your latest commit. Think "update a pointer on a server", not "run my project".

6.2 The Git host notices, and fires a trigger

The commits now live on GitHub. Because your repository has a workflow configured, the host emits an event — a webhook: an automated "this just happened" message — that says "main was updated." Your CI system is subscribed to that event, so it wakes up. This subscription is the seam that replaced "a human remembering to deploy": the machine is watching, so you don't have to.

6.3 Build — exactly once, in a clean room Module 9 · Module 7

CI spins up a fresh ephemeral runner and does, in order:

  1. Checkout the exact commit SHA you pushed — not "latest", that specific one.
  2. Install dependencies deterministically from the lockfile, so the versions are pinned and identical every time.
  3. Compile / bundle the app.
  4. Package the result into one container image — your built code + its exact dependencies + a minimal OS, sealed together — and tag it with the commit SHA.

This is build once (Lesson 1.1, §6.3). The image produced here is the only thing that will ever run in production; it is never rebuilt downstream. Because it was built in a clean, throwaway environment, it cannot secretly depend on some leftover state — which is what kills §4.1's "build on the box".

6.4 Verify — the gate Module 9

Against that exact image, CI runs the checks: unit tests, then integration tests against a real Postgres and Redis, then security and licence scans, ordered cheapest-and-most-likely-to-fail first. This is the gate. If anything fails, the line stops here and the image never advances — the broken "Sign in" button never reaches a user. Nothing downstream can run until this passes.

6.5 Publish — put the artifact somewhere addressable Module 7

The verified image is pushed to a container registry and addressed by its content digest — a hash like sha256:9f2c… that names those exact bytes and no others. Now the question "what is running in production?" has a one-line, unambiguous answer, and any machine anywhere can pull that identical image. This is what §4.2 was missing.

6.6 Deploy, then release Module 10

A deployment step tells the runtime: "pull image sha256:9f2c… and start it." Two distinct actions live here, and the whole art of safe delivery is in keeping them apart:

  • Deploy — the new container starts running alongside the old one, but no users are sent to it yet. It reports a health check (an endpoint the platform polls to ask "are you alive and ready?").
  • Release — only once it is healthy does traffic get shifted onto it, by a chosen strategy: all at once (rolling), instant swap with the old kept warm (blue-green), or a cautious 1%→100% ramp watching error rates (canary). If health checks fail, traffic never moves and the old version keeps serving — an automatic, instant, proven rollback, because the old artifact is still right there.

6.7 The runtime — where the process actually lives Modules 2 · 3 · 6 · 13

The container is now a running process on a real machine: a virtual server rented from a cloud provider (Modules 2 & 6), whose operating system (Modules 2 & 3) schedules it on a CPU, gives it memory, and lets it open a network port (say, 3000) to listen for requests. At larger scale, an orchestrator like Kubernetes (Module 13) runs many identical copies across many machines and restarts any that die. For now, picture one container listening on one port on one small server. The delivery path ends here: your change is now a live process. It has not yet met a single user.

Halfway checkpoint

Everything so far — push, trigger, build, verify, publish, deploy, release — is the delivery path, and it ran once for your button change. Now we flip direction entirely and follow the request path, which runs every time anyone visits, forever after.

6.8 The request path — how a user actually reaches your process Modules 4 · 5

A user in Lagos opens their browser and types devboard.app. Here is every hop their request takes to reach the container from §6.7 and come back:

  1. DNS resolution (Module 4). The name devboard.app means nothing to the network; it must be translated to an IP address like 203.0.113.10. The browser asks the Domain Name System, a global distributed directory, and gets back an address. This is why "the domain is not the server" — the domain is a lookup key that points at one.
  2. Transport & TLS (Module 4). The browser opens a TCP connection to that IP and performs a TLS handshake — the negotiation that turns http into encrypted https. The request travels as encrypted packets across many networks.
  3. The load balancer (Module 5). The request arrives not at your app but at a load balancer: a front door that spreads incoming requests across however many identical copies of your service are running, and refuses to send traffic to unhealthy ones. To the user there is "one server"; behind the door there may be twenty.
  4. The reverse proxy (Module 5). Next, a reverse proxy such as nginx typically terminates TLS (decrypts here so your app doesn't have to), serves static files itself, and routes by path — /api/* to the backend, everything else to the frontend. This is why "HTTPS is usually handled at the edge, not in your app."
  5. Your process (the runtime, §6.7). The request finally reaches the container listening on port 3000. Your Express code runs the handler for that route.
  6. Data (the project stack). To render the page your code queries Postgres (the database of record) and perhaps Redis (a fast cache). These are more running processes, reached over the network the same way.
  7. The response returns back up the same chain — app → proxy → load balancer → across the internet → the user's browser, which paints the page. They see "Sign in." Your change is live.

6.9 Observability — the return channel that closes the loop Module 12

As it serves that request and millions of others, the running service emits logs (what happened), metrics (how much, how fast, how many errors) and traces (the path of one request through the systems). A monitoring stack collects these; alerts fire when something crosses a threshold and page you; and when something breaks, a blameless postmortem turns the incident into an improvement that feeds back to §6.1. This arrow — from the running service back to you — is what makes the whole thing a loop rather than a one-way street, and it is the only stage that reports the truth about real users (Lesson 1.1, §6.2).

The invariants, restated as map rules

Three rules from Lesson 1.1 are really rules about this map: (1) the pipeline is the only road — no SSH-ing in to edit production, or the map becomes a lie; (2) build once, promote the same artifact — the digest that passed the gate is the digest that serves users; (3) fast, proven reversal — the previous artifact stays ready so release can be undone in seconds.

7 · Real Industry Examples

The course project, timed devboard

This is the exact stack you will build: GitHub → GitHub Actions → a container registry → a $5 virtual server running your containers behind nginx. Here is the button change from §6, on the clock: 

00:00   git push origin main            you press Enter
00:03   GitHub fires the workflow        webhook → Actions runner boots
00:20   checkout + npm ci + build        clean-room build of the exact SHA
02:10   unit + integration tests pass    THE GATE (a fail would stop here)
02:40   docker build → image tagged      one immutable artifact
03:05   push image to registry           addressed by digest sha256:9f2c…
03:30   deploy to staging + smoke test   runs, but no public traffic
04:10   release to production (rolling)  health-gated; old version kept warm
04:30   observability confirms green     error rate flat, latency normal
        ── total: ~4.5 min, zero downtime, one-command undo available ──

Contrast the compressed path from §3 doing the "same" work: you SSH in, pull, rebuild on the box (using whatever is installed today), restart (dropping live connections), and eyeball the logs — no gate, no artifact, no health check, no record, and a rollback that means rebuilding an untested state by hand. Same change; a completely different risk profile.

The request path, from Lagos

Once deployed, a visitor's request for devboard.app runs the §6.8 chain: DNS resolves the name to your server's IP; the browser opens an encrypted TLS connection; the request hits nginx, which terminates TLS and routes /api/tasks to your Express container on port 3000; Express queries Postgres, checks Redis, and returns JSON; the response travels back and the browser renders the board. None of that touched the delivery pipeline — it is the other half of the map, exercised on every single visit.

The map is scale-invariant

Amazon deploying every 11.6 seconds and Netflix running across thousands of instances (Lesson 1.1, §7) use the same map — the nodes are identical; only the automation and redundancy at each node are turned up. A solo engineer's map and Amazon's map have the same shape. That is why learning the map once pays off at every scale: you are not learning a beginner's simplification you will later discard, you are learning the actual structure.

10 · Limitations

The map is a model, and every model lies a little. Know where.

Managed platforms collapse nodes
A PaaS (Heroku, Render, Fly, Vercel) or serverless platform hides several nodes behind one git push — they still build, publish, deploy, route and load-balance, but you don't see it. That is a convenience, not an exception: the nodes are still there, and when the platform misbehaves you must know they exist to reason about it.
Not every project has every node
A static site skips the runtime and database entirely (files served from a CDN). A tiny internal tool may have no load balancer and no staging. The map is the maximal path; real projects use a subset. Knowing the full shape lets you see what you chose to omit.
The boundaries blur in practice
A reverse proxy can also load-balance; a load balancer can terminate TLS; an orchestrator can subsume deploy, release, health-checking and load-balancing at once. The nodes are roles, not always separate boxes — one component can play several.
It is a happy-path sketch
Real systems add CDNs, message queues, background workers, cron jobs, multiple databases, read replicas, secrets managers, and more. Those attach to the map; they don't replace it. This lesson deliberately draws the spine, not every rib.
"Once per change / every visit" is a simplification
Autoscaling, restarts and config reloads mean the delivery-side machinery can stir without a new commit. The two-paths model is a teaching frame, not a claim that the delivery path is ever truly idle.

11 · Common Misconceptions

"git push deploys my app."

Push uploads commits to the Git host and updates a ref. Full stop. It may trigger a pipeline that eventually deploys, but push itself never builds, tests, or ships anything. On a repo with no pipeline configured, git push changes nothing a user can see. Conflating "push" with "deploy" is the single most common reason beginners cannot reason about what broke.

"The server runs my source code / my repository."

Production runs a built artifact — a container image containing compiled/bundled output plus pinned dependencies — not your .jsx files and not your .git folder. The repository is the recipe; the artifact is the cooked dish; the running process is the dish being served. Editing source on the server (if you even can) changes nothing until something rebuilds and redeploys.

"The domain name is my server."

A domain is a lookup key. DNS translates it to an IP address, and that address might point at a load balancer in front of twenty servers, or move to a completely different machine tomorrow with no code change at all. The name and the machine are joined only by a directory entry you control — which is exactly why you can swap servers without users noticing.

"If it works on localhost, it'll work in production."

Localhost exercises neither the real delivery path (a clean-room build with pinned deps) nor the real request path (DNS, TLS, a proxy, a load balancer, a network between your app and its database). Most "works on my machine" failures live precisely in those two gaps. The whole point of building an artifact and having a production-like staging environment is to shrink this gap to near zero.

"Deploying and releasing are the same thing."

Deploy puts the new version on the runtime; release sends users to it. Keeping them separate is what enables canaries (release to 1% first), blue-green (instant swap, instant swap-back), and feature flags (deploy the code dark, switch it on later). Fuse them — as a bare restart does — and you lose every one of those safety mechanisms at once.

"The build happens on the production server."

In a real pipeline the build happens once, on a clean CI runner, before production ever sees it — and the exact bytes that passed the tests are the bytes that get deployed. Building on the production box (as the compressed path does) reintroduces drift and means production runs something no test ever saw.

"HTTPS is handled by my application code."

Usually TLS is terminated at the edge — the load balancer or reverse proxy decrypts the request and forwards plain HTTP to your app on a private network. Your app code typically never touches a certificate. This is why "add HTTPS" is mostly a Module 5 (proxy) and Module 4 (certificates/DNS) task, not an application change.

"There is one server behind the domain."

Often there are many identical copies behind a load balancer, precisely so that one can die, or be replaced during a deploy, without downtime. "The server" is a convenient fiction for "whichever healthy instance the load balancer picked for this request."

12 · Practical Use Cases

Debugging: localise before you theorise

When something is wrong, walk the request path outside-in and ask a yes/no question at each node: Does DNS resolve (dig devboard.app)? Does the port answer (curl -v https://devboard.app)? Is it TLS or the app that fails? Does the proxy route /api correctly? Is the app process up? Can it reach the database? Each answer halves the search space. "The site is broken" is not a bug report; "TLS connects but /api returns 502 while / loads" points at exactly one node.

Learning: use the map as your syllabus

Pin the §8.3 diagram somewhere. As each module arrives, mark which node it fills in. You will finish the course able to point at any node and explain what it does, why it exists, and what breaks without it — which is the definition of understanding a system rather than memorising its tools.

Architecture: decide which nodes you actually need

The map is maximal on purpose. For a side project, a defensible subset is: GitHub → Actions → one built image → one small server running it behind nginx, with uptime alerting. No load balancer, no orchestrator, no staging — yet. Knowing the full map lets you make those omissions deliberately, and know the exact node to add when you outgrow the choice (add a second instance and a load balancer when one server is no longer enough; add staging when a bad deploy first burns you).

Onboarding: "show me the map"

The fastest way to understand any unfamiliar system — a new job, an inherited codebase — is to reconstruct its two paths: how does a change get to production here, and how does a request get served? Draw it on a whiteboard and have someone correct you. You will learn more in twenty minutes than from a day of reading the code.

13 · Summary

  • The gap between git push and a served request is not one step called "deploy" — it is roughly a dozen distinct systems, each doing one job and each able to fail on its own.
  • There are two paths: the delivery path (code → running service, once per change, left to right) and the request path (user → response, every visit, right to left). They meet at the running service.
  • git push only uploads commits to the Git host and updates a ref. Everything after — build, test, publish, deploy, release — is triggered by the push, not done by it.
  • The delivery path is: source → CI build (once, clean room) → verify (the gate) → registry (immutable artifact) → deploy → release (health-gated) → runtime.
  • The request path is: DNS → transport & TLS → load balancer → reverse proxy → your process → data → back.
  • Deploy ≠ release. Deploy places the artifact; release directs traffic. Separating them is what makes safe rollouts and instant rollback possible.
  • Production runs a built artifact, not your source; the registry gives "what is in production?" a precise, one-line answer (a digest).
  • The compressed solo deploy (SSH + pull + rebuild + restart) contains every stage of the full map, but fused, manual and invisible — which is the source of each of its failure modes.
  • The map is scale-invariant: a solo project and Amazon share its shape; only the automation and redundancy at each node differ. Managed platforms hide nodes but never remove them.
  • Carry the map and you can localise any failure, scope any decision, navigate the whole course, and read any team's system. It is the diagram Milestone 1 asks you to draw from memory.

16 · Quiz

How to use this

Answer in your own words before revealing the model answer — retrieval builds the memory; recognition only feels like it does. Two or three sentences each. Module 1 is complete when you can answer Q1, Q2, Q4 and Q8 cold, and complete exercise E1 unaided.

Precisely, what does git push do — and name three things it does not do?

It uploads your new commit objects to the Git host and advances a remote ref (e.g. main) to point at your latest commit. That is all. It does not build your code, does not run your tests, and does not deploy or release anything. On a repository with no pipeline configured, a push changes nothing a user can observe; anything further happens because the push triggers other systems, not because push did it.

Distinguish the delivery path from the request path: direction, frequency, and where they meet.

The delivery path turns source code into a running service — build, test, publish, deploy, release — running once per change, left to right, keyboard to server. The request path carries a user's request to that running service and returns a response — DNS, TLS, load balancer, proxy, app, database — running on every visit, right to left and back. They meet at exactly one node: the running service.

A user reports the site is down. Walk the request path and give the sequence of yes/no questions you would ask.

Outside-in: (1) Does DNS resolve the name to an IP (dig)? (2) Does the IP accept a connection and complete a TLS handshake (curl -v)? (3) Does the reverse proxy respond, and does it route the failing path correctly (e.g. / works but /api 502s)? (4) Is the app process actually running and listening on its port? (5) Can the app reach its database/cache? Each answer roughly halves the search space, turning "it's down" into a specific node.

What is a build artifact, why build it exactly once, and what precisely goes wrong if you build on the production server instead?

An artifact is the single immutable output of the build — here, a container image of your compiled code plus pinned dependencies plus a minimal OS. Building once, in a clean CI runner, means the exact bytes that passed the tests are the bytes that run in production. Building on the production server instead makes the running code depend on that box's current state (Node version, system libraries, leftover files), so production runs something no test ever saw, environments drift into unreproducible snowflakes, and a half-finished build can leave the box in a broken in-between state.

Explain the difference between deploy and release, and name one thing separating them makes possible.

Deploy = place the new artifact on the runtime and start it (no users sent to it yet). Release = shift user traffic onto it. Separating them enables canary releases (send 1% of traffic first and watch), blue-green (instant swap with the old version kept warm for instant swap-back), and feature flags (deploy code "dark" and switch it on later). A bare restart fuses the two and loses all of these.

Your friend says "I pushed my code but the website hasn't changed — git push is broken." What's actually going on?

git push is working fine — it put the commits on the Git host, which you can verify in the host's commits view. The website hasn't changed because nothing is configured to turn those commits into a running deploy: there is no pipeline (or it failed), or the deploy step hasn't run. Push and deploy are different events; the friend has conflated "my code is on GitHub" with "my code is serving users," which are separated by the entire delivery path.

What does a reverse proxy like nginx typically do in the request path, and why isn't that job done by your application?

It sits in front of the app and commonly: terminates TLS (decrypts HTTPS so the app can speak plain HTTP internally), serves static files directly, and routes by path (e.g. /api/* to the backend, everything else to the frontend). It's kept out of the app because these are cross-cutting edge concerns — certificate handling, routing, static serving — that are better centralised, hardened and reused than reimplemented in every application, and because it lets you change routing or certificates without redeploying the app.

Why is the map called "scale-invariant," and what does that imply for how you should learn it?

Because a solo project's map and a giant like Amazon's have the same shape — the same nodes (source, build, gate, registry, deploy/release, runtime, edge, data, observability). Only the automation and redundancy at each node differ (one server vs thousands; manual approve vs full auto). The implication: learning the map once is not a throwaway beginner's simplification — it is the actual structure of production systems, so effort spent understanding it now pays off at every scale later.

Name three nodes a typical PaaS (e.g. Heroku/Render/Vercel) performs invisibly on a git push, and why it still matters that you know they exist.

Any three of: the build (it builds your artifact), the registry/storage of that artifact, the deploy and release, the load balancer, TLS termination, and routing — all hidden behind one push. It matters because when the platform misbehaves (a build fails oddly, TLS won't provision, routing sends /api to the wrong place, a deploy half-succeeds), you can only diagnose it if you know the node exists behind the convenience. The platform removed the work, not the nodes.

A change "works on localhost" but fails in production. Using the two paths, where are the most likely culprits and why?

Localhost exercises neither real path. On the delivery path, localhost skips the clean-room build with pinned dependencies, so a missing/loose dependency or an environment assumption can differ. On the request path, localhost has no DNS, no TLS, no reverse proxy, no load balancer, and the app talks to a local database instead of one across a network — so path routing, TLS, environment variables/secrets, and database connectivity are the classic culprits. The fix strategy is to shrink both gaps: build a real artifact, and use a production-like staging environment that includes the edge and real data connections.
