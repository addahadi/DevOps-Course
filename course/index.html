From Commit to Production

A semester-length, first-principles DevOps course for software engineers who do not want to become DevOps engineers — they want to build, ship, run, and scale their own systems without depending on anyone else. Everything that happens between git push and a user seeing your response, explained from the ground up.

How this course works

This is not a tutorial series. A tutorial gives you commands; this course gives you models — accurate mental pictures of how each piece of machinery actually behaves, so that when reality diverges from the happy path you can reason your way out instead of searching for a different tutorial.

The teaching contract

PrincipleWhat it means in practice
First principlesEvery technology is introduced by the problem it was invented to solve, what people did before it, and why that stopped working. Tools are consequences, never starting points.
No undefined termsJargon is defined the first time it appears. If a lesson uses a term you have not been given, that is a bug — say so.
Depth over speedWe do not advance until the current lesson is understood. Every lesson ends with a quiz you answer in your own words.
Internals alwaysDocker is namespaces and cgroups. TLS is a specific sequence of messages. Nginx is an event loop. You will learn the mechanism, not the marketing.
Trade-offs, not verdictsEvery lesson states when not to use the thing. Anyone who tells you a technology has no downside is selling something.
One project throughoutKnowledge that never touched a running system is trivia. Each module upgrades the same real application.

All 95 lessons follow the same 16-part structure, so you always know where you are:

Output format

Every roadmap, lesson, study guide and cheat sheet exists twice: in our conversation, and as a self-contained HTML file on disk under D:\DevOps\course\. The HTML files have no CDN links, no external fonts and no network calls — they work offline, forever, and you can print them. If a lesson is revised, its whole file is regenerated.

What you need before starting

  • Assumed: you can build a backend and a frontend, you use Git daily, you understand functions/types/async/HTTP-at-the-API-level, and you can read a stack trace.
  • Not assumed: anything about Linux administration, networking below the fetch() call, virtualization, containers, CI systems, or production operations.
  • Hardware: any machine with 8 GB+ RAM and virtualization enabled. Windows is fine (we use WSL2 where needed).
  • Spend money: from Module 2 onward you need one small cloud server (~$5/month) and one domain name (~$10/year). This is the single non-negotiable cost — you cannot learn production on localhost alone.

How to study (the method matters)

  1. Read the lesson once without touching a keyboard. Build the model first.
  2. Answer the quiz from memory, in writing, before checking answers. Retrieval, not re-reading, is what encodes knowledge.
  3. Do the exercise on the real project. Break it deliberately at least once and read the error.
  4. Write one paragraph in your own words in NOTES.md: what problem this solves and what it costs. If you cannot, you have not understood it yet.
  5. Revisit the connection diagram at the end of each module and place the new concept on it.

The project: DevBoard

One application, built and operated for the entire course: a collaborative task board (think a minimal Trello) — chosen because it needs authentication, persistent relational data, caching, sessions, real-time-ish updates, background work and file uploads. That means it exercises every production concern we will study, without being so large that the application code distracts from the operations.

Stack (fixed for the whole course)

  • React — SPA client, built to static assets
  • Express — JSON API, Node.js
  • PostgreSQL — source of truth, migrations
  • Redis — sessions, cache, job queue
  • Docker + Compose — packaging & local orchestration
  • GitHub Actions — CI and automated deployment
  • Nginx — reverse proxy, TLS termination, static serving
  • Prometheus / Grafana / Loki — metrics, dashboards, logs

How it evolves

  1. M1 Repo, branching model, decision log
  2. M2–3 A hardened Linux server you own
  3. M4 Real domain, real HTTPS certificate
  4. M5 Nginx reverse proxy in front of Express
  5. M6 Reasoned hosting decision, cloud VM
  6. M7 Production-grade container images
  7. M8 docker compose up → whole stack
  8. M9 CI gate on every pull request
  9. M10 Push to main → zero-downtime deploy
  10. M11 Backups, secrets, restore drill
  11. M12 Dashboards, alerts, structured logs
  12. M13–14 Scale-out design & capstone review

M1 Foundations & Why DevOps Exists 5 lessons · ~6 hours · Week 1 · start here
Lessons
  1. open →
  5. open →
Prerequisites

None beyond software engineering experience.

Learning objectives
  • Explain the structural conflict DevOps was invented to resolve.
  • Trace the history from Waterfall → Agile → DevOps and say what each fixed.
  • Define lead time, deployment frequency, change-failure rate and MTTR, and measure them on your own work.
  • Draw the end-to-end delivery path and name every stage.
Project increment

Create the devboard repository: monorepo layout, branching strategy, README, decision log (ADR-0001), placeholder CI workflow.

Milestone 1

◆ You can explain, in one diagram and without jargon, everything that happens after you push — and why each stage exists.

M2 Machines: Infrastructure & Operating Systems 5 lessons · ~8 hours · Week 2
Lessons
  1. open →
  2. open →
Prerequisites

Module 1.

Learning objectives
  • Describe what happens between power-on and your process running.
  • Explain why a syscall is expensive and what it protects.
  • Predict how your app behaves under CPU starvation vs memory exhaustion vs disk saturation.
  • Read a cloud instance spec sheet and know what you are paying for.
Project increment

Provision your first Linux server (a $5 VPS) and inventory exactly what is running on it. No app yet.

M3 Linux Fundamentals for Engineers 8 lessons · ~10 hours · Week 3
Lessons
Prerequisites

Module 2 and a running server.

Learning objectives
  • Navigate and administer a Linux server without copying commands from the internet.
  • Run your app as an unprivileged, auto-restarting service.
  • Answer "why is the disk full / the CPU pinned / the port already in use" from first principles.
  • Secure remote access to a machine exposed to the public internet.
Project increment

Harden the server: dedicated deploy user, key-only SSH, firewall, automatic security updates, DevBoard running under systemd (pre-Docker, on purpose).

Milestone 3

◆ You can triage a broken Linux server under time pressure, and DevBoard survives a reboot unattended.

M4 Networking from First Principles 12 lessons · ~14 hours · Weeks 4–5 · densest module
Lessons
Prerequisites

Modules 2–3 (you will use ss, dig, curl, tcpdump on your server).

Learning objectives
  • Follow a request from browser keystroke to your handler, naming every hop and header.
  • Debug DNS, connection-refused, timeout and certificate errors deterministically.
  • Explain what TLS protects, what it does not, and how trust is established.
  • Reason about latency: RTT, handshakes, connection reuse.
Project increment

Buy a domain, configure DNS records, obtain and auto-renew a real certificate, serve DevBoard over HTTPS. Capture your own handshake with tcpdump.

Milestone 4

◆ A browser shows a padlock on your domain, and you can narrate every packet that produced it.

M5 Serving Traffic: Web Servers, Reverse Proxies, Load Balancers 6 lessons · ~8 hours · Week 6
Lessons
Prerequisites

Module 4 (HTTP, TLS, ports).

Learning objectives
  • Justify why application processes should never be exposed directly.
  • Write and reason about an Nginx configuration you did not copy.
  • Distinguish 502 / 504 / 499 and know which component produced them.
  • Explain what must be true of your app before it can sit behind a load balancer.
Project increment

Nginx terminates TLS, serves the React build with cache headers, proxies /api to Express, adds security headers, gzip/brotli, and rate limits login.

Milestone 5

◆ DevBoard is served by a correctly configured reverse proxy and scores well on an external TLS/header audit.

M6 Virtualization & Cloud Computing 6 lessons · ~7 hours · Week 7
Lessons
Prerequisites

Modules 2 and 4.

Learning objectives
  • Explain how one physical machine safely runs many strangers' servers.
  • Choose between a VPS, a PaaS, managed services and serverless with reasons and numbers.
  • Identify what the provider guarantees and what remains entirely your problem.
  • Estimate the monthly bill for an architecture before building it.
Project increment

Write ADR-0002: hosting model comparing VPS + self-managed Postgres vs PaaS + managed Postgres, with a real cost model; then execute your choice.

Milestone 6

◆ You can defend your hosting decision on cost, risk and operational load — not on preference.

M7 Containers & Docker 9 lessons · ~12 hours · Weeks 8–9
Lessons
Prerequisites

Modules 2–4 (processes, filesystems, networking). This module is where they pay off.

Learning objectives
  • Explain containers as a Linux kernel feature, not a virtual machine.
  • Write small, fast, secure, cache-friendly images from scratch.
  • Debug a container that exits instantly, hangs on shutdown, or cannot reach a peer.
  • Decide what belongs in an image, in a volume, and in the environment.
Project increment

Production images for the React build and Express API: multi-stage, non-root, <150 MB, healthchecked, signal-correct, published by digest.

Milestone 7

◆ DevBoard runs byte-identically on your laptop and your server, from the same image.

M8 Composing a System: Multi-Service Environments 5 lessons · ~6 hours · Week 10
Lessons
Prerequisites

Module 7.

Learning objectives
  • Describe a whole system declaratively and start it with one command.
  • Separate build-time from run-time configuration, and code from secrets.
  • Decide when a database belongs in a container and when it absolutely does not.

M9 Continuous Integration 7 lessons · ~8 hours · Week 11
Lessons
Prerequisites

Modules 7–8 and a test suite you are not proud of (that's fine).

Learning objectives
  • Explain why long-lived branches and CI are mathematically opposed.
  • Build a pipeline that fails in under 5 minutes when it should fail.
  • Produce one immutable artifact per commit and never rebuild it.
  • Give CI exactly the permissions it needs and no more.
Project increment

Every pull request runs the full gate; every merge to main publishes a digest-pinned image to GHCR with provenance metadata.

Milestone 9

◆ Nothing reaches main without machine-checked proof that it builds, passes and is scanned.

M10 Continuous Delivery & Deployment 8 lessons · ~10 hours · Week 12 · the payoff module
Lessons
Prerequisites

Modules 5, 8, 9.

Learning objectives
  • Design a deployment that never serves an error during a release.
  • Choose a deployment strategy from traffic, risk and infrastructure constraints.
  • Ship a schema change across three deploys instead of one big-bang.
  • Recover from a bad deploy in minutes, on purpose, having practised it.
Project increment

Merging to main automatically deploys DevBoard to production with zero downtime, runs migrations safely, verifies health, and rolls back on failure.

Milestone 10

◆ You deploy on a Friday afternoon without anxiety, several times, and can prove no request failed.

M11 Production Reality: Reliability & Security 5 lessons · ~8 hours · Week 13
Lessons
Prerequisites

Module 10 (you need something worth protecting).

Learning objectives
  • State your own RPO/RTO and prove you meet them.
  • Keep credentials out of Git, images, logs and CI output.
  • Make your service fail partially instead of totally under overload.
  • Run an incident and write a postmortem that produces change, not blame.

Automated encrypted nightly Postgres backups to object storage, a scripted restore into a throwaway environment, and a written incident runbook.

Modules 8, 10, 11.

Learning objectives

  • Read a p99 latency graph and explain what it does and does not tell you.
  • Write an alert that would have caught your last outage — and no others.

M13 Orchestration: Kubernetes, Conceptually 5 lessons · ~6 hours · Week 15 · no cluster required

Modules 7–10.

Learning objectives

  • Translate any Compose service into the equivalent K8s objects.

M14 Production Architecture — Capstone 7 lessons · ~8 hours · Week 16
Lessons
Prerequisites

All previous modules.

Learning objectives
  • Design an architecture for a stated load, budget and reliability target.
  • Identify the bottleneck in a system before it is reached.
  • Justify every component you added — and every one you refused.
  • Hand your system to another engineer using only your documentation.
Capstone deliverable

DevBoard v1.0: live on your domain over HTTPS, containerized, CI-gated, auto-deployed with zero downtime and rollback, backed up with a tested restore, monitored with dashboards and alerts, documented with architecture diagram, ADR log and runbook.

Milestone 14 · final

★ You can build, ship, operate and defend a production system alone — and explain every layer beneath it.

Milestone timeline

  • M14 · Independent engineerBuild, deploy, operate, document and defend a production system by yourself.
The point of all this

At the end you are not a DevOps engineer, and that was never the goal. You are a software engineer who cannot be blocked: you can take an idea to a URL that real people use, keep it up, know when it is unhealthy, fix it, and explain every layer between your code and the user's screen. That independence is the deliverable.
